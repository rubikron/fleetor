title: "Phase 3: the pane registry and the `fleet` CLI"
phase: "3"
status: alive
---

- **The two halves landed together**, because neither is demonstrable alone. `crates/fleetor-cli` became the `fleet` binary — five verbs over the unix socket, no MCP server — and `src-tauri/src/pty.rs` became a `PaneRegistry` of N ptys keyed by `PaneId`.
- **Per-pane event channels** (`pty://output/2`, `pty://exit/2`) are a correctness boundary before a performance one: pane 2's component *cannot* receive pane 1's bytes if it never listens on that name. The perf win (L6 chokepoint #2 — `AppHandle::emit` wakes every listener on a name, so a shared channel means 5× the JS wakeups for zero benefit) comes free with it.
- **The read pump is two threads, not one.** A single thread can only check its coalescing window *after* the next blocking `read` returns, so the tail of a burst would sit unflushed until the pane happened to print again — the last line of a finished turn, invisible for as long as the pane stays quiet. The coalescer's `recv_timeout` has no such blind spot.
- **One write, one lock.** Paste-open, body, paste-close, 30 ms, `\r` — all under a single hold of that pane's writer mutex. Tauri dispatches sync commands on a thread pool, so a keystroke racing a delivery could otherwise land between a message's body and its submit. The lock is per-pane, so the 30 ms costs that pane's keystrokes and nobody else's.
- **The delivery loop never blocks.** Each `Deliver` goes to `spawn_blocking`. Inline, five panes would serialize behind each other, and the hub awaits broadcast legs one at a time — so a slow pane's cost multiplies by the roster.
- **The L1 re-seed requirement is met structurally.** `seed_config_dir` is called at the spawn site, next to the cwd it is keyed by, rather than at the target picker. `hasTrustDialogAccepted` is keyed by absolute project path, so it can now be got wrong by deleting a line but not by forgetting a code path.
- **`fleet_bin_path` is an explicit ladder with an existence check at every rung**, and a `Notice` when it comes up empty. The shim it replaces resolved its binary through a hand-made untracked symlink, behind a doc comment claiming cargo put it there — it did not; these are two cargo workspaces with two target dirs (L4).
- **`kill_all` signals the process group.** `openpty` gives each pane its own session, so killing the pid alone can leave a `claude`'s children running with no terminal and nobody watching. For an Opus session that is a bill that keeps growing after the window closes.
- **Deviations:** no `pending`/`last_input_at` on `Pane` — nothing reads them, and they exist in the plan only to support the idle guard and flush ticker D-034 bans; dead state whose only purpose is a banned pattern is the same trap as the `lead://inject` queue Phase 2 deleted. `src-tauri` became a lib plus a one-line bin, because a bin-only crate cannot expose `PaneRegistry` to an integration test and a registry only exercisable through a GUI is a registry nothing tests. Worker worktrees live under `~/.fleetor/_shell/worktrees/` rather than inside the target so they never appear in the operator's `git status`, with an announced fallback to sharing the checkout when git refuses. `kill` leaves the exit event to the pump, which fires it on EOF — two deaths for one process is a visible wart.
- **Verified:** `tests/fake-pane/fake-pane.sh` plus a `FLEETOR_PANE_CMD` override gives six zero-token tests over five real ptys — channel isolation both ways, a message landing in its target and nowhere else, keystrokes and deliveries sharing a writer, a dead pane refusing by name, a killed pane respawning, `kill_all` reaping the fleet. Deliberately *not* covered: whether a live `claude` reaches its prompt. That is L1/L2, settled by measurement in Phase 0, and a fake pane would answer it wrong in the reassuring direction.
