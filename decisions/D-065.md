id: D-065
title: "WP-17: the write guardrail is a `PreToolUse` hook, writes only, and its Bash half enforces stated intent"
phase: "WP-17"
status: alive
---

- **What changed.** Every pane now spawns with a `PreToolUse` hook installed into its own `CLAUDE_CONFIG_DIR` (`src-tauri/src/guardrail.rs`, called from `fleet::spawn_pane` beside `seed_config_dir`), refusing any `Bash` / `Write` / `Edit` / `MultiEdit` / `NotebookEdit` call that would write outside that pane's roots. The roots are the pane's **own cwd** — a worker's git worktree, `orch`'s target repo — plus `~/.fleetor/_shell/`, minus `_shell/pane-config/`. Reads are untouched: the hook is not registered for `Read`, `Grep` or `Glob`, so it is never consulted about one. A refusal names the path as written and as resolved, which rule fired, the full root list, and what to do instead; it also appends a line to `~/.fleetor/_shell/guardrail.jsonl`, which a task of the fleet's own drains onto the Activity feed once a second. `prompts/launch.conf`'s `[fence]` section gained a repeatable, absolute-only `allow` key.
- **Why this shape and not the two the operator rejected.** A read denylist and a full read+write allowlist were both considered. Reads stay open because a Bash command a hook allows can read anything internally — read-blocking is friction wearing enforcement's clothes — and because a read allowlist has to cover every toolchain path, which wedges a pane in the way that looks exactly like a healthy pane (the risk register's worst entry). Network blocking is not here either: D-063 already settled that the answer key's mitigation is a post-hoc transcript audit, not egress control. Stripping the inherited environment is the sandboxing decision `docs/notes/fence-notes.md` rules out by name.
- **The gate was verified before anything was built on it.** WP-12's deny-layer list called `PreToolUse` interception of `Bash` unverified for the installed version. `examples/write-guardrail-spike/probe.py` settled it against CC 2.1.224 with four real `claude -p` arms, checking the **filesystem** rather than the model's prose: a deny stops the tool call, the reason reaches the model as words it acts on (in one arm it redid the write inside the worktree), and — the strong form — **the hook's deny beats an explicit `--allowedTools` allow**, which is the posture a worker actually runs in.
- **Why the Bash half enforces *stated intent*, and why that is the honest scope.** `Write`/`Edit`/`MultiEdit`/`NotebookEdit` name their destination in the tool call, so those refusals are enforcement. `Bash` does not, and two measurements decided the rule rather than a plan (`building.md` §4). A worker's first `git commit` writes **eight files into the target repo's `.git`** — outside its allowlist, by design of `git worktree` — and `fleet done` runs it first, so a guardrail built as a real write sandbox would have wedged every worker on receipt one. A real `cargo build` writes into `~/.cargo/registry` and names nothing at all. Both pass because the scanner only sees paths a command *states*, and both are now pinned by a test; `git -C <somewhere outside> commit`, which does state one, is refused.
- **Where the setting went, and why not a third mechanism.** `prompts/launch.conf`'s `[fence]` section, not `~/.fleetor/config.json`. D-052 created that key saying it exists "so a future one has somewhere to land without a new setting surface", and this is that future one: `launch.conf` is the hand-edited, documented, read-once-at-bootstrap file, whereas `config.json` holds app state the app itself writes (the target, WP-16's `dev_mode`). `allow` is additive and repeatable — "one more directory the fleet may write in" is the shape of the request — and refuses a relative path with the reason, because a relative root would resolve against each pane's own cwd and mean five different directories from one line.
- **Tier 1.7 is narrowed here, not widened, and that is stated so it is not re-litigated.** Workers already spawn `--permission-mode auto` scoped to their worktree; this refuses a subset of what that allowed. §9.2's escalation trigger is *widening* auto-approve. **Tier 1.4 is held structurally, not promised:** the hook is consulted by Claude Code inside the pane's own process, and `src-tauri/tests/write_guardrail.rs` pins both directions — no delivery-path file mentions the guardrail, and `guardrail.rs` mentions no `Hub`, `AppCommand`, `PaneRegistry`, `Op` or `deliver::`. Its only outputs are a settings file and a journal line, and nothing on the message path ever waits on either. D-062 is what makes any of this possible for `orch`: before it, `orch` ran on the operator's own config dir, which is not somewhere this app may write policy.
- **What it does not stop, named rather than implied.** A write whose path the command does not name (`cargo build`, `python3 -c` with a runtime-assembled path) — structural, and closing it means the OS sandbox the arc rules out. A pane disabling its own hook via `$CLAUDE_CONFIG_DIR/settings.json`, which is not a literal path — `_shell/pane-config/` is refused by spelling only. The journal is inside `_shell`, so a pane can mangle it; a bad line is skipped and the real ones around it still report, and losing a notice never costs a decision.
- **A pre-existing Fence breakage the spike found and this package deliberately did not fix.** A worker cannot `cargo build` at all: the Fence redirects `HOME`, rustup resolves `$HOME/.rustup`, and the private home has no toolchains — measured with the guardrail entirely uninvolved. `fence-notes.md`'s catalogue checked `gh` and reasoned about `nvm`; it never checked rustup. This is exactly the "live evidence that a worker legitimately needs a tool" D-052 reserved as its own reversal condition, and the fix is a Fence decision with its own entry, not a root on this allowlist. It is WP-17 open question 1, and an improve run is a Rust build, so it wants closing first.
- **What would reverse it.** Live evidence that the write-position scanner refuses something a pane legitimately needs — the fix is a case in `examples/write-guardrail-spike/cases.py` and a rule beside it, not a wider root. Evidence that panes are routinely denied for `/tmp` scratch files, which is one `allow = /tmp` line. Or Claude Code changing the `PreToolUse` contract, which is version-stamped at 2.1.224 in `docs/notes/write-guardrail-notes.md`; the degradation there is the loud kind only if someone re-runs the probe, which is why that file names the reproduce command.
- **Verified:** 210 workspace tests green (unchanged — WP-17 touched no core crate) and **143** shell tests green, up from 121: 121 lib (including 11 new `guardrail` unit tests and 3 new `[fence] allow` parser tests), 3 dev-mode, 11 real-pty unchanged, and 8 new in `tests/write_guardrail.rs` that drive the decision through the *installed* `settings.json` command with a real shell. `npx tsc --noEmit` and `npx vite build` clean; no UI or prompt-template file touched, so `brief-cost` stayed at the spec's own 0. **Not verified:** the guardrail on an interactive pane inside the running app — the same honest gap D-062 records for `orch`'s config dir; no fleet has been started since this landed. Live spend: four `haiku` print-mode turns, ~$0.13.
