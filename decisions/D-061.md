title: "WP-16: dev mode is a key in the operator's config, not a webview preference"

- **What changed.** Dev mode is stored as `dev_mode` in `~/.fleetor/config.json` and read on the Rust side through exactly one function, `dev::is_enabled()`, which re-reads the file rather than caching a boot-time snapshot. The UI is a view of that flag, never a second copy: `dev_mode_get` / `dev_mode_set` are the whole surface, the settings switch does not move until the write has landed, and the coral band is rendered from what came back. Two tests hold the boundaries the mode must not cross — no file on the path from `fleet send` to a pty may mention it (Tier 1.4), and no prompt file, brief renderer or roster type may either (WP-12's open question 4, answered the cheap way).
- **Why the default lost.** The established pattern for an app-wide preference in this repo is `localStorage`, where the theme and the nav selection live — and dev mode looks like one more of those. It is not one: WP-15's evaluator window and WP-17's fence branch on the mode from code that has no webview, so a `localStorage` flag would have to be mirrored to Rust, and two copies of one fact means the copy that is wrong is the one somebody reads. A second file under `~/.fleetor` was the other candidate and lost to "a mode with its own file is a mode the operator has to be told where to find" — `config.json` is where they already set the target. Reading fresh rather than snapshotting at bootstrap is the inverse of the call made for `Fleet::target`: a target has an incoherent half-state (half a fleet in one repo), a mode has none today, and caching would have pre-empted WP-15's decision about its own window's lifecycle.
- **What would reverse it.** A reader on a hot path that cannot afford a file read per call — at which point the answer is a cached handle *at that call site*, not a second store. Or WP-15 finding that a mode which can change under a running evaluator is a real hazard, which would make the flag snapshot at bootstrap like the target does; the seam for that is one function, `is_enabled`. **Not verified:** the band was reviewed against building.md §7 rule by rule but never seen on screen — this repo has no frontend test framework, and adding one is a Tier 2 dependency decision left to the operator, so nothing about the React half of this is machine-checked.
