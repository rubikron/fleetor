## D-001 — Working name: FLEETOR

- **What:** Project branded FLEETOR (was: Fleet).
- **Why:** max's call; "for now" — expect a possible rename before any public artifact.
- **Reverses if:** a real name is chosen; grep-friendly, so a rename is one pass.

## D-002 — DeepSeek reached via Anthropic-compatible endpoint, not LiteLLM

- **What:** Workers point at `ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic` with `ANTHROPIC_MODEL=deepseek-v4-flash`, auth via `ANTHROPIC_AUTH_TOKEN`. No LiteLLM/OpenRouter proxy (handoff cited those from memory).
- **Why:** DeepSeek ships a native Anthropic-compatible endpoint; removes a proxy hop and a dependency. Verified working in Phase 0.
- **Reverses if:** the endpoint drops tool-use fidelity or a model not on it is needed — slot a proxy behind the same `AgentProcess` seam.

## D-003 — Workers run under an isolated `CLAUDE_CONFIG_DIR`

- **What:** Every worker spawns with `CLAUDE_CONFIG_DIR` pointed at a fleet-owned dir, never the operator's `~/.claude`.
- **Why:** Phase 0 measured the operator's global config leaking in (28 tools, personal MCP servers, global CLAUDE.md) at ~36k input tokens/call and a polluted tool surface; isolation drops it to vanilla CC (~26k, 25 tools, 0 MCP). Also upholds the Tier-1 zero-footprint boundary. Profiles (handoff §7) layer on top of this clean base.
- **Reverses if:** we deliberately want the operator's project `.claude/` to flow through — then inherit that dir explicitly rather than the personal global one.

## D-004 — `total_cost_usd` ignored; cost computed from token counts

- **What:** Real cost = tokens × DeepSeek Flash rates ($0.14 in / $0.28 out per M, cache-read ~0.1×), computed in `fleetor-cli`. The `result.total_cost_usd` field is kept for reference only.
- **Why:** Claude Code computes `total_cost_usd` from its built-in Anthropic price table via model-name mapping — off by ~30× against DeepSeek ($0.13 reported vs ~$0.004 real).
- **Reverses if:** DeepSeek's endpoint starts returning a trustworthy cost field, or published rates change (update the constants in `report.rs`).

## D-006 — Phase 0.5 pty spike: PASS (GO); no companion-window fallback

## D-007 — Spike shell: standalone `src-tauri` package, plain-TS frontend

- **What:** `src-tauri/` is its own cargo workspace (empty `[workspace]`), deliberately **not** a member of `crates/*` — keeps tauri's dep tree and build profile out of the clean fleetor-cc/cli lockfile. The spike frontend is plain TypeScript + xterm.js (no React), single Vite host at repo root with source under `ui/`.
- **Why:** YAGNI + isolation. A one-terminal spike needs no framework; a framework would be dead weight. Isolating the tauri workspace means a UI-layer build problem can never hold the headless core hostage (BUILDING §3).
- **Reverses if:** Phase 4 (the real shell) folds `src-tauri` into the main workspace and adopts React per BUILDING §2 — expected, and cheap since the spike is throwaway-grade.

## D-010 — Assign-first: don't gate the first stdin write on the `init` event

- **What:** The supervisor writes the ticket to the worker's stdin *immediately* after spawn, then reads the event stream (consuming `init` inline). It does **not** "read stdout until init, then send" as handoff §5 step 2–3 prescribes.
- **Why:** Verified against real Claude Code: in `-p --input-format stream-json` mode, `claude` emits `system/init` only *after* it begins processing the first stdin message. Gating the first write on `init` deadlocks (server waits for init; CC waits for input) — the symptom was a real-CC run that produced zero events until the wall-clock kill. The handoff explicitly said to verify event ordering against the installed CC rather than trust the doc; this is that correction. Multi-turn streaming confirmed in the same probe (the process stays alive after `result`, awaiting more input), which the no-report reprompt relies on. `session_id` is still captured from `init` when it arrives; it just isn't needed to send the first message.
- **Reverses if:** a future CC emits `init` eagerly at startup — the assign-first path still works (init consumed earlier), so no revert needed; only revisit if streaming multi-turn semantics change.

## D-008 — Phase 1 report ingested from a transcript block, not MCP

- **What:** In Phase 1 the worker files its report by ending its final message with a fenced ```` ```fleet-report ```` JSON block; the supervisor extracts and parses it from the transcript (`Report::from_transcript_text`). The assignment message carries the schema and an example. The real `report()` MCP tool (handoff §4) is **not** built yet.
- **Why:** The MCP `report()` channel needs the stdio-shim + unix socket, which is Phase 2's deliverable. Transcript-block ingestion makes the full ticket lifecycle testable end-to-end *now* (against fake-claude and one real-CC run) without pulling Phase 2 forward. Reversible: when the shim lands, `report()` becomes primary and this parser stays as the "no report filed" backstop (handoff §5).
- **Reverses if:** Phase 2 wires the MCP surface — then reports arrive as structured tool calls and the transcript scrape demotes to a fallback (or is dropped if the tool proves reliable).

## D-009 — Phase 1 crates: added `fleetor-core`, `fleetor-db`, `fleetor-server`

- **What:** Grew the workspace from 2 crates to 5, per BUILDING §3's layout: `fleetor-core` (frozen contracts — envelope, events, report, ticket, `Store`/`AgentProcess` seams), `fleetor-db` (rusqlite + migrations, the 5-table sketch), `fleetor-server` (the supervisor loop). `fleetor-cc` gained the streaming `supervised_command`, the `AgentProcess` seam, and the persistent stdin/stdout `Session` driver.
- **Why:** Phase 1 is when supervision, persistence, and the contract layer are first needed (D-005 said add crates when their phase needs them). Only two of the four sanctioned seams are introduced — `AgentProcess` and `Store`; `Transport` and `GateRunner` are deferred to their phases (2, 3) to avoid speculative abstraction (BUILDING §8).
- **Reverses if:** a crate proves to carry no weight — collapse it back. `fleetor-server` in particular is a lib so Phase 4's Tauri app can consume it directly.

- **What:** Created just the two crates Phase 0 needs (not the full 6-crate layout), and the spawn/stream path uses `std::process` + threads, not tokio.
- **Why:** YAGNI + reversible. `fleetor-cc`'s spawn builder returns a `Command` whose env/arg logic ports to `tokio::process` unchanged; remaining crates (core/db/server/shim) get added when their phase needs them.

## D-011 — Phase 2 adopts tokio for the socket + hub (D-005/D-009 deferral resolved)

- **What:** `fleetor-ipc` (the new `Transport` crate) and `fleetor-server`'s hub run on **tokio**. The Phase 1 sync supervisor (`std::process` + threads + mpsc) is untouched and still passes; only the new Phase 2 surface is async.
- **Why:** Phase 2 multiplexes a socket accept loop + N worker connections + a blocking lead long-poll (`await_events`) + blocking `ask_lead` waiters — the exact "async multiplexing" D-009 said would trigger the promotion, and the runtime BUILDING §2 already names. `tokio::sync::{oneshot, Notify}` model the ask/reply and long-poll cleanly; hand-rolling them on `Condvar` would diverge from §2 for no gain.
- **Reverses if:** the async surface proves not to earn its keep — unlikely now that the hub, shim, and CLI all consume it.

## D-012 — New `Transport` seam lives in its own crate `fleetor-ipc`; wire types in `fleetor-core`

- **What:** The socket **wire contract** (`Request`/`Response`/`Op`/`OpResult`/`LeadEvent`/`Hello`, versioned `WIRE_VERSION=1`) is pure serde in `fleetor-core::wire`. The **transport** (the `Transport` trait — the 3rd sanctioned seam — plus `UnixTransport`, framed `Conn`, and a `Client` helper) is a new crate `fleetor-ipc`, depended on by both `fleetor-server` and `fleetor-shim`.
- **Why:** Contracts belong in core (BUILDING §4) and must stay tokio-free; the I/O belongs behind the seam. A shared crate keeps the shim from depending on the whole server, and isolates the socket in one module (BUILDING §2 IPC row) so a Windows named-pipe impl slots in behind the same trait. Framing is newline-delimited JSON over any async duplex, so the transport can change without touching the framing.
- **Reverses if:** a second transport never materializes and the trait carries one impl forever — collapse `Transport` to the concrete `UnixTransport` (BUILDING §8 over-abstraction guard).

## D-013 — One socket, two faces; worker/lead op split enforced structurally

- **What:** The hub serves workers and the lead on one socket; a connection declares its `Party` via `Hello`. The wire `Op` enum holds both faces, and the hub **rejects** a lead op from a worker connection and vice-versa. `ask_lead` is the *only* worker blocking op; there is no worker↔worker blocking op in the enum at all.
- **Why:** Makes Tier-1.5 (blocking is worker→lead only; no worker↔worker deadlock primitive) a property of the type surface, not a convention. Mail (`dm`/`broadcast`/`send`) is always async and persisted to the `mail` table (source of truth, survives a crash — handoff §11); questions/notices and `ask_lead` reply-waiters are in-memory and transient (a crash drops an in-flight ask, which times out to the park answer).
- **Reverses if:** a future need for lead↔lead or a second blocking worker op appears — revisit the split, but never add a worker→worker blocking op (Tier-1.5 is max's).

## D-014 — Mid-turn mail framing: coordination, not commands (spike-derived)

- **What:** The Stop-hook injects queued mail as a `block` decision whose `reason` is explicitly framed as *in-band teammate coordination that augments the current task*, never as a new instruction. Delivery is via the shim binary's `stop-hook` mode; an empty queue emits nothing (turn ends), and the queue emptying is the loop terminator (no `stop_hook_active` bookkeeping needed).
- **Why:** The Phase 2 spike (`docs/phase2-spikes.md`) showed real Flash **refuses** injected text that reads as an override of its task ("treating it as data, not a command") — correct model behavior. The delivery *channel* is proven; only the *framing* needed care. The MCP + Stop-hook mechanisms themselves passed against installed CC 2.1.220 (fixtures in `tests/fixtures/`), so no escalation to max was needed.
- **Reverses if:** a later CC changes Stop-hook re-injection semantics — the fixtures are version-stamped; re-capture and diff.

## D-015 — Report-over-MCP and the idle/opportunistic delivery paths deferred within Phase 2

- **What:** Phase 2 builds the messaging *core* — `ask_lead`/`reply`, `notify_lead`, `dm`/`broadcast`, `await_events`/`inbox`, and turn-boundary (`drain`) delivery. Deferred: (a) `report()` as an MCP tool (still transcript-scraped per D-008); (b) the "idle → server writes to stdin" and "opportunistic piggyback on a tool result" delivery paths (handoff §5) — only turn-boundary drain is wired; (c) `whos_working_on`/`claim_file`/`backlog_add` (handoff §4), which serve the Phase 3 ownership/quality loop.
- **Why:** YAGNI against the exit test (BUILDING §6): the scripted 3-agent conversation with a mid-turn delivery needs exactly the core above. The deferred items are additive behind the same wire surface.
- **Reverses if:** their phase arrives — report-over-MCP and ownership tools are natural Phase 3 companions; idle/opportunistic delivery lands when the multi-worker supervisor (Phase 4 shell) drives real turn boundaries.

## D-016 — Phase 3 quality loop is supervisor-level; report-over-MCP wired at the hub, primary in Phase 4

- **What:** The quality loop (gate → auto-bounce → peer review → done) lives in `fleetor-server::quality`, driving one worker session over stdin/stdout (reusing the Phase 1 `assign`/`drive_to_report` primitives, now kept alive across bounces) plus a **fresh reviewer session** per review round. Report/verdict are transcript-scraped (`fleet-report` / new `fleet-review` fenced blocks). Separately, `report()` is promoted onto the MCP surface (`Op::Report`, shim `report` tool, hub persists + emits `report-filed` + notifies the lead), proven at the hub layer — but the *supervisor's* ingestion stays transcript-scrape.
- **Why:** The supervisor (stdin/stdout) and the hub (socket) are deliberately unwired until Phase 4's multi-worker runner (BUILDING §6 table; D-015). Making report-over-MCP the supervisor's primary path now would require the supervisor to consume hub events — pulling Phase 4 forward. Keeping the loop supervisor-driven makes the exit test ("buggy ticket bounces, gets fixed, passes review") fully testable against fake-claude + a real shell gate with zero tokens, exactly as Phases 1–2 were.
- **Reverses if:** Phase 4 unifies the runner with the hub — then `report()`-over-MCP becomes the supervisor's primary ingestion and the transcript scrape demotes to the "no report filed" backstop (handoff §5); the `fleet-review` verdict can move onto an MCP tool the same way.

## D-017 — GateRunner seam takes config, not discovery; two retry caps default 3; `claim_file` carries the ticket

- **What:** `GateRunner` (the 4th sanctioned seam) is `run(cwd) -> GateReport`; *which* commands is `GateSpec` config on the concrete `ShellGateRunner` (`sh -c` per check, exit 0 = pass, combined output tailed to 4 KB for the bounce). Gate *discovery* (reading CLAUDE.md/package.json/Makefile — handoff §3) is left to Phase 4. The loop uses two retry caps — `gate_retry_cap` and `review_retry_cap`, both default 3 — escalating to the lead (ticket → `Blocked`) after the cap rather than grinding. Added a `ReviewResult`/`ReviewOutcome` event variant and a `backlog` table (migration 0002); `whos_working_on`/`claim_file`/`backlog_add` route through the hub against the existing `leases` table + the new `backlog` table. `claim_file(path, ticket)` carries the worker's ticket id (a Tier-2 tweak over handoff §4's `claim_file(path)`) so the hub records the lease without tracking slot→ticket state it doesn't yet own.
- **Why:** The seam stays model-agnostic (a future non-shell runner keeps the same face); config-not-discovery is YAGNI for the exit test. Separate caps because gate and review failures are independent loops. Escalate-to-Blocked matches handoff §8 ("capped at ~3 retries then escalate"). Carrying the ticket on `claim_file` avoids inventing hub-side assignment state before Phase 4 wires it.
- **Reverses if:** Phase 4 gives the hub real slot→ticket assignment (drop the `ticket` arg, infer it) or discovery lands (the spec is populated by a scan instead of a literal).

## D-018 — Phase 4a fleet runner lives in `fleetor-server::runner`; sync supervisor bridged to the async hub via `spawn_blocking`; `WorkerSpec` carries the `AgentProcess` seam so fake and real share one path

- **What:** The multi-worker fleet runner is a module in `fleetor-server` (`run_fleet`), not a new crate. It boots the hub on a tokio runtime, connects a stand-in lead `Client`, spawns a `run_lead_loop` (long-polls `await_events`, answers `ask_lead`, sends mid-turn mail), and runs each worker's **sync** supervisor (`run_ticket`, the Phase 1 std-process/threads loop) on `tokio::task::spawn_blocking`. Worker fleet-wiring (the `--mcp-config`/`--add-dir`/`mcp__fleet` allow-list, the `fleet-mcp.json` + `settings.json` Stop hook, and `FLEET_SOCKET`/`FLEETOR_SLOT` env) is written by `WorkerConfig::write_fleet_config()` and lives entirely in `fleetor-cc::spawn` — the one place that knows how a fleet worker differs. `WorkerSpec` holds a `Box<dyn AgentProcess + Send>` with `::real(config,…)` / `::fake(agent,…)` constructors, so the fake-claude integration test and the live `fleetor run --real` drive the identical runner.
- **Why:** The sync↔async seam is the core Phase 4 problem (BUILDING §6 table: supervisor and hub were deliberately unwired through Phase 3). `spawn_blocking` bridges them without rewriting the proven sync supervisor to async or hand-rolling a second event loop — the two channels stay decoupled for 4a (report-over-MCP as the supervisor's *primary* signal, and idle/piggyback delivery, are still deferred; see below). Routing `WorkerSpec` through the `AgentProcess` seam (rather than hardcoding `RealClaude`) is what lets the whole runner be exercised for free against fake-claude's dual-personality worker (stdin-driven **and** socket-speaking at once), keeping the live-CC run a confirmation gate rather than the only test. Runner-in-server (not a 7th crate) because Phase 4's Tauri app consumes `fleetor-server` directly (D-009); a crate would carry no weight (BUILDING §8).
- **Live confirmation (the 4a gate, cost ~cents):** `fleetor run --real` drove one real Flash worker fully wired. Event log showed the full loop: `mcp__fleet__ask_lead` → worker **blocked** → lead answered → worker **working** → `mail` (lead→worker-1) → `Write`/`Bash`/`mcp__fleet__report` → ticket **done**. Two independent proofs the messaging landed in-model: (1) the worker named the file `hello.sh` — exactly the lead's reply, not the decoy `greet.sh` — so the blocking `ask_lead` answer was consumed, not ignored; (2) the transcript shows the Stop-hook mail delivered and the model reasoning *"coordination only, keep to my ticket… my ticket is already done"* — the D-014 framing worked against real CC 2.1.220, not just fixtures.
- **Followups (not bugs):** (a) the worker called `mcp__fleet__report` **twice** (once before, once after acknowledging the mail), yielding two `report-filed` events; ticket state transitions once (idempotent), so it's benign — but mail-arriving-after-a-report can prompt a redundant report, worth smoothing when 4b makes report-over-MCP primary. (b) `fleetor run` has no free fake path (it `bail!`s without `--real`); the fake path is the `fleet_runner` integration test, by design.
- **Reverses if:** 4b lands the D-015/D-016 reversals — report-over-MCP becomes the supervisor's primary ingestion (transcript scrape demotes to the "no report filed" backstop) and idle→stdin / opportunistic-piggyback delivery join turn-boundary drain. If the sync supervisor is ever rewritten to async, `spawn_blocking` drops out; until then it is the seam.

## D-019 — Phase 4b: report-over-MCP is the supervisor's primary done-signal; the sync↔async bridge is the shared event log; quality loop stays transcript-scrape; D-015 idle/piggyback deferred to 4c/4d

- **What:** The base supervisor (`run_ticket`) now treats the worker's `fleet.report` MCP call as its **primary** terminal signal (the D-016 reversal). The hub already persists the report and appends `ReportFiled`; the supervisor watches the shared event log — a new `Store::latest_seq()` cursor captured at assign, scanned via `events_since` at each turn boundary (`mcp_report_step`, with a bounded ~500ms `grace_poll_mcp_report` for the hub task's commit lag) — and finishes on that event *without re-saving or re-emitting*. It's a plain `ReportStep::Terminal { Reported }`, so no new outcome variant. The transcript `fleet-report` scrape (D-008) is demoted to the backstop for a turn that ends with a block instead. Gated behind a `prefer_mcp` flag on `drive_to_report`: `run_ticket` passes `true`; the **quality loop passes `false`** and is unchanged.
- **Why:** This is the tight coupling Phases 1–3 deliberately left open (the runner doc's "4b"). The key design move: the sync supervisor (`spawn_blocking`) and the async hub (tokio) are bridged through the **shared, persisted event log they both already hold** — no cross-runtime channel, no rewrite of either loop (KISS). Report-over-MCP being primary also removes the supervisor's transcript-scrape *duplicate* — note the 4a live double-`ReportFiled` was actually the model invoking `fleet.report` **twice** (two hub emits), a separate worker-behavior/hub-idempotency concern the supervisor can't and shouldn't police; 4b guarantees only that the *supervisor* adds no duplicate (deterministically proven by the `mcp-report` fake: exactly one `report-filed`, no scrape).
- **Quality loop stays transcript-scrape:** it needs the full `Report` **body** to attach gate results and drive bounces; the event-only primary path carries just `status`. Unifying it needs a `Store` report-load read + a `fleet-review` MCP tool — a natural 4c/4d companion (D-016's own reversal note). `prefer_mcp = false` keeps it byte-for-byte as Phase 3 shipped.
- **D-015 idle/opportunistic delivery deferred (again, deliberately):** idle→stdin and piggyback-on-tool-result have no live consumer yet — no idle detection and no real orchestrator — and turn-boundary Stop-hook drain already covers the headless worker (proven in 4a). YAGNI: they land in 4c/4d where live turn boundaries and the orchestrator TUI make them meaningful. Only the D-016 half of the "4b" plan is delivered here.
- **Verified:** `runner_terminates_on_report_over_mcp_no_double_log` — a worker that files only over the socket (no transcript block) closes `Done` via the hub event with exactly one `report-filed`; the existing `fleet-ask` test now exercises the backstop (transcript block) path. Full suite 44 tests, 0 warnings. No live-CC spend: the fix is deterministic at the supervisor layer; a real re-run is confounded by model nondeterminism (a worker may still call the report tool twice).
- **Reverses if:** the quality loop is unified onto report-over-MCP (drop `prefer_mcp`, add the report-load read) — then transcript-scrape becomes a pure backstop everywhere; or if `latest_seq`/`events_since` polling proves too coarse under a busy multi-worker log (promote to a per-slot notify channel from the hub).

## D-020 — Phase 4c: the live event bus is a `Store` decorator (`BroadcastStore`) in `fleetor-server`, not a new emit path; persist-then-publish; lag recovers from the DB

- **What:** The UI's live event feed (README roadmap "4c") is delivered by wrapping the [`Store`] seam. `fleetor-server::bus` adds `EventBus` (a `tokio::sync::broadcast` fan-out of `(seq, FleetEvent)`), `BroadcastStore` (a `Store` decorator that delegates every method and, right after a successful `append_event`, publishes the row's real `seq`), and `EventFollower` (`EventBus::follow(store, after)` → an async `next()` that yields the DB snapshot then live events, gap-free and dup-free). Wrap the inner store once and **both** emitters — the sync supervisor (`supervisor::emit`) and the async hub (`Hub::emit`) — publish for free; neither loop is touched. `fleetor run` now wraps its store and prints events live via a follower task (replacing the post-hoc `print_event_tail` dump). Capacity is `BUS_CAPACITY = 1024`.
- **Why:** Every event already funnels through the one chokepoint `Store::append_event`; a decorator there captures all of them with zero change to the proven Phase 1–4b code (KISS + reversible — unwrap and you have a plain store, BUILDING §8). The bus lives in `fleetor-server`, not `fleetor-core`, because it needs `tokio` and core must stay tokio-free (D-012). **Persist-then-publish** keeps the DB the single source of truth (matching the 4b "shared, persisted log" bridge, D-019): publish is best-effort (no subscribers = no-op; the event is already durable), and a follower that joins late or lags the bounded ring recovers by re-reading `events_since(cursor)` — the channel only *accelerates* delivery, it never becomes a second source of truth. `broadcast::Sender::send` is sync and runtime-free, so the sync supervisor thread publishes without a handle to the runtime. This is the substrate 4d (orchestrator feed) and 4e (Tauri event pump) consume.
- **Verified:** `event_bus.rs` (4 tests) — a subscriber live for a whole `run_fleet` receives *exactly* the persisted log (same seqs, strictly increasing, no gaps/dupes); a late subscriber gets the full DB history then live events seamlessly across the snapshot boundary; a follower flooded past `BUS_CAPACITY` without reading recovers **every** event from the DB, contiguous and in order; and a bare `EventBus` fans one publish to all subscribers. Full suite 48 tests, 0 warnings. No live-CC spend (deterministic at the store/bus layer).
- **Reverses if:** a second transport for the feed never appears and `broadcast` proves heavier than needed — collapse to a plain `Vec<Sender>` or a single mpsc; or if per-event fan-out is too coarse for the UI, batch in the follower. If the Tauri app (4e) would rather subscribe from inside the app process than through the CLI, `BroadcastStore::bus()`/`follow()` are already the public handles it consumes.

## D-021 — Phase 4d: orchestrator-as-lead drives a *dynamic* fleet over the lead MCP face; the lead seat becomes external; `run_fleet` stays for the static path

- **What:** The scripted `LeadPolicy` stand-in is replaced by a real lead seat that drives the fleet through MCP tools. (a) New lead-facing wire ops `Op::Assign { ticket }` and `Op::FleetStatus`, plus `OpResult::Status { board }`; `Ticket`/`Budget` gain `PartialEq/Eq` so `Op` keeps its derives (as `Op::Report` already required of `Report`). (b) The hub gains an optional dispatcher (`mpsc::UnboundedSender<AssignCommand>`, via `Hub::with_dispatcher`): `assign` validates the slot, persists the ticket so `fleet_status` reflects it immediately, and forwards the command; a **static** hub (no dispatcher) answers a clean error rather than dropping it. `fleet_status` returns the board from `store.tickets()`. (c) New `run_dynamic_fleet` (runner): workers are spawned **on demand** as the lead calls `assign`, not from a fixed list up front (`run_fleet` is untouched). The lead seat is *external* — a `driver` future runs the session; when it returns, the runner stops accepting work, joins the spawned workers (the hub stays up so they can still report over the socket), and returns per-slot outcomes. The hub→runner bridge is a plain mpsc channel; each assign becomes a supervised worker on `spawn_blocking` — the same sync↔async seam as 4a (D-018), now fed dynamically. (d) The shim gains a **lead role** (`FLEETOR_ROLE=lead` → `Party::Lead`), a lead tool face (`assign`/`await_events`/`inbox`/`fleet_status`/`reply`/`send`), and renders `Events`/`Status` for the orchestrator to read. One binary, role via env — mirroring worker-slot-via-env.
- **Why:** This is the first time a real model (not a Rust script) can drive the fleet, and the point of "orchestrator-as-lead" is **dynamic assign** — the orchestrator *decides* to dispatch and it happens, which needs the hub→runner command seam a static fleet never had. Keeping `run_fleet` byte-for-byte preserves every 4a/4b/4c test (reversible; BUILDING §8). A `driver` future for the lead session covers both faces: a Rust test lead connects a `Client`; the future `fleetor run --real` path (deferred) spawns the real orchestrator process and awaits it — the process connects independently through the lead shim, so the runner code is identical either way. `fleet_status` + `await_events` give the orchestrator a supervise loop without reading transcripts.

## D-025 — Phase 4f: the lead can interrupt / restart a worker; the async→sync yank is a kill-by-pid over one `RunnerCommand` channel; a deliberate kill is `Interrupted`, not `Crashed`

- **What:** Two new lead ops, `Op::Interrupt { slot }` and `Op::WorkerRestart { slot }` (with matching shim lead tools `interrupt` / `worker_restart`), let the orchestrator yank a busy worker. The hub's single dispatcher channel is generalized from `AssignCommand` to a `RunnerCommand` enum (`Assign(AssignCommand)` / `Interrupt { slot }` / `Restart { slot }`); the hub routes control ops through the same slot-validated, dynamic-only path as `assign` (a static fleet answers a clean error). In the dynamic runner, each spawned worker now carries an `Arc<WorkerControl>` — a shared handle holding the worker's **pid** (published by `run_ticket` the instant `Session::spawn` returns) and an `interrupted` flag. `WorkerControl::kill()` sends `SIGKILL` to that pid (via `libc`, already in-tree); the worker's stdout stream then closes, the *sync* supervisor loop sees `Recv::Closed` and unwinds normally, and the runner **relabels** that worker's `Crashed` outcome to the new `Outcome::Interrupted` (only when it initiated the kill). `Restart` kills the live worker and re-dispatches its ticket through the same factory, producing a fresh worker in the slot. The command loop keeps a per-slot `HashMap<u8, (Arc<WorkerControl>, Ticket)>` (touched only by the one loop, so no lock).
- **Why:** This is the async↔sync interrupt D-021 explicitly deferred as "a real feature, not a stub" — the hard part is signalling a worker whose supervisor runs on a `spawn_blocking` thread with no async cancellation point. Killing by pid is the clean, reversible seam: it reuses the stream-close the supervisor *already* handles (no new state machine, no restructuring of `Session` ownership), and `libc::kill` needs no cross-runtime channel. Generalizing the existing dispatcher channel (rather than adding a second) keeps one ordered command stream lead→runner, so an `interrupt` can't overtake an in-flight `assign` for the same slot. Relabelling `Crashed`→`Interrupted` at the runner (not in the supervisor) keeps the sync loop untouched and honest: a stream-close the operator *caused* is not a crash, and the flag lives on each worker's own control so a later real crash on a reused slot is never mislabelled.
- **Deferred / not silent (BUILDING §9):** `worker_restart` is proven at the mapping + routing level (shim tool → `Op` → `RunnerCommand`, shared with the interrupt seam) but its full kill-then-respawn is not yet an end-to-end integration test (the two-worker timing is fiddly against fake-claude; the kill mechanism it depends on *is* proven end-to-end by the interrupt test). SIGKILL is a hard kill (no graceful drain / SIGTERM-then-wait); a worker mid-write leaves a partial worktree, which the git-branch isolation already contains. Windows is unaddressed (unix `kill(2)`), consistent with the rest of the unix-socket stack. `interrupt` cannot yet target the lead's own turn (it is the operator's TTY).
- **Verified:** `orchestrator::lead_interrupt_yanks_a_busy_worker` — a `hang` worker (consumes its assignment, never reports) is assigned, driven to in-progress, then `interrupt`ed; the run ends `Outcome::Interrupted` (not `TimedOut`/`Crashed`), proving the pid-kill reached the sync supervisor before the idle watchdog and that the deliberate close is relabelled. The shim lead-tool mapping tests gain `interrupt`/`worker_restart` (drift guard + "every listed lead tool is translatable"), and the cross-process bridge test is updated for the `RunnerCommand` channel. Full workspace suite green; `cargo check` on the shell (separate workspace, path dep on the changed server) passes. No live-CC spend — deterministic against fake-claude.
- **Reverses if:** a graceful interrupt is wanted (SIGTERM + grace window before SIGKILL, or a cooperative cancel token the supervisor polls) — `WorkerControl::kill` is the one place to change; or if the fleet ever needs Windows workers (swap `libc::kill` for a portable process-kill handle); or if per-slot ordering guarantees are relaxed and control commands want their own priority channel.

## D-026 — Phase 4g (D-015 reversal): the last two mail-delivery paths land — idle→stdin (supervisor) and opportunistic piggyback (shim); mail framing single-sourced in `fleetor-core`

- **What:** The two delivery paths deferred since D-015 (again at D-019, D-021) are now wired, closing the messaging model. **(a) Idle→stdin** — at a report-less turn boundary, `supervisor::drive_to_report` runs a bounded `idle_drain_step`: it flips the worker `Working→Idle`, briefly polls `store.take_mail(&Party::Worker(slot))` (10×50ms, honoring the wall-clock `deadline`, mirroring `grace_poll_mcp_report`), and if mail is queued writes it straight to stdin as a **fresh turn** via the existing `Session::send_user` — *not* counted against the no-report reprompt cap (a mail-driven turn is real work, bounded by `deadline`), then `Idle→Working`. Empty window → falls through to the unchanged reprompt/finish path. **(b) Opportunistic piggyback** — in the shim's `call_tool`, after any *worker* tool call, one `Op::DrainMail` folds pending mail into the rendered MCP result as an extra content block (`protocol::append_piggyback`); skips the `report` op (mail-after-report can prompt a redundant report — D-018 followup a) and the lead face (no mailbox). **(c) Framing single-sourced** — `frame_mail_for_injection` + `sender_label` moved from the shim's `protocol.rs` to `fleetor_core::mail`, so all three paths (Stop-hook drain, idle→stdin, piggyback) inject byte-identical D-014 coordination framing.
- **Why:** These paths finally have a live consumer — Phase 4d's `run_dynamic_fleet` + external lead can `send` steering at arbitrary times (D-019/D-021 deferred them precisely for want of that). **Idle→stdin is supervisor-side, not a new channel:** the supervisor already holds `Arc<dyn Store>` and reads it for `ReportFiled` (D-019's shared-log bridge), so it drains the same store directly — no cross-runtime plumbing. **Piggyback is shim-side, not hub-side:** `Client::call` returns only `OpResult` (a Response-level piggyback field would force Client + every-caller plumbing), and fake-claude speaks the raw socket *bypassing the shim*, so enriching the **MCP** result a real worker sees is inherently the shim's job. **Exactly-once holds across all three drains** because `Store::take_mail` is an atomic destructive SQLite drain: concurrent drainers serialize, each message goes out exactly one path, and the orderings are naturally disjoint (mid-turn → Stop hook / piggyback; after the turn's `result` — emitted only once the Stop hook declines to block — → the supervisor's idle drain, which therefore never races the hook for the same message).

## D-029 — Phase 4i: a persistent worker pool — 4 headless workers spawned idle at startup, messaged/broadcast by the orch; `session = ticket` relaxed to `session = worker`

- **What:** The shell now runs a **standing pool** instead of the dynamic assign-to-spawn fleet. A new `supervisor::run_standby_worker` spawns a worker session once and keeps it alive idle: it polls its mailbox, delivers each queued message to stdin (the D-015 idle→stdin path) and drives the resulting turn via `read_until_result` (so words + tools stream to the transcript, D-028), then returns to idle — it **never reports-and-dies**. A new `runner::run_pool_fleet` spawns N such standby workers up front on `spawn_blocking` (the D-018 sync↔async seam), wires the hub with a dispatcher so `interrupt`/`worker_restart` still act on a slot (assign-to-spawn is a no-op — the pool takes work as messages), runs the lead `driver`, then signals all workers to stop and drains. The Tauri app's `spawn_pool_fleet` builds 4 real workers from the existing `build_factory` and runs the pool, so `fleet_bootstrap` brings up **1 orch + 4 idle workers** with no assign. Added a **lead `broadcast`** (`Op::LeadBroadcast` → hub fans `enqueue_mail` from the lead to every slot → shim lead tool `broadcast`) so the orch messages all four at once.
- **Why:** The operator wants an interactive fleet — 4 available workers to message and watch — not a one-shot ticket runner. The key economy: the messaging + observability substrate already existed. D-015's idle→stdin *is* the delivery mechanism for a standing worker, and D-028's transcript events *are* how you watch it; so the only genuinely new code is the standby loop that keeps a worker alive (spawn once, idle-wait-for-mail) instead of `run_ticket`'s spawn→report→die. `run_ticket`/`run_fleet`/`run_dynamic_fleet` are **untouched**, so the quality loop and every existing test still pass; the pool is additive. An idle standby worker spends **no tokens**; each message is one turn. This relaxes `session = ticket` to `session = worker` for the pool only.
- **Verified (no real spend):** new fake-claude `standby` scenario (echoes each delivered message, stays alive) + `pool::pool_spawns_four_standby_workers_and_broadcast_reaches_all` — four standby workers spawn, a lead `broadcast` produces four `mail` events and lands in **all four** workers' transcripts (`worker-said` per slot), then drains. Lead-broadcast shim mapping added to the drift guards. Full crates suite green (23 test binaries, 0 warnings); `src-tauri` `cargo check` + `tsc/vite` clean. Live: real backend brings up 4 idle workers in the band; the orch `broadcast`s → all four receive → replies type back into the orch TUI (D-027).
- **Deferred (stated):** formal ticket/board dispatch to pool workers (pool is message-driven; the assign→spawn path stays for dynamic mode); auto-respawn of a crashed standby worker (stays dead, surfaced via `WorkerExited` in the Workers tab, until `worker_restart`); Claude-TUI-per-worker (a separate, larger pivot — this delivers "message & watch 4 workers" with headless workers + the transcript view).

## D-030 — The 5-TUI messaging pivot: MCP and the headless supervision model are deleted; all five agents become live `claude` TUIs

- **What:** A ground-up narrowing of the product to *messaging + visibility*. The MCP shim (`fleetor-shim`), the headless stream-json supervision model (`supervisor`/`quality`/`gate`/`runner`, `fleetor-cc`), and the whole ticket/board/report/review apparatus are deleted. In their place: **1 orchestrator + 4 worker `claude` TUIs**, each in its own pty owned by the Tauri app, each viewable in the shell (orch fixed left, workers tabbed right). Agents address each other through a small **`fleet` CLI invoked via Claude Code's built-in Bash tool** (`fleet send 2 "…"`), a plain socket client — no MCP, no JSON-RPC. The hub survives as a pure router; `fleetor-ipc` and the `BroadcastStore` event bus survive untouched. Plan: `docs/tui-pivot-plan.md`. Phase 0 findings: `docs/tui-spawn-notes.md`. Branch `feat/tui-fleet`.
- **Why:** Mapping the as-built system (`docs/fleet-comms-map.md`) showed two things. First, **messaging is the only part that works** — the shipped app runs `run_pool_fleet`, where `RunnerCommand::Assign(_) => {}`, so a lead's `assign` returns `Ack`, lands the ticket on the board as `Backlog`, and nothing ever runs or moves it; gate/review/report are unreachable from the app entirely. Second, and decisively, **the headless model is what forces the complexity**: mail has to be queued and drained at turn boundaries (three delivery paths, a Stop hook, an atomic `take_mail`) *only* because a `-p` process has no writable stdin between turns. Turn detection, report ingestion, transcript reconstruction and pid-interrupt all exist to compensate for not having a terminal. A live TUI has an always-writable stdin, so all of it becomes **unnecessary rather than merely unused** — delivery is just "write bytes to the target pty." Net ~3,500 lines out. This also reverses D-028's "tmux-TUI workers rejected" and D-029's deferred "Claude-TUI-per-worker" — that pivot is now the product, because the operator wants to *watch and steer* four agents, not run a one-shot ticket pipeline.
- **Consequences accepted:** No queue — a send to a dead pane fails loudly (nonzero exit + stderr) rather than buffering; the model self-corrects from its own Bash result. No blocking — `ask_lead`, the waiters, the ask timeout and `WorkerState::Blocked` all die. Message **bodies** move into the event log (`FleetEvent::Mail` carried metadata only, which is useless for a product about watching messages). `session = worker` (D-029) becomes permanent. Delivery is honest best-effort: the event field is `accepted`, never `delivered` — we queued bytes to a live pty and cannot know the model read them. Worker transcript reconstruction is abandoned outright (the TUI *is* the view); parsing redrawn ANSI to rebuild it is explicitly rejected.
- **Verified (Phase 0, real CC 2.1.220, no app code changed):** The onboarding wedge is **absolute, not intermittent** — a virgin `CLAUDE_CONFIG_DIR` never reaches a prompt, and the four worker config dirs on disk are in exactly that state. Bisected to a **two-key** minimum seed (`hasCompletedOnboarding` + `projects[cwd].hasTrustDialogAccepted`; `theme` unnecessary), with the sharp edge that **`hasTrustDialogAccepted` is keyed by absolute path**, so the target picker must re-seed every pane cwd. `ANTHROPIC_API_KEY` blocks the interactive TUI on api-key approval — only `ANTHROPIC_AUTH_TOKEN` may be set, though `apply_env` currently sets both. Bracketed paste + `\r` submits at 0/10/30 ms, multi-line included. `--permission-mode auto` is prompt-free for Bash/Read (ran the testbed suite, returned the right count) where the default `manual` would wedge. `tauri::ipc::Channel` was **rejected** for now: under its 1 KB threshold raw payloads serialize to a JSON integer array (~4× base64), so Phase 3 ships per-pane event names + base64 + 16 ms/64 KB coalescing instead. New finding: `CLAUDE_CODE_CHILD_SESSION` leaks through env inherit and silently disables transcript saving — add to `env_remove`.
- **Deferred (stated):** Phases 1–6 unstarted. `tauri::ipc::Channel` revisited in Phase 6 behind a measurement. Broadcast amplification is the highest-consequence *new* failure mode (five peers that can all broadcast and are all instructed to be helpful — the old system was immune only because headless workers had no volition between turns); three mitigations are required together, none yet built: a hub-side per-pane token bucket, an explicit "never reply to a broadcast unless it names you" brief clause, and a visible per-pane messages/min rate. An instant write into the orch pane can land mid-line if the operator is typing; accepted, with a "hold" toggle as the fix if it bites.

## D-031 — Phase 1: the pane contract lands additively alongside the headless one; delivery becomes request/response so the log can never claim a send that didn't happen

- **What:** The D-030 contract, built **beside** the old surface rather than on top of it, so the workspace stays green and all 85 pre-existing tests pass untouched. New in `fleetor-core`: `pane.rs` (`PaneId`/`PaneState`/`PaneEntry`, serialized as bare strings — `"orch"`, `"worker-2"` — so the CLI arg, DB payload, event field and TS type are one thing; `FromStr` accepts `orch`/`lead`/`2`/`w2`/`worker-2`), `message.rs` (`Message` carrying the **body**, plus the single-sourced `frame_for_pane` / `frame_broadcast_for_pane` injection framings), and `brief.rs` (`orch_brief`/`worker_brief` for `--append-system-prompt`). `event.rs` gains `Message { id, from, to, body, group, accepted, detail }` and `PaneState { pane, from, to }`. `wire.rs` gains `Hello.pane`, four pane ops and `OpResult::{Delivered, Roster}`. `hub.rs` gains `AppCommand`/`DeliveryResult`, `Hub::with_app`, the four handler arms, `last_inbound_from` and a per-pane token bucket. New `crates/fleetor-server/tests/pane_messaging.rs` (14 tests) drives the whole surface in-process against a fake app.
- **Why request/response at the app seam:** `RunnerCommand` is fire-and-forget because a runner's job is asynchronous. `fleet send 3` is not — it needs a real yes/no, and only the pty registry knows whether pane 3 is alive. So `AppCommand::Deliver` carries a `oneshot` ack, and the hub **awaits it before appending the event**. That ordering is the whole point: the feed records what happened, never an intention. Keeping the seam in the hub (rather than collapsing routing into `src-tauri`) is what preserves in-process, zero-spend testing — a test can answer a delivery exactly as a live pane, a dead pane, a missing app or a wedged app would, and then assert on the log. The 2s ack ceiling exists only so a wedged app cannot park the CLI forever; the round-trip is a HashMap lookup and a pty write, and nothing in the path sleeps.
- **Naming deviation from the plan (deliberate):** the plan says "add `Op::{Send, Broadcast, Reply}`", but `wire.rs` already has all three with different shapes (`Send { to: u8 }`, `Reply { event_id, .. }`), so adding them under those names is impossible while the old surface lives. They land as `PaneSend`/`PaneBroadcast`/`PaneReply`; **Phase 5 deletes the originals and renames these to the bare verbs.** Likewise `PaneConfig` is a separate struct rather than fields on `HubConfig`, because six existing test files construct `HubConfig` by literal and a new field would break every one; Phase 5 folds them together.
- **Bug the tests caught, at the contract layer:** `Response` `#[serde(flatten)]`s `OpResult` into the same JSON object as its own `id`, so `OpResult::Delivered { id, .. }` produced a **duplicate `id` key** and failed to deserialize — every delivery would have come back as a client error. Field renamed to `msg_id`, and `wire.rs` now has a round-trip test over every pane frame so the next variant cannot reintroduce it.
- **L5, and why the rate limiter was pulled back out:** a per-pane token bucket was built and then **removed on operator direction** — nothing may sit in the delivery path that can stop a message from landing while messaging itself is still unproven. It was a guard against a hypothesis (a broadcast fountain) whose only power is to refuse sends, with hand-picked defaults nobody had measured; the failure mode it prevents costs tokens, the failure mode it introduces is *the product not working*. Mitigation 2 — the "never reply to a broadcast unless it names you" brief clause — stays, and is the right layer for this: it is prompt text with zero code in the send path, so it cannot cause a message to be dropped. Mitigation 3 (a visible per-pane messages/min figure) is Phase 4 and is likewise observation, not enforcement. The direct and broadcast framings differ (`[fleet · worker-1]` vs `[fleet · worker-1 → all]`) precisely so a worker *can* obey clause 2. If amplification turns out to be real, it comes back in Phase 6 behind a measurement — and behind a demonstrated fountain, not a predicted one.
- **Other decisions made here:** `reply` resolves against `last_inbound_from`, updated **only on accepted deliveries** — you cannot reply to a pane that never heard you (tested). Pane identity comes from `Hello.pane` and a connection that never declared one is refused rather than guessed at; a misattributed message is unrecoverable. `PaneId::from_str` is permissive and does **not** validate slot existence — the hub holds the roster, so it is the hub that rejects `worker-9`. `roster` is answered by the app, not the config: "this pane should exist" and "this pane is alive" are different questions with different owners.
- **Verified (zero spend):** `cargo test --workspace` — 99 tests across 24 binaries, 0 failures, 0 warnings; `cargo check` clean in `src-tauri`. Nothing is wired: `src-tauri` still runs the old pool fleet, and no pane op is reachable from the app until Phase 2 unwires it and Phase 3 builds the registry.
- **Deferred (stated):** everything Phase 1 deliberately does not do — no pty registry, no `fleet` binary, no UI, and the briefs are unvalidated against a real Flash worker (Phase 6). Rate limiting entirely (see above). The one thing left in the delivery path that can refuse a send is the 2s ack ceiling, kept because it protects the caller rather than policing it: without it a wedged app parks the `fleet` CLI — and therefore the agent's Bash call — forever.

## D-032 — Delivery-path audit: only a dead pane may refuse a message, and membership has exactly one source of truth

- **What:** Two guards removed from the send path, both introduced in Phase 1 and both capable of silently refusing a healthy pane. (1) `PaneState` no longer gates delivery on `Live`. `is_live()` stays as a *display* predicate for the roster and band; the delivery path uses the new `accepts_input()` — `!Dead`. (2) `pane_send` no longer validates its target against `HubConfig.slots`, and `pane_broadcast` takes its targets from the app's roster rather than config. `roster_ids()` is gone; `app_roster()` is the single read of fleet membership.
- **Why (1):** nothing tells us when `claude` reaches its prompt. `Spawning` is a *guess about a running process*, so gating sends on `Live` means a perfectly healthy pane refuses every message until the guess flips — and if the flip is never implemented, or is implemented against a banner string that changes next `claude` release, the fleet goes mute while reporting exactly the error it was designed to report. That is L1's shape: it looks like it works and it doesn't. Writing into a still-booting pty is buffered by the kernel and read when the TUI starts reading; that is a failure we can live with, whereas refusing a live pane is not. The asymmetry decides it — a delivery gate should only fire on a fact (the process is gone), never on an inference.
- **Why (2):** `HubConfig.slots` and the pty registry were two answers to "who is in this fleet", and they can disagree — a pane the app is running would have been rejected as `unknown pane worker-4` with no way for the model to correct it, and a config entry never spawned would have looked reachable. The machine holding the ptys is the only one that knows, so it is now the only one asked. Config is not allowed to veto it (tested: a pane outside `SLOTS` is reachable if the app runs it). The self-send check stays, because it compares the sender to itself and cannot be wrong.
- **Verified:** `cargo test --workspace` — 98 tests, 24 binaries, 0 failures, 0 warnings; `cargo check` clean in `src-tauri`. New/changed tests: a spawning pane accepts while a dead one is rejected and logged; membership is the app's answer; a pane outside the hub config is still reachable.
- **Standing rule this establishes:** nothing may sit between `fleet send` and the pty that can refuse on an inference, a prediction, or a second copy of state. The remaining refusals in the path are the app saying a process is gone, the app being absent, and the 2s ack ceiling — which protects the caller (a wedged app would otherwise park the agent's Bash call forever) rather than policing it.

## D-033 — A message body can escape the bracketed paste that carries it; framing now sanitizes at the pty boundary

- **What:** `frame()` passes every body through `sanitize()` before it becomes bytes for a pty. CRLF and lone CR collapse to newlines; tabs and newlines survive; every other control character is dropped. `Message::body` keeps the raw text — sanitizing is a property of the pty boundary, not of the message, and the log should record what was actually sent.
- **Why:** delivery wraps the framed text in `\x1b[200~ … \x1b[201~` then `\r`, which makes the body *data* only for as long as it contains no escape of its own. A body carrying `\x1b[201~` ends the paste early and every byte after it arrives as **live keystrokes** at a `claude` prompt — where `\x1b` cancels and `/` opens a menu. That is L3 ("delivery is remote control of a text field, not messaging") in its sharpest form, and it is reachable by any pane that can compose a message, including a worker quoting terminal output it just read. A lone `\r` is the same bug in miniature: it submits the turn, splitting one message into two.
- **Why strip rather than reject:** consistent with D-032 — a mangled message that lands beats a clean one that doesn't. No legitimate body contains ESC, and the Phase-0-verified multi-line case (`\n`, tabs) is preserved exactly.
- **Verified:** `cargo test --workspace` — 102 tests, 24 binaries, 0 failures, 0 warnings. Tests: a hostile body cannot escape its paste through either framing; CR becomes a newline rather than submitting; newlines and tabs survive; the record keeps the raw body.
- **Two findings from the same audit left as Phase 3 requirements, not built:** (1) the `fleet` CLI has **no client-side timeout** — `fleetor_ipc::Client::call` waits forever, so a wedged hub parks the calling agent's Bash tool indefinitely; the hub's ack ceiling does not protect the caller. (2) Broadcast legs are awaited **sequentially**, so a receiver that blocks multiplies the ack ceiling by the number of targets. Both are recorded against `deliver.rs` in the plan. Neither is fixed here, because both fixes add concurrency to the delivery path and the path's simplicity is currently worth more than its worst case.

## D-034 - Delivery is unbounded: every timeout, ceiling and success-heuristic removed from the message path

- **What:** Operator direction after a two-agent audit of `crates/`, `src-tauri/` and `ui/`. The 2s ack ceiling is gone, and with it `PaneConfig` entirely - `Hub::with_app(store, config, app)` is back to three arguments, and `ask_app`/`app_roster` simply `rx.await`. Three live bugs the audit surfaced are fixed in the same pass. No timeout, rate limit, retry, backoff, queue, batch, idle guard or delay constant now exists anywhere between `fleet send` and the pty.
- **Why remove the ceiling:** it could not do the job it was there for. The `AppCommand` is already in an unbounded channel when the timer fires, so a timeout cannot *cancel* the delivery - it can only cause the hub to report failure for a message that then arrives. The `fleet` CLI exits non-zero, the model reads its own Bash stderr exactly as the brief teaches it to, and resends. Net effect of the guard: duplicate messages plus a log that says "rejected" about a message sitting in the recipient's terminal. Waiting forever is the honest failure mode, and it is diagnosable - a hung `fleet` is visible; a phantom rejection is not.
- **Live bugs fixed in the same pass:**
  - **A broadcast leg hijacked the recipient's reply target.** `log_message` set `last_inbound_from[to] = from` on every accepted delivery including fan-out legs, so a worker mid-conversation with the orch had its reply target silently repointed by whoever broadcast last - and `fleet reply` is what the worker brief calls its usual move. This was the only path where a message could arrive somewhere it was never meant to go. Broadcast legs no longer register a reply target; a fan-out is not a conversation.
  - **A broadcast reported success if *any* leg landed.** `accepted` drove the CLI's exit code, and the brief has taught the model that a zero exit means the bytes reached a terminal - so a fan-out that missed three of four panes read as a complete one, with the failures buried in a `detail` that a zero-exit path never prints. `accepted` now means every leg landed.
  - **A poisoned mutex ended messaging for the process.** One panic while holding `last_inbound_from`, `waiters`, `lead_events` or the SQLite connection would make every subsequent delivery panic its connection task forever, surfacing only as "server closed the connection". All `.lock().unwrap()` in `hub.rs` and `fleetor-db` are now `.unwrap_or_else(|e| e.into_inner())`.
- **Audited and found clean (stated so it is not re-audited):** no rate limits, token buckets, quotas or caps remain on the pane path; no retries, backoff or circuit breakers; no sleeps, intervals, debounce, coalescing, idle guards or parking; no size limits or clipping of bodies; no bounded channels on the delivery path; no locks held across an await. Everything the sweep found in `supervisor.rs`/`quality.rs`/`runner.rs`/`gate.rs`/the shim belongs to the headless surface deleted in Phase 5 and is unreachable from any `Pane*` op.
- **Kept, with reasons:** `sanitize()` (D-033 - it stops a body escaping its own bracketed paste and becoming keystrokes, and it alters rather than refuses); the self-send guard (compares the sender to itself, cannot be wrong); the `Hello.pane` requirement (there is no other identity source, and it fails loudly per call); `emit` swallowing a store error (a log failure must never fail a delivery).
- **Known and accepted, not fixed:** the SQLite `append_event` is a blocking write on the response path behind one global connection mutex - consistent with the now-unbounded posture, and moving it off-path risks reordering the message log. Broadcast legs are still awaited sequentially. `last_inbound_from` is in-memory, so a hub restart silently breaks `fleet reply` until each pane is addressed again. A malformed frame tears down the connection rather than being answered - loud to the sender, so not silent. Each is recorded rather than pre-emptively engineered: the priority is proving the mechanism works end to end.
- **Verified:** `cargo test --workspace` - 104 tests, 24 binaries, 0 failures, 0 warnings; `cargo check` clean in `src-tauri`. New regression tests: a broadcast does not hijack a reply target; a broadcast alone gives its recipients nobody to reply to; a partial fan-out is not accepted.

## D-035 — Phase 2: the headless fleet is unwired from the app, and the socket half of messaging is proven

- **What:** `src-tauri` no longer runs a fleet. `spawn_pool_fleet`, `build_factory`, `WorkerBackend`, `FakeWithEnv`, `resolve_backend`, `fake_script_path` and `shim_path` are gone, along with the four headless standby workers they produced; the `fleetor-cc` dependency goes with them. What replaces all of it is one line of intent — `Hub::with_app(store, HubConfig::default(), app_tx).run(transport)` — plus the pane seam the hub talks to. The store, the live bus and the follower→webview pump are untouched, which is why the feed still streams. `fleet.rs` went 689 → ~430 lines.
- **The target replaces the scratch repo.** `~/.fleetor/config.json`'s `target` names the repo the fleet works on; absent or unusable, it falls back to a seeded testbed at `~/.fleetor/testbed/` with a `Notice` on the feed. A config that names *nothing* is the ordinary first-run case (Info); a config that names something broken is a Warn that quotes the problem, because reading a typo'd path as "no target configured" would put the fleet in the testbed while the operator believes it is in their own repo.
- **The seed is embedded, not copied.** `include_str!` over `testbed-seed/`, ~9KB in the binary. A path ladder — repo-relative under `tauri dev`, a resource in a bundle — is L4's exact shape: it works in dev and silently resolves to nothing in a bundle, leaving the fleet an empty directory to "work on". Seeding never overwrites an existing file (after the first run this directory holds the fleet's real work) and makes an initial commit, because `git worktree add` needs one and Phase 3 gives every worker pane a worktree.
- **The MCP wiring left `pty.rs` here rather than in Phase 3.** `shim_path()` dies in this phase and `pty.rs` called it, but the deeper reason is that `mcp__fleet__assign / await_events / reply` now point at a hub that spawns nothing. A tool surface that silently cannot work is worse than no tool surface — the orchestrator would call `assign`, receive an `Ack`, and wait. `FLEET_SOCKET` stays: Phase 3's `fleet` CLI reads it.
- **The lead inbox pump and its consumer are deleted together.** `spawn_lead_inbox_pump` long-polled a queue only headless workers ever wrote to. Its consumer — the `lead://inject` queue in `TerminalPane.tsx`, with the 1500ms operator-idle guard and the 400ms one-message-per-tick flusher the D-034 sweep found — went with it. Leaving dead code that implements precisely the pattern this pivot bans is a trap, not a harmless leftover: the obvious next move is to re-point it at message events, and both delays come back with it.
- **The pane seam answers, it does not park.** Until Phase 3's `deliver.rs` exists, `spawn_pane_seam` refuses every `Deliver` with "no panes are running yet" and answers `Roster` with an empty list. It must answer *something* for every command: the hub awaits the ack with no deadline (D-034), so a command received and left unanswered parks the caller's `fleet send` forever. That is the failure mode the unbounded design accepts in exchange for never lying about a delivery, and it is not one to hand out for free.
- **The socket half is now proven.** `a_pane_op_crosses_the_real_socket_and_is_answered` binds the hub on a temp socket, dials it with a real `Client` the way the `fleet` CLI will, sends `Op::PaneSend`, and asserts both the refusal it gets back and the event on the feed carrying the body. Everything before this was in-process against a fake app. `spawn_hub` takes the socket path as a parameter rather than reading `socket_path()` precisely so this is reachable without a window.
- **Deviation, stated:** `tauri-plugin-dialog` was not added. An unregistered plugin dependency does nothing but slow builds and read as wired to anyone reviewing; it lands with the picker that uses it.
- **One user-facing lie fixed on the way past:** the spend gate read `worker_backend` and rendered anything that was not `"flash"` as "fake (free proof path)". With the backends gone the field is `"none"`, so the gate would have promised a free worker path that no longer exists — on the one screen whose entire job is telling the operator what a click will cost.
- **Verified:** `cargo check` clean in both workspaces, no warnings; 9 shell tests + 104 workspace tests, 0 failures; `tsc --noEmit` clean. Not verified: the app launching as a window, which needs a GUI session.

## D-036 — Phase 3: the pane registry and the `fleet` CLI

- **The two halves landed together**, because neither is demonstrable alone. `crates/fleetor-cli` became the `fleet` binary — five verbs over the unix socket, no MCP server — and `src-tauri/src/pty.rs` became a `PaneRegistry` of N ptys keyed by `PaneId`.
- **Per-pane event channels** (`pty://output/2`, `pty://exit/2`) are a correctness boundary before a performance one: pane 2's component *cannot* receive pane 1's bytes if it never listens on that name. The perf win (L6 chokepoint #2 — `AppHandle::emit` wakes every listener on a name, so a shared channel means 5× the JS wakeups for zero benefit) comes free with it.
- **The read pump is two threads, not one.** A single thread can only check its coalescing window *after* the next blocking `read` returns, so the tail of a burst would sit unflushed until the pane happened to print again — the last line of a finished turn, invisible for as long as the pane stays quiet. The coalescer's `recv_timeout` has no such blind spot.
- **One write, one lock.** Paste-open, body, paste-close, 30 ms, `\r` — all under a single hold of that pane's writer mutex. Tauri dispatches sync commands on a thread pool, so a keystroke racing a delivery could otherwise land between a message's body and its submit. The lock is per-pane, so the 30 ms costs that pane's keystrokes and nobody else's.
- **The delivery loop never blocks.** Each `Deliver` goes to `spawn_blocking`. Inline, five panes would serialize behind each other, and the hub awaits broadcast legs one at a time — so a slow pane's cost multiplies by the roster.
- **The L1 re-seed requirement is met structurally.** `seed_config_dir` is called at the spawn site, next to the cwd it is keyed by, rather than at the target picker. `hasTrustDialogAccepted` is keyed by absolute project path, so it can now be got wrong by deleting a line but not by forgetting a code path.
- **`fleet_bin_path` is an explicit ladder with an existence check at every rung**, and a `Notice` when it comes up empty. The shim it replaces resolved its binary through a hand-made untracked symlink, behind a doc comment claiming cargo put it there — it did not; these are two cargo workspaces with two target dirs (L4).
- **`kill_all` signals the process group.** `openpty` gives each pane its own session, so killing the pid alone can leave a `claude`'s children running with no terminal and nobody watching. For an Opus session that is a bill that keeps growing after the window closes.
- **Deviations:** no `pending`/`last_input_at` on `Pane` — nothing reads them, and they exist in the plan only to support the idle guard and flush ticker D-034 bans; dead state whose only purpose is a banned pattern is the same trap as the `lead://inject` queue Phase 2 deleted. `src-tauri` became a lib plus a one-line bin, because a bin-only crate cannot expose `PaneRegistry` to an integration test and a registry only exercisable through a GUI is a registry nothing tests. - **Verified:** `tests/fake-pane/fake-pane.sh` plus a `FLEETOR_PANE_CMD` override gives six zero-token tests over five real ptys — channel isolation both ways, a message landing in its target and nowhere else, keystrokes and deliveries sharing a writer, a dead pane refusing by name, a killed pane respawning, `kill_all` reaping the fleet. Deliberately *not* covered: whether a live `claude` reaches its prompt. That is L1/L2, settled by measurement in Phase 0, and a fake pane would answer it wrong in the reassuring direction.

## D-037 — Phase 4: the shell becomes five terminals and a message record

## D-039 — concurrent messages to one pane: a serial writer that drains

- **The trigger was observed, not predicted.** With the fleet running, several workers messaging the orchestrator at once "glossed over" some of them. Two separate causes, one of them ours.
- **Ours: ordering.** Every `Deliver` got its own `spawn_blocking` task, and those raced for the pane's writer lock in whatever order the blocking pool scheduled them. Nothing was dropped — the mutex and the kernel buffer see to that — but a pane could see messages in an order the log disagreed with. That is a defect, not a tradeoff.
- **Not ours: the merge.** A `claude` input box is one text field. Message A submits and starts a turn; B's paste lands mid-turn and is queued by CC; C lands on the same buffer. What the model reads is a blend of the three. We cannot reach inside the TUI.
- **One writer task per pane, draining.** When the writer is free it takes *everything* currently queued for that pane (`try_recv`, never `recv`) and sends it as one bracketed paste, each message still framed with its sender and separated by a blank line. Ordering becomes the hub's order by construction, and the merging the TUI was doing invisibly and badly is now ours, done where the framing still says who sent what.
- **This is not the batching the pivot bans.** That was an idle guard plus a flush ticker that could withhold a message indefinitely while the operator typed. This adds **zero** delay to a message arriving at a free pane — nothing ever waits for more to accumulate. It groups only messages that were already concurrent, which is exactly the set the TUI was going to merge anyway. Every message keeps its own log row, its own `accepted`, and its own ack: batching groups the write, never the accounting.
- **What it does not fix, stated plainly.** A pane thirty seconds into a turn still receives messages into CC's own queue, at CC's mercy. Nothing on this side of the pty can change that, and it is the reason `accepted` has never meant "delivered" (L3).
- **Verified:** `a_burst_from_four_peers_arrives_whole_in_order_and_in_fewer_writes` fires four concurrent deliveries at one real pty, asserts all four are answered and accepted, that the pane saw them in the hub's order, and that they reached it as **fewer bracketed pastes than there were messages** — the property that would silently regress if the drain ever became a per-message write again. Deterministic rather than lucky: the 30 ms submit gap guarantees messages 2–4 are queued while 1 is in flight.

## D-041 — startup orphan sweep: the teardown that runs when teardown can't

- **The problem was structural, not a bug.** Close-time teardown (`on_window_event` + `RunEvent::Exit`, both calling `pty::kill_all`) only runs if the process gets a chance to — Force Quit, `kill -9`, and a crash all skip it, and a leaked `claude` with no terminal and nobody watching is a bill that keeps growing. That same risk was already on `building.md`'s table with "Startup sweep" listed as the planned fallback; this implements it.
- **Two gaps closed at once.** (1) On macOS, `Cmd+Q` and Dock → Quit bypass `WindowEvent::CloseRequested` entirely — a documented, currently-open Tauri bug (tauri-apps/tauri#9198, #13778). Without `RunEvent::Exit` as a backstop, quitting the app any way other than clicking the close button leaked every pane. (2) Even with both close hooks, a crash or Force Quit still skips them by definition. The startup sweep catches that.
- **`src-tauri/src/orphans.rs` (new).** Every `PaneRegistry` spawn/kill/kill_all durably writes the current set of live pane pids to `~/.fleetor/_shell/panes.pids`. At next launch, before spawning anything new, `orphans::sweep()` reads that file, verifies each pid is still alive **and** still actually a process named `claude` (via `ps -o comm=`), then `killpg`s it. The identity check guards against pid recycling — a stale pid could since have been reassigned to an unrelated process.
- **The registry path is now explicit in `PaneRegistry::new`.** Deliberate refactor: tests were writing into the operator's real `~/.fleetor/_shell/` on every run. Now every test builds its own registry around a scratch path, and `kill_all` clearing the registry is verified by reading the on-disk file back (`spawn_kill_and_kill_all_keep_the_pid_registry_in_sync_with_reality`).
- **One gotcha survived the spike and is documented.** A pane that exits *naturally* (the pty EOFs, pump thread notices) does not trigger a registry rewrite — only explicit mutations do. Harmless: the sweep's liveness+identity check already treats "gone" as a no-op, so a stale entry costs nothing on the next launch. A comment on `record_live_pids` explains why that's fine rather than a bug.
- **Testing the `killpg` itself required real processes, not mocks.** A copied binary loses its code signature on macOS and behaves unpredictably, so the test can't just `cp /bin/sleep ./claude`. Instead, `reap_if_named` (and now `sweep_at_named`) take the expected name as a parameter, so the tests exercise the real mechanism against `/bin/sleep` directly. One test that polled `kill(pid, 0)` to check death was fooled by zombies — switched to `try_wait` since we're the parent in that test.
- **Verified:** 45 tests total (36 lib + 9 integration), all green. Coverage of the new module: registry round-trips, sweep on absent file, sweep on empty file, sweep with a dead pid, sweep with a live non-matching pid, sweep with multiple live matching pids, `write_registry` failing closed when its parent can't be created, the `killpg` mechanism itself against a real process, and the full `spawn`/`kill`/`kill_all` wiring keeping the on-disk registry in sync with reality.

## D-042 — the briefs stop being Rust and become `prompts/*.md`

- **The default that lost was "brief text is a `format!` literal in `fleetor-core`."** It was a fine default while the briefs were two paragraphs nobody was arguing about. It stopped being one the moment the briefs became the thing most likely to need iterating: `decisions.md` D-031 records that they are **unvalidated against a live Flash worker**, and the fix for a misbehaving worker is almost always a sentence, not a function. Putting the one part of this system that most wants a fast loop behind a Rust rebuild was backwards.
- **What changed.** `prompts/` at the repo root now holds the prose — `orch.md`, `worker.md`, and two fragments, `delivery-contract.md` and `broadcast-rule.md` — plus `launch.conf` for the worker's model, endpoint and permission mode. `brief.rs` keeps them with `include_str!` and becomes a renderer (`render_orch` / `render_worker` / `render`) and a validator (`validate_orch` / `validate_worker`). `src-tauri/src/prompts.rs` adds `PaneContext::resolve`, which reads the operator's own copies from `~/.fleetor/prompts/`.
- **Baked in *and* on disk, not one or the other.** `include_str!` means the binary always has a working brief, the tests still pin what ships, and there is no runtime path where a missing file produces an unbriefed pane. The disk copy is an override, never the source of truth.
- **The mechanism moved; not one byte of prose did.** All five rendered briefs are identical to what the `format!` literals emitted, `--append-system-prompt` is unchanged, and `launch.conf` carries the old `DEEPSEEK_BASE_URL` / `MODEL_FLASH` / `auto` constants verbatim. That was the point: a change of substrate and a change of content are two arguments, and reviewing them together means reviewing neither. What a pane is *told* is the next argument.
- **Two clauses are composed in, not written out — and a template that dropped one is refused.** `{delivery_contract}` is the only reason a model can tell a failed send from a good one (L3: `accepted` is not `delivered`, and the model's own exit code is the only correction available). `{broadcast_rule}` is the only mitigation left for broadcast amplification, because D-031 removed the rate limiter and Tier 1.4 forbids putting it back. So the operator may rewrite every word around them and cannot lose them. Validation also refuses a rendered brief that has stopped teaching a `fleet` verb — same failure `VERBS` exists to catch, now reachable by editing a file.
- **Every override outcome is announced.** Loaded → `Info` naming the file. Refused → `Warn` quoting the validator's complaint and saying the built-in is running instead. Absent → silence, the ordinary first run. A prompt change that quietly did nothing is indistinguishable from one that did not work, and the operator would then be reading a live fleet's behaviour against a brief it is not running. Same reason an unrecognised `launch.conf` key is a warning rather than a skip: a typo'd `permission_mode` reads exactly like a working config until a pane wedges on its first tool call.
- **Resolved once at bootstrap, not per spawn.** A fleet whose panes were briefed from two revisions of a file the operator was editing is not a fleet anyone can reason about. Edits take effect next launch — the same rule `fleet_pick_target` already follows, and a system prompt cannot be changed after `exec` anyway.
- **`fleetor-core` still does no I/O.** The app reads files and hands templates in as arguments; core renders and validates. And the briefs still go in as a system prompt, never as a `CLAUDE.md` in a pane's cwd (Tier 1.1) — `src-tauri/tests/panes.rs` still pins that.
- **What would reverse it.** Evidence that the file rung is a hazard rather than a help: an operator override that gets a pane into a state validation cannot describe, or a `~/.fleetor/prompts/` copy silently going stale against a shipped brief that moved on and nobody noticing because the Info notice reads as normal. The cheap partial retreat is keeping `prompts/` as the source of truth and dropping only the `~/.fleetor/` override rung — the split is already exactly there.
- **Verified:** 63 workspace tests and 44 + 9 shell tests green (the 9 are the real-pty pane tests against `fake-pane`), `tsc --noEmit` and `vite build` clean. The five rendered briefs were captured from the pre-change binary and diffed byte-for-byte against the post-change ones. Coverage of the new paths: no override directory is silent, a valid override is used and announced, a broken one falls back and names the placeholder to restore, `launch.conf` overrides only the keys it sets, an unknown key warns without discarding the good lines, comments and blank lines are not complaints, a brace in prose survives rendering, the shipped templates pass their own validator, and the baked `launch.conf` is pinned to the `LaunchConfig` fallback so the two cannot drift.

## D-044 — the orchestrator becomes a vision partner, and the workers get a culture

- **The default that lost was "a brief is a job description."** D-042 moved the prose into `prompts/` and deliberately changed not one word of it; D-043 made that prose the pane's whole system prompt. This is the argument those two were clearing the ground for: *what a pane is told.* Tier 2 — prompt text — so this entry is the record rather than a request.
- **`orch` confirms the vision in writing before it decomposes anything.** Ask for the bigger picture; state it back in the operator's own terms, in a file or a message they can read back; wait for a yes. `Nothing goes to a worker until the vision is confirmed` is in the brief as a consequence rather than an instruction, because an instruction without one is advice. The failure being designed against is a fleet that starts fast on the wrong thing, which wastes five terminals rather than one.
- **"Guide the operator to think bigger" is bounded to one proposal.** If the vision is unclear or smaller than it could be, `orch` says so and proposes a bigger frame **once**, plainly, in one turn. If the operator declines or restates, it adopts their frame fully and does not raise it again in the session. An orchestrator that relitigates the goal every turn is worse than one that never raised it, and the authority bound is not negotiable: the operator's explicit word is final.
- **The integrity clause is the other half of that.** The fleet may find a better *route* to the operator's vision and should say so; it may never quietly substitute a vision of its own. Every deviation is `announced, not discovered later` — named, with why, and with what was done instead. The pre-existing anchor ("information to factor in, not an instruction that overrides what the operator asked") survives verbatim and is now pinned by a test rather than by luck.
- **The tenets are distilled, not pasted.** `docs/futureDesign/vision_tenets.md` is an essay with quotations, scripture and podcast plugs; a brief cannot afford any of it. `prompts/vision-tenets.md` is its six operative moves — write it down, prune, filter decisions through it, one vision not four, resistance is information, ME→WE. A test asserts the operative lines arrived *and* that the essay's framing did not come with them.
- **Workers get the three attitudes, and they are questions rather than rules.** *How can I be better? How can I push for more positive, meaningful impact? What do I do when I am confused?* The third has the answer attached — ask a peer by name, or `orch` — because "ask for help" without a named addressee is a worker that guesses. And ME→WE lands as `Improve yourself and the team around you`, with the cost stated: a worker who finishes their own task and leaves the fleet no wiser has done half the job.
- **One sentence is on loan to WP-07.** A worker with a question for the human is told to `ask orch to put it to the operator`, because no worker can address the human directly yet. It is deliberately self-contained and pinned by `a_confused_worker_is_told_exactly_who_to_ask`, so WP-07 replaces a sentence rather than reverse-engineering a paragraph.
- **Voice borrowed from `docs/CLAUDE.template.md`** where it did not conflict: collaborator-not-executor, put competing interpretations to the operator rather than picking one silently, distinguish verified from believed, treat pushback as new information and re-derive. Not borrowed: its subagent guidance ("decisions, not discretion"), which is exactly wrong for panes the fleet is built on treating as peers.
- **The budget, measured (WP-09 baseline).** Rendered orch **1,637 tokens**, worker **1,115** (DeepSeek Flash tokenizer, `examples/system-prompt-spike/count.py`). The progression across this package: 487/506 before WP-02 → 878/868 after the parity switch → 1,637/1,115 now. Against the **1,485 tokens** of CC guidance that stopped being sent, orch starts a session ~335 tokens lighter than before and a worker ~876 lighter. Four packages still queue behind this budget; WP-09 audits the sum.
- **What would reverse it.** Live evidence from a Flash worker — D-031 still records that these briefs are unvalidated against one, and WP-09's live shakedown is where that gets settled. The likeliest failures are named: an orchestrator that stalls on vision confirmation when the operator wanted one small thing done, or workers whose "push for more impact" reads as licence to widen their own scope. Both are prose fixes in `prompts/`, and both would show up as behaviour before they showed up as a bug.
- **Verified:** 71 workspace tests and 53 shell tests green, `tsc --noEmit` and `vite build` clean. Six new pinned-literal tests join the anti-amplification one: confirm-the-vision-before-decomposing, propose-bigger-once, the integrity clause with its surviving anchor, the three attitudes with ME→WE, the ask-orch routing, and the tenets-distilled-not-quoted check. Both fragments are asserted *absent* from the templates, so an operator rewriting prose cannot inline and then lose them.

## D-045 — `fleet cmd`: a command channel that is not the message path

- **The default that lost was "the router chops the prefix off for slash commands."** That framing describes a content-inspecting transform *inside* the delivery path — the shape Tier 1.4 has rejected twice. This lands the capability the other way round: a separate verb, a separate `Op::Cmd`, a separate `AppCommand::Command`, a separate hub arm and a body that was never framed. **Commands are not messages; nothing is chopped.** `Message::framed`, `sanitize`, `write_paste` and `Op::Send`/`Broadcast`/`Reply` are byte-identical — verified as an empty `git diff` on `crates/fleetor-core/src/message.rs` and `src-tauri/src/pty.rs`, plus a grep over `hub.rs` and `wire.rs` showing no line of the message arms changed.
- **`fleet cmd <pane|self> "<command>" --why "<reason>"`.** `--why` is `required` in clap, not documented-and-hoped-for: it is a contract on the sender, enforced before anything enters the path, the same class as `Hello.pane`. The why is the reason the verb exists as much as the command is — the log of *when and why* the fleet decided to clear or compact is the reasoning chain a later self-improvement pass reads. An optional one would be skipped.
- **The allowlist is `["/clear", "/compact"]`, matched on the command word** (Tier 2, in `command.rs`). Arguments pass, so `/compact keep the parser` is one command and `/compactify` is not one at all. Refusal happens **only at accept time**, against that constant, with a sentence for the sender's stderr — the same refusal class as the self-send guard, which D-034 explicitly keeps. Nothing is written and nothing is logged when a command is refused; after acceptance nothing delays, drops or alters it.
- **Control characters are refused, not stripped** — the one place this diverges from `message::sanitize`, deliberately. A mangled message that lands beats a clean one that doesn't; a mangled *command* is a different command. It also keeps `sanitize` untouched, which the empty-diff criterion required.
- **Self-targeting is allowed for `cmd` and only for `cmd`.** `fleet cmd self "/compact …"` is the ordinary use — a worker pruning its own context between task blocks. The message self-send guard at `hub.rs` and its pinning test are byte-identical, and one test now asserts both facts together so the two can never quietly converge.
- **The spike overruled the plan on the delivery mechanism.** WP-03's doc specified raw unpasted bytes, on the theory that a bracketed paste makes `/` literal. Measured against CC 2.1.223 (`docs/command-channel-notes.md`, six live runs): **typed** commands fire the wrong menu entry; a **bracketed paste** filters and selects correctly. So the command path is a new *caller* of `write_paste` with an unframed body, and the 30 ms `SUBMIT_GAP` needed no change — the plan's "does the menu need a longer gap" question answered itself as no.
- **A command is never joined into a message batch.** The per-pane serial writer drains concurrent messages and joins them with a blank line (D-039); a command inside such a join would not have its `/` in column 0. So `spawn_writer` splits a drained batch into *runs* — consecutive messages join exactly as before, byte for byte, and every command is a write of its own. Same queue, same writer task, so a command still cannot interleave with an in-flight paste.
- **`FleetEvent::Command { from, to, command, why, accepted, detail }`,** rendered as its own card in the Messages record and its own gold line in Activity. Not a `Notice` (which would bury the reasoning chain) and not a marked `Message` (which would put words in a pane's mouth). The UI says `accepted — the bytes reached the terminal` and never that the command ran.
- **Two measured failure modes are accepted rather than engineered around.** A command landing on a non-empty input box is concatenated and submitted as prose; a command landing mid-turn is queued by CC and executes when the turn ends. Both are invisible from this side, which is exactly why `accepted` has never meant "executed" (Tier 1.5). A line-kill prefix would fix the first and was **not** taken: on `orch` it silently destroys what the operator was typing, and that trade is not a builder's to make. Recorded in the notes with its cost attached.
- **No automation, and none is coming from here.** No "compact at 80%" daemon, no system-triggered commands. An agent decides and owns the why; auto-anything here is the deleted supervisor growing back.
- **What would reverse it.** A CC release that changes how a pasted slash command is parsed — the menu-ranking of a bare `/clear`, the concatenation behaviour, or the mid-turn queueing. `docs/command-channel-notes.md` is version-stamped against 2.1.223 and names those three as the claims most likely to move. Also: a live shakedown showing the concatenation happening often enough to be worth the line-kill trade.
- **Cost, measured — over budget, and said out loud.** The rendered orch brief goes 1,637 → **1,885** tokens and the worker 1,115 → **1,343** (DeepSeek Flash tokenizer, `examples/system-prompt-spike/count.py`): **+248 and +228**, against WP-03's budgeted ~120 *across both*. Roughly four times the estimate. Where it went: each brief needs the verb line, what the two commands do, the allowlist boundary, and the rule that makes the verb worth having — the worker's "between tasks, never mid-task" timing bound, the orchestrator's "re-brief a worker you cleared" with its consequence. Every one of those is pinned by a test because shortening it turns it into advice. The honest options were "spend it" or "ship a verb nobody uses correctly"; this took the first. WP-09 audits the sum and is now carrying a visible overrun rather than a hidden one.
- **Verified:** 93 workspace tests and 59 shell tests green, `tsc --noEmit` and `vite build` clean. New pins: the unframed keystrokes against a real fake-pane pty in a burst with two messages (the command alone, in arrival order); the allowlist refusal reaching no pty and writing no event; self-command accepted while the message self-send is still refused in the same test; a command never becoming a reply target; and the run split asserting that a messages-only batch still produces `join`'s exact bytes.

## D-047 — WP-05: the task board is a fold over the event log, and the one arm that never reaches a terminal

- **The default that lost was "a board of work needs somewhere to live."** It does not: `fleet task list` is `task::board(store.events_since(0))`, a fold over the same log the message feed replays. No `tasks` table, no cached copy in the hub, no second source of truth — two hubs over one store compute the same board, pinned by `a_restarted_hub_replays_the_same_board_from_the_log_alone`. The vestigial `tickets` table migration 0003 dropped stays dropped; this package adds no migration at all, because a new `FleetEvent` variant is already a `kind` and a `payload` in the one table there is.
- **`fleet task post|update|list` — one verb, three subcommands, one wire op.** The requirements spend the verb budget once, so `VERBS` gains exactly `task`, the clap tree nests underneath it, and `Op::Task { action: TaskAction }` keeps the pinned "wire tag *is* the CLI verb" test true. Flat flags throughout (`--outcome`, repeatable `--crit-t` / `--crit-s`, `--to`, `--instructions`, `--parent`, `--converges-on`): a weak model emits flat flags far more reliably than JSON, and a malformed nested document costs a whole turn to diagnose from a parser error.
- **The schema is the vision's shape verbatim.** `TaskBlock { outcome, technical[], semantic[], worker, instructions?, parent?, converges_on? }` — what this execution enables, how anyone could check it, which part of the confirmed vision it serves, whose it is, and where it sits among the streams. The block carries no id of its own: the id lives on the `FleetEvent::Task { task, from, at, change }` that posted it, so a post and every later update join on one field rather than two spellings that could disagree. `at` is on the payload rather than only the DB row because the board is replayed in two places and only one of them ever sees a row.
- **`--to`, `--crit-t` and `--crit-s` are `required` in clap** — the same contract-on-the-sender argument that made `fleet cmd --why` required (D-045), and for a sharper reason here. An unassigned block sitting on a board is a *backlog item*, and a backlog item is a thing something eventually picks up: that is the ticket system's first move. Requiring the owner at post time means every block is a decomposition already decided rather than a queue. A block with no checkable criterion is a wish, and the whole point of the shape is that a claim of `done` can be argued with.
- **Status is descriptive and no transition is enforced.** `planned|claimed|done|dropped`, and `done → claimed → planned` is legal, tested twice (unit and over the socket). A worker who marked a block done and then found a failing criterion has to be able to say so; a board that argued would only teach the fleet to stop updating it. `done` is an **unverified claim** — WP-06's receipts and review are what turn one into a fact, and nothing in the CLI or the UI renders it as anything else.
- **Anyone may update any block.** No ownership check: the event's `from` is the whole of the accountability, and a peer who spots that a block marked `done` has a failing criterion must be able to say so on the same record. That is what makes WP-06's review possible without a permission system.
- **The one refusal that is not a gate.** An update naming a block that is not on the board is refused with `no task "…" is on the board — 'fleet task list' shows the ids`, and nothing is written. This is referential validation, the same class as "no pane worker-9 is running" — it constrains nothing about *which* status may follow which, only that a claim has something to be a claim about. Without it a typo'd id vanishes into the log unread. Recorded here rather than absorbed, because it is the only place in this package where anything reads task state before doing something.
- **The tripwire list held; nothing on it was built.** No gate, no supervisor or poller, no auto-routing or load-balancing, no blocking claim, no per-task worktrees, no `Assign`-like op. Cycles in the parent links are tolerated — the replay never walks them, and `fleet task list` renders flat with a note when it finds one. A dangling parent id renders as a root. Validating the links into a legal graph is the workflow engine this is deliberately not.
- **The delivery path's diff is empty, and this time the whole crate that owns it is.** `crates/fleetor-core/src/message.rs`, `crates/fleetor-core/src/command.rs`, `src-tauri/src/deliver.rs`, `src-tauri/src/pty.rs`, `crates/fleetor-server/tests/pane_messaging.rs` and `src-tauri/tests/panes.rs` have **zero** `git diff`. `hub.rs` grew a `task` arm and its dispatch line; no line of `send`/`broadcast`/`reply`/`deliver`/`log_message`/`ask_app`/`last_inbound` changed (checked as a grep over the diff). `src-tauri`'s only change is one test fixture's verb list in `prompts.rs`. `task.rs` copies eight lines of control-character filtering rather than reusing `message::sanitize`, on purpose: same idea, different boundary (a terminal *printing* `fleet task list` vs the pty delivery path), and sharing it would have meant touching the file whose diff had to stay empty.
- **`Hub::task` is not `async` and never touches `self.app`.** Every other arm asks the app to do something to a terminal; this one only reaches the store. The delivery-independence pin makes that a number rather than a reading of the code: ten posts, an update and a list send the app **zero** commands, and a `fleet send` to worker-2 is byte-identical at the pty and in the log whether the board is empty or holds ten blocks including worker-2's own marked `done`.
- **One asymmetry with the message path, deliberate.** A failed `append_event` fails a task op, where it only reaches stderr for a message. For a message the store records something that already happened; for a task the store *is* the deliverable, and reporting success would put a block on a board that does not have it.
- **The Tasks view is the fifth view and writes nothing.** `fleet | messages | tasks | activity | settings`, mounted like every other one (`.is-hidden`, never conditional rendering — §7.5, L7; the 11 real-pty tests and every xterm buffer are untouched). No post button, no status dropdown, no drag-to-reorder: an operator control here would be a second writer with no attribution on a screen where every entry is an attributed claim. WP-07 is where the operator gets a voice, by speaking to the fleet rather than editing its record behind its back. `ui/src/fleet/board.ts` mirrors the Rust fold — duplicated rather than fetched, because the events already arrive on the live bus and a Tauri command re-asking for them would be the second source of truth this package spent its whole design avoiding. Rust is the authority when they disagree.
- **Cost, measured — over budget again, and said out loud.** Rendered orch **1,910 → 2,228** tokens and worker **1,343 → 1,591** (DeepSeek Flash tokenizer, `examples/system-prompt-spike/count.py`): **+318 and +248**, against WP-05's budgeted ~150 *across both*. Just under four times the estimate — the same multiple, and the same reason, D-045 recorded: a verb costs what its *rules* cost, not what its syntax costs. Where it went: seven flag names that have to appear or the schema is unreachable, four status words that have to appear or an invented `in-progress` is a refusal, "write criteria that could fail" with its counter-example, and the diary-not-dispatcher clause with its consequence. Every one is pinned by a test, because shortening it turns it into advice. One tightening pass ran before the number was recorded (−6 orch, −27 worker). WP-09 now audits a **second** visible overrun; the standing tension in `00-index.md` carries both.
- **What would reverse it.** A live shakedown (WP-09) showing DeepSeek Flash cannot write criteria that could fail — in which case the block shape is right and the model is wrong, and the Tier 2 worker-model default is what moves. Evidence that the compact `list` output is still too expensive for a pane's context, which would make `--full` the wrong default half of a split. Or the failure this design is built against actually appearing: any pressure to have something *read* the board, at which point the answer is a Tier 1 question, not a feature.

## D-048 — WP-06: the worktrees stay, because the object database was already shared

- **The default that lost was "peer review needs a shared checkout."** The worktree reconsideration was open since the fleet grew a review phase: four workers in four checkouts looked like the thing standing between a reviewer and a peer's code. It is the opposite. `git worktree add -B` gives each worker a **private** `git-dir` — its own `HEAD` and index, which is the whole reason four workers can commit concurrently — while `--git-common-dir` points every one of them at **one** object store. A peer's commit is already local; `git log --oneline HEAD..fleet/worker-3` and `git diff HEAD...fleet/worker-3` work from the reviewer's own directory with no fetch, no remote and no second checkout. Validated live against plain git rather than argued: `docs/peer-review-notes.md` is the transcript, built with the exact command `fleet.rs::ensure_worktree` runs, with both branches genuinely diverged.
- **This is what keeps Tier 1.7 out of the way.** The alternative designs both cost something the builder is not allowed to spend: a shared checkout collapses review semantics (one working tree reported five times — a reviewer looking at its own edits), and cross-worktree access widens auto-approve past a worker's own worktree, which `building.md` §9.2 puts above the builder. The arrangement that was already there needs neither. Read-only is worth stating precisely, though: it is auto-approve's scope plus a brief rule, **not** a git guarantee — nothing in git stops a worker writing into a peer's directory, and calling this sandboxing would be the L3 failure in a new costume.
- **Three dots, and the reason travels with it.** Two-dot diff renders everything the *reviewer* has committed since the fork as a deletion by the *author* — reproduced in the transcript, where worker-2 reading worker-1 two-dot sees its own `lexer.rs` as deleted. A reviewer opening with "you deleted my lexer" is wrong in a way a peer cannot easily argue back from. `prompts/worker.md` teaches the three-dot form *with* the reason, and both are pinned as literals, because the rule without the reason is what a rewrite deletes first.
- **Merging is a worktree, not a checkout.** `orch` merges reviewed branches into `fleet/integration` from `~/.fleetor/_shell/worktrees/integration`, so it never moves the branch the operator is standing on. Verified: after two `--no-ff` merges the target is still on `master` at its original commit with zero changed files, and `rm -rf` + `git worktree prune` leaves the repo clean minus `fleet/*` — exactly the carve-out Tier 1.1 already names. Never trunk; the operator merges trunk themselves.
- **The fallback got louder rather than safer.** When the target is not a git repo, `worker_cwd` still shares the target directory — a fleet that refuses to start over a worktree is worse than one sharing a checkout. But WP-06 raised what that costs: there are no per-worker branches, so `git diff fleet/worker-N` has nothing to compare and review stops meaning anything. The notice now says that in words and says what to do about it (`treat a reviewed done as unreviewed`), pinned by a test — an operator reading "sharing the target checkout instead" had no way to know the review step had quietly become theatre.
- **What would reverse it.** A git version or filesystem where worktrees stop sharing objects (nothing suggests one), or live evidence from WP-09 that workers cannot use branch review from their own directory — which would be a prompt problem before it was an architecture one. Per-task worktrees remain out of scope and are still on WP-05's tripwire list.

## D-049 — WP-06: the reviewer is named in the assignment message, not in a field on the block

- **The default that lost was the spec's own recommendation.** `06-receipts-review-merge.md` open question 4 recommended a `reviewer` field on the task block, and WP-05's schema landed without one. Adding it was the smaller-looking change and the wrong one. Tier 2 — schema and prompt text — so this is the record, not a request.
- **A `reviewer` field is the first field on the board that something would be tempted to read.** WP-05's whole finding (D-047) is that the board is a **diary, not a dispatcher**: nothing reads it back to permit, order or refuse anything, and its tripwire list bans routing by task state. `reviewer` is the one field that begs for it — the obvious next commit is a check that the reply came from the named pane, and that is a review gate in code, which this package's guardrails rule out by name. `outcome`/`technical`/`semantic`/`worker` describe the *work*; `reviewer` would describe *who may act*, which is a different kind of field wearing the same clothes.
- **So the duty is created where the assignment already is.** D-047 already established that posting a block assigns nobody and the `fleet send` is the assignment. The reviewer rides in that same send — "worker-3 reviews this when you are done" — which keeps one act, one message, and one attributed author. `prompts/orch.md` carries the rule and its reason (a peer, never the block's author, never orch itself: an orchestrator reviewing its own decomposition finds what it expected to find), and `prompts/worker.md` tells a worker to ask if it was not named. Nothing enforces any of it; the review reply is an ordinary message, and the board records what happened via `--note`.
- **The side benefit is that WP-05's tests did not move.** `TaskBlock`, its serde shape, `task_board.rs` and the Tasks view are byte-identical — a schema change would have touched a landed package's pinned tests to buy a field whose best use was one nobody is allowed to build.
- **What would reverse it.** Live evidence from WP-09 that reviewers are simply never named — a fleet where `done` goes unreviewed because the instruction sat in a message the worker had already compacted away. The fix would then be a field on the block *plus* the discipline to leave it unread, and the second half is the hard part. The cheaper intermediate fix is prompt text, and it is where this would be tried first.

## D-050 — WP-06: `fleet done` runs the check locally, and its exit code still means delivery

- **The one verb that runs something runs it in the CLI process.** `fleet done <task-id> "<check>"` executes the block's check via `sh -c` in the worker's own worktree, then composes a receipt and sends it to `orch` as an **ordinary `Op::Send`**. The hub never executes anything and never sees the command. That is not a nicety: a hub that ran commands would be the supervisor Phase 5 deleted, with a shell attached.
- **The delivery contract did not move, and this is the place it would have.** `fleet done` is the only verb where a model could reasonably assume the exit code describes the *check*. If it did, a failing check would exit non-zero, both briefs promise that means *not delivered*, and the worker would resend a receipt that had already arrived — D-034's shape in a new place. So: **a failing check still produces a receipt**, `op()` returns `Err` only when nothing could be checked at all, and the check's own result travels in the body (`· exit 7`). Pinned three times — in `done.rs`, in the CLI's `report` test, and as a literal in the worker brief (`never in the exit code`).
- **The receipt is evidence with no opinion in it.** `[receipt] task-1-0 · fleet/worker-2 @ a1b2c3d · exit 0`, then the command, then a fenced tail. There is deliberately no `passed` bool — a bool would be the CLI forming a view about somebody else's criteria, and judgement is the reviewer's (Tier 1.8). A signal-killed command is rendered `killed by a signal` rather than an invented `exit -1`. Uncommitted changes are named on the receipt, because review reads the *commit* the receipt cites and a hash that does not contain the checked work sends a reviewer to honestly review the wrong thing. No git, no invented hash: `not a git checkout — nothing here can be reviewed by branch`.
- **2 KB of tail, and it says what it dropped.** The tail rather than the head, because that is where the summary and the first failure are; a head-capped build log is all compiler noise and no verdict. It reports the dropped byte count for the same reason `accepted` never renders as "delivered" (L3) — a tail pretending to be the whole output is the same lie one layer down. The cap slices on a char boundary, escapes are stripped before anything is measured (legibility and budget, *not* security — the pty boundary is still `message::sanitize`, untouched), and the fence grows past any backtick run inside the output.
- **No deadline on the check** (Tier 1.4's argument, reused): a ceiling could only report failure for a command that then finishes. The pane's own Bash tool has a timeout and it is the caller's to set.
- **The message path's diff is empty, and this time so is the wire.** Zero diff in `message.rs`, `command.rs`, `wire.rs`, `task.rs`, `hub.rs`, `deliver.rs`, `pty.rs`, `pane_messaging.rs`, `panes.rs`, `fleetor-db` and `ui/`. `fleet done` needed no new op, no new `OpResult` variant and no event kind — it reuses `Op::Send` and gets back `Delivered`, so WP-05's `Recorded`/`Board` naming stays coherent by not being touched. `src-tauri`'s only changes are the fallback warning and one test fixture's verb list.

## D-051 — WP-07: the operator is a name in the record, and `recorded` is one word rather than two

- **The default that lost was the spec's own wire recommendation.** `07-operator-participant.md` proposed `OpResult::Recorded { msg_id }` for a pane→operator send, but WP-05 had already landed `OpResult::Recorded { task_id }` for a task claim. Two variants both called `Recorded`, differing only in a field name, would have been two spellings of one fact — the drift `PaneId`'s bare-string serde and the wire-tag-is-the-verb rule exist to prevent, and on a `#[serde(tag = "result")]` enum they cannot even coexist: both serialize to `"recorded"` and the second would shadow the first. So there is **one variant**, `Recorded { record_id }`, and its meaning is stated once: *something entered the log and no pty was written to*. A task claim and a message to the human are the same event class; they differ in what the id names, which is what the field doc says. The rename is the whole wire diff (Tier 2, in-repo, CLI and app ship together).
- **`recorded` is derived, never stored.** `FleetEvent::Message` gained no field. The operator's row carries `accepted: false, detail: None` — which is the *literal truth* of `accepted`'s one meaning, "the bytes reached a live pty", when there is no pty. Every renderer derives the word from `PaneId::has_pty(to)`, a total function that cannot disagree with itself, and `Message::into_recorded_event` is the single constructor so the rule has one home. The alternative the spec explicitly ruled out — `accepted: true` with `detail: "recorded"` — would have diluted the one word Tier 1.5 exists to keep undiluted. `detail: None` matters too: a detail is a reason for a failure, and nothing failed.
- **The asymmetry that comes with it: a failed append fails the op.** For a pane message the log records something that already happened at a terminal, so a store error reaches stderr and the send still succeeds. For a message to the human the log **is** the delivery — the inbox is a view of it — so an append that failed means they will never see it, and answering `recorded` would be L3's lie with a person on the other end. Same asymmetry, same reason, as a task post (D-047).
- **`PaneState::Present`, never a faked `Live`.** The operator sits on `fleet roster` with a word of its own. `Live` is a claim about a terminal — the delivery predicate, the roster dot, the operator's own reading of "is that pane up" all rest on it — and a participant with no terminal wearing it would be the roster's version of rendering `accepted` for a message no pty received. `accepts_input()` is `false` for it: nothing asks, because the operator's messages never enter the delivery path, but a `true` would be a standing invitation for something to try.
- **The operator joins the roster *listing* and not the app's roster.** `Hub::roster` prepends the row; `Hub::app_roster` — which is what `broadcast` fans out over — is untouched. A leg addressed to the operator would be asked of a pty that does not exist, come back refused, and make **every** `fleet broadcast` in the fleet report a partial failure, which the brief teaches means "the panes that missed it need following up". The human is addressed by name, which is also the only reading consistent with "the inbox is a surface, not a system": nothing sweeps fleet chatter into it.
- **The message path's diff for pane↔pane traffic is one guard clause.** `message.rs` is additive only (a constructor and its tests); `command.rs`, `deliver.rs`, `pty.rs`, `event.rs`, `panes.rs` and `fleetor-db` have **zero** diff. In `hub.rs`, `send`/`broadcast`/`reply`/`log_message`/`ask_app`/`ask_app_command`/`last_inbound`/`emit` are byte-identical; `deliver` gained `if !msg.to.has_pty() { return self.record(msg) }` above everything it used to do, and `roster` gained the row. `cmd` gained one refusal, at accept time next to the allowlist check, because letting `fleet cmd operator "/clear"` through to be rejected by the registry would have described the human as a crashed pane.
- **The composer calls the hub in-process rather than dialling the socket.** The human has no pane and so no socket, but "operator → pane rides the existing path unmodified" has to be a property rather than a promise: `fleet_send` calls `Hub::handle(PaneId::Operator, op)` — the identical function `serve_conn` calls after reading a `Hello`, with only the socket missing. Its target select resolves to the fleet's three existing message verbs (`all` → `Broadcast`, `reply` → `Reply`, a name → `Send`) and no fourth kind of message; `all` and `reply` are spellings of a *verb*, so they are resolved in `operator_op` rather than added to `PaneId`, exactly as the CLI resolves `self` locally (D-045).
- **`operator` is exact, and `o` still means orch.** The parser is generous about pane names because a model types them constantly; the human is addressed rarely and by one name both briefs spell out, so a short alias would only buy a way to reach a person by typo. Pinned by a test that also refuses `op`, `human` and `operator-1`.
- **Never spawnable, and refused where the spawn decision is made.** `spawn_pane` returns "the operator is a participant, not a pane" rather than leaving it to fail deeper; there is no command to run, no cwd, and no config dir to seed. The UI offers no control for it either.
- **The inbox and composer are footers to the record, not a second column.** No notification, no unread count, no chime — the Open Loops alert was cut upstream for exactly this reason. Both stay mounted (§7.5): an inbox that appeared when it had something would be attention machinery wearing a layout's clothes. The composer's default target follows the last pane that wrote to the operator, until the operator picks one themselves — overriding a deliberate choice because a message landed mid-sentence would send it somewhere they did not pick. That default is a fold over the same events the hub folds into `last_inbound_from`, so the two cannot disagree.
- **Typing into a terminal is still unlogged.** This package adds a logged channel; it does not log keystrokes. `pty_write` is untouched.
- **Cost, measured — the fourth overrun, and the smallest.** Rendered orch **2,542 → 2,668** and worker **1,967 → 2,102** (DeepSeek Flash tokenizer, `examples/system-prompt-spike/count.py`): **+126 and +135**, against a budgeted ~60 for the worker alone. Roughly 2× rather than the 3–5× of D-045/D-047/D-050, and the reason is that this package added **no verb**: `fleet send` already existed, so what had to be taught is one name, one word, and one authority clause. The vocabulary sentence went into `delivery-contract.md`, the fragment already composed into *both* briefs, so it is written once and arrives twice. A tightening pass ran before the number was recorded (−27 orch, −11 worker). `OVERNIGHT-QUESTIONS.md` Q-4 carries the number, because Q-2 and Q-3 had already said the headroom was gone.
- **What would reverse it.** Live evidence (WP-09) that workers address the operator for things `orch` should have settled — in which case the fix is prompt text ("only the human can settle it" is already the bound), not removing the channel. Or an operator who wants fleet broadcasts in their inbox after all, which is one line in `Hub::broadcast`'s target list plus accepting that every fan-out then reports `accepted: false`; the honest version of that change is a `recorded` leg, and it is a bigger change than it looks.
- **Verified:** 186 workspace tests and 86 shell tests green (45 CLI, 99 core, 26 pane-messaging, 7 task-board, 11 real-pty), `tsc --noEmit` and `vite build` clean. The delivery-contract and broadcast-rule tests are untouched and green; `panes.rs`'s eleven real-pty tests never saw the new name.

## D-052 — WP-08: the fence is `HOME`, seeded with one file, and the PATH leak it would have left open

- **What changed.** `worker_command` now sets `HOME` to a private per-slot directory (`~/.fleetor/_shell/home/worker-N`, created and seeded on spawn — a sibling of `pane-config` and `worktrees`, `fleet::worker_home_dir`), seeded with exactly one file: a `.gitconfig` naming `fleet worker-N` as commit author (`spawn::seed_worker_home`). `augmented_path()` — which read the **app's own** `$HOME` (the operator's real one) to prepend `{home}/.local/bin:{home}/.bun/bin` onto every pane's PATH, workers included — is now orch-only; a new `worker_augmented_path()` keeps the fleet-bin rung and the two system dirs and drops both operator-HOME rungs. `prompts/launch.conf` gained a `[fence]` section with `posture = open`, parsed into `LaunchConfig` and validated (any value other than `open` is refused with a warning and falls back, because no other posture is implemented and a setting that silently did nothing would read as hardening that never happened — no Posture Ladder exists; one was proposed and rejected upstream).
- **Why the PATH half is in the same commit and not a follow-up.** A fenced `HOME` that still left `{operator's real HOME}/.local/bin` on a worker's PATH would have been fenced in name only: `~/.ssh` stops resolving, but a worker could still reach the operator's own scripts by an unqualified command name through PATH. The spec's own design sketch named this exact pairing (open question 2), and splitting it into a later commit would have shipped the weaker half alone.
- **What was seeded, and what was deliberately left broken.** Only the gitconfig — the spec's own recommendation (open question 1: "nothing beyond gitconfig — add files only when the breakage catalogue demands"). `docs/fence-notes.md` is that catalogue, measured live: `gh` loses its stored credentials entirely under a fenced `HOME` (`gh auth status` goes from a real logged-in account to "not logged into any GitHub hosts"), and `nvm`-style tools would lose their installed-version state by the same mechanism (`NVM_DIR` defaults to `$HOME/.nvm`; not installed on the measuring machine, so this one is reasoned from `nvm`'s own documented default rather than run live). Neither is seeded — nothing in any landed package has a worker call `gh`, and no version manager is in scope anywhere. `CLAUDE_CONFIG_DIR` is unaffected by construction, exactly as the spec's current-state note predicted (it was already an explicit env var, never `HOME`-derived).
- **What the fence does not stop, named rather than implied.** Two gaps, both explicit in `docs/fence-notes.md` rather than left for someone to discover: (1) the PATH fix only removes the two rungs `augmented_path()` itself computes — the *inherited* tail (whatever PATH the app's own process already had) is untouched, so a worker launched from a terminal whose shell profile already exported `~/.local/bin` can still reach it there; stripping the inherited tail is the sandboxing decision the spec rules out by name. (2) non-`HOME`-keyed ambient credentials (`SSH_AUTH_SOCK` chief among them) are untouched — `~/.ssh` stops resolving by path, but an agent socket still lets `git+ssh` authenticate as the operator. Both are named in the notes doc rather than fixed, because fixing either is the deferred Posture Ladder, not this package.
- **The falsification test and the WP-06 debt, both run live rather than reasoned about.** `ls ~/.ssh` under a worker's exact fenced env (`env -i HOME=<private dir> PATH=... sh -c ...`) fails by path resolution — ordinary "No such file or directory," not a permission error. Separately, a real `git commit` under the same fenced env with no `-c user.*` override succeeded and attributed correctly from the seed, and a second worker's `git diff HEAD...fleet/worker-1` from its own (also fenced) worktree reproduced `peer-review-notes.md`'s original clean three-dot diff with no fetch and no shared checkout — confirming the worktree mechanism `peer-review-notes.md` measured does not route through `HOME` at all, so fencing it does not disturb peer review. Zero live DeepSeek probes: the overnight brief allowed up to two if a real-`claude` confirmation would add information over the env-level proof, and it would not have — `claude`'s pty resolves `~` and `$HOME` through the same OS call a plain `sh` does, so the shell-level proof is the whole proof.
- **What would reverse it.** Live evidence that a worker legitimately needs `gh` or a version manager mid-task — the fix is scoping and seeding that tool's config for the worker specifically (a `decisions.md` entry naming what got added and why), not loosening `HOME` generally. Evidence that the inherited-PATH gap or the `SSH_AUTH_SOCK` gap is being exploited or relied on in practice is what would justify building the Posture Ladder this package deliberately left un-built.
- **Verified:** 186 workspace tests unchanged and green (WP-08 touched no core crate); 92 shell tests green — 81 lib (`cargo test` in `src-tauri`, including 8 new fence tests: private-HOME wiring, worker-vs-orch PATH, gitconfig seeding and its idempotency, `[fence] posture` parsing and its fallback) plus the 11 real-pty tests in `panes.rs`, all previously-passing tests untouched including the L1/L2 pins (`a_virgin_config_dir_gets_the_two_keys...`, `a_worker_carries_the_auth_token_and_never_the_api_key`). `tsc --noEmit` and `vite build` clean — no UI or prompt-template files touched, so `brief-cost` stayed at the spec's own `0`.

## D-058 — WP-11: a run is a database, rotated at start, and history is a directory of frozen files

- **What changed.** The event log stops being one file that every fleet start appends to. `~/.fleetor/_shell/state.db` is now always and only the **live** run; at each `fleet_bootstrap`, before the store is opened, the previous run is archived to `~/.fleetor/runs/<timestamp>/state.db` and a fresh database is opened. Archiving checkpoints the old WAL and moves a single self-contained file (strategy B in `docs/notes/run-rotation-notes.md`), falling back to moving `state.db`+`-wal`+`-shm` together, and finally to leaving them alone with a `Warn` — rotation may never fail a boot. `runs/index.json` holds each run's editable label, target and derived counts, and is a **cache**: reads scan `runs/*/` for existence and merge, so losing it costs labels only. A new History view lists past runs and opens one read-only into the existing Messages, Tasks and Activity components. The run id is the timestamp directory; the label is a separate mutable string, auto-suggested at archive time, so renaming never moves a file.
- **Why the default lost.** The single shared log was about to become actively wrong: the evaluation loop this unblocks compares one cycle against another, and cannot while cycle 4's read returns cycle 1's messages. Physical isolation beat the cheaper `run_id`-column design because run separation behind a `WHERE` clause on the one table that is this app's whole persistence story is the corruption being prevented, reimplemented as a predicate — and migrations here are appended, never edited, so a wrong schema would be permanent. The boundary is cut at **start** rather than at teardown because teardown is the thing that fails; `orphans.rs` exists for exactly that reason, and a crash under rotate-on-stop silently reopens the previous run.
- **What would reverse it.** Runs accumulating to the point that the directory needs a retention policy — at which point the answer is a size column and an operator-driven delete before it is automatic expiry. Or a measured need for cross-run queries frequent enough that opening N files hurts, which would argue for `ATTACH` over a schema change, not for the `run_id` column.

## D-059 — the archive is written for an agent to read, and it takes the workers' transcripts with it

- **What changed.** An archived run stops being one SQLite file and becomes a readable directory. Rotation now also writes `events.json` (the whole log as a JSON array, each row the event exactly as it crossed the wire plus its `seq` and `ts` columns) and `manifest.json` (the run's metadata, what each file in the directory is, and what the data does *not* cover), and **moves** each worker's Claude Code session transcripts from `pane-config/worker-N/projects/*/` into `runs/<id>/transcripts/worker-N/`. Moved rather than copied: transcripts live in a config dir that outlives a run, so copying would leave every archive carrying its predecessors. `RunRecord` gains a `transcripts` count, the History rows gain an Export button, and `run_export` saves `events.json` wherever the operator points via the Rust-side dialog — a copy of the file that already exists, never a second serialization, so "download the logs" and "what an agent reads" cannot drift into two formats.
- **Why the default lost.** The operator's stated purpose for History is that *agents* read and evaluate past runs, humans later. That inverts the design: the primary artifact is a directory readable with `cat` and `jq` — no SQLite, no running app, no GUI to drive to produce the reader's own input — and the download button becomes a convenience over it rather than the mechanism. The event log alone was also the wrong evidence base: it records what the panes said to each other, and an evaluator asking why a run went the way it did needs what each pane *did* between saying things, which only the transcripts hold. `events.json` is deliberately re-emitted from parsed JSON rather than re-serialized through `FleetEvent`, so a field a future build adds survives being read by an older one.
- **What would reverse it.** Disk: every run now stores its log twice plus its transcripts, and a long run's transcripts dwarf both. If that bites, the answer is generating `events.json` on demand and keeping `state.db` as the only stored copy — at the cost of the property that makes this useful, so measure the actual sizes first. **The known gap, unreversed:** `orch`'s transcript is *not* archived, because it lives in the operator's own `CLAUDE_CONFIG_DIR` outside `~/.fleetor` and reaching in there crosses Tier 1.1's boundary. The pane doing the deciding is the one whose reasoning the evaluator cannot read. Closing it needs an operator decision, not a builder's.

## D-062 — WP-14: `orch` gets a config dir of its own, and D-059's named gap closes

- **What changed.** `orch` stops running on the operator's own `CLAUDE_CONFIG_DIR`. It now spawns with `CLAUDE_CONFIG_DIR=~/.fleetor/_shell/pane-config/orch`, seeded at the spawn site with the same two onboarding keys a worker's dir gets — because once it is a fleet-owned directory, L1 applies to `orch` exactly as it applies to a worker. Its session transcript therefore lands under `~/.fleetor`, and `runs::harvest_transcripts` archives it into `runs/<id>/transcripts/orch/` with **no code change**: it already walked `_shell/pane-config/*`. Nothing is read, copied or linked out of the operator's directory; `orch` starts a new one and goes forward from there. `worker_config_dir(slot)` became `pane_config_dir(PaneId)`, one root for every pane. This also gives WP-17's deny rules and hooks the home they need — the second job WP-12 filed this package for.
- **The load-bearing detail, and it is not obvious.** `CLAUDE_CONFIG_DIR` alone **logs `orch` out**, invisibly. Claude Code namespaces its macOS Keychain service name by `sha256(config dir)[..8]` whenever that variable is set, so a fleet-owned directory is a fresh, empty login. The pane still reaches its input box, so every `fleet send` into it reports `accepted` and only its turns fail — the risk-register failure that looks exactly like a healthy pane. `orch_command` therefore also sets `CLAUDE_SECURESTORAGE_CONFIG_DIR` to the **empty string**, which selects the unsuffixed service name: the entry the operator's own `/login` already wrote. That moves the credential *lookup* and nothing else — `claude` performs the identical keychain read it performs today, so this does not touch the operator's auth, it preserves it. `worker_command` `env_remove`s the same variable so a worker can never inherit the key to that entry. Measured against CC 2.1.224 in `docs/notes/orch-config-dir-notes.md`, four arms of a real interactive pane plus the derivation read out of the binary.
- **Why the default lost.** D-059 left this gap open and said closing it needed an operator decision, because reaching into the operator's personal Claude history to move it would cross Tier 1.1. The operator made the call: the pane that makes every decision cannot be the one pane an evaluator cannot read, and the event log alone gives it `orch`'s messages with none of its reasoning. The refusal that produced the gap is intact — nothing reaches into their directory. What changed is that `orch` gets a directory of its own going forward, which is a different move from the one D-059 refused.
- **What it costs, stated plainly.** `orch` no longer inherits the operator's user `CLAUDE.md`, skills, subagents, MCP servers, settings or hooks — all of which are read from `CLAUDE_CONFIG_DIR` (`docs/notes/system-prompt-notes.md` §3 measured that they load today). D-030's "orch is untouched" is narrowed here for the first time, and narrowed to exactly one thing: the config dir. The Fence stays worker-only, `HOME` is still the operator's, `augmented_path()` still reads it, and `orch` still spawns with no `--permission-mode` and no `ANTHROPIC_*` override. Three tests assert that, because the cheap way to break this package is to make `orch` slightly more like a worker.
- **What would reverse it.** An operator noticing that `orch` stopped being *their* Claude — no skills, no MCP servers, no memory. The fix is not to undo this: it is to let the operator populate `~/.fleetor/_shell/pane-config/orch/` themselves, which is a directory they own and this app only seeds two keys into. Or Claude Code dropping `CLAUDE_SECURESTORAGE_CONFIG_DIR`, which is an internal and not in `claude --help`. That failure is bounded and self-healing — `orch` shows `Not logged in · Run /login`, one `/login` inside the pane writes the credential into the fleet dir's own namespace, it persists, and it cannot disturb the operator's own entry. `spawn_pane` puts that sentence on the Activity feed at every `orch` launch rather than leaving the operator to diagnose a pane that looks fine.
- **Not verified:** `orch` reaching a prompt *inside the running app*. The exact environment was spawned by hand in a pty and reached `Claude Max` with an input box; no fleet has been started since the change landed.

## D-063 — the answer key is absent, not unobtainable, and a frozen grader is not enough

- **What changed.** Two claims in WP-12 are corrected by the rewind harness's own measurement (`~/harness/fleetor-eval/NOTES.md`, 2026-08-07). (1) The answer key was called "airtight and free." It is free and **not airtight**: the pinned tree names its own upstream in six files and states its version, and GitHub serves arbitrary SHAs to `git fetch`, so a deliberate clone or a fetch-by-SHA retrieves everything the shallow clone withheld. Scrubbing the upstream identity is not available as a fix — the information that makes the hole possible *is the project*. (2) Case 5 said the grader must be frozen across generations; that is necessary and **not sufficient**, because judging weights are per-mission, and the same mission run twice is contaminated by the previous generation's branches and archived reasoning.

## D-067 — worktrees namespaced by target repo

- **What changed.** `worktree_dir(slot)` became `worktree_dir(target, slot)`. Worker worktrees now live at `~/.fleetor/_shell/worktrees/<target-slug>/worker-N` where `<target-slug>` is the target directory name plus a 4-character hex hash of the canonical path (e.g. `my-project-a3f2`). `target_slug()` in `fleet.rs` computes it.
- **The default that lost was a flat `worktrees/worker-N`.** Switching targets left stale worktrees from the old repo on disk. `ensure_worktree` saw `.git` and short-circuited, so workers ended up in checkouts of the wrong repo. The alternative — detect-and-recreate — would have torn down and rebuilt worktrees on every target switch, losing any uncommitted worker state and adding teardown logic. Namespacing preserves each target's worktrees independently, so switching back reuses them.
- **What would reverse it.** Evidence that the disk accumulation matters (each target's four worktrees persist until `rm -rf ~/.fleetor/_shell`), or a target whose directory name plus hash collides with another in practice — which would require two targets whose canonical paths produce the same 16-bit hash *and* share a directory name.

## D-069 — the Fence learns about rustup: both toolchain homes are the fleet's own

- **What changed.** A worker is now launched with `CARGO_HOME=~/.fleetor/_shell/cargo` and `RUSTUP_HOME=~/.fleetor/_shell/rustup`, plus one PATH rung (`_shell/cargo/bin`) holding eight shims symlinked to the operator's real `rustup` binary. `_shell/rustup` is a **mirror**: `settings.toml` copied, one symlink per installed toolchain into the operator's real `~/.rustup/toolchains/`. 4 KB seeded, against the 1.9 GB it points at. Both are seeded at spawn beside the private HOME (`spawn::seed_fleet_toolchain`), shared by all four workers, and set only when this machine actually has a rustup. `orch` gets neither — it is the operator's own `claude` (D-030).
- **This is D-052's own reversal condition, exercised as written.** D-052 reserved "live evidence that a worker legitimately needs … a version manager mid-task — the fix is scoping and seeding that tool's config for the worker specifically, **not** loosening `HOME` generally." `HOME` is untouched. `docs/notes/fence-notes.md` gains the 8th catalogue row and thirteen arms behind it.
- **The recorded bug was smaller than the real one.** WP-17 open question 1 recorded `rustup could not choose a version of cargo to run`. That measurement, and every arm in `examples/write-guardrail-spike/allowlist.sh`, ran with `PATH="$PATH"` — the operator's *login* PATH, which carries `~/.cargo/bin` — so it never asked whether a worker can find `cargo` at all. It cannot: `/opt/homebrew/bin/cargo` and `/usr/local/bin/cargo` are both absent, and those are the only two non-fleet rungs `worker_augmented_path` supplies. Under any PATH but an inherited login one the failure is `cargo: command not found`, exit 127, *before* rustup is reached. That is why the fix is a PATH rung and not two environment variables.
- **The plan going in was wrong about `RUSTUP_HOME`, and the spike won (`building.md` §4).** It proposed pointing `RUSTUP_HOME` at the operator's real `~/.rustup` on the grounds that it is read-only in practice, with the residual gap named. Arm 6b falsifies that: a `rust-toolchain.toml` naming an **uninstalled** channel — an ordinary thing for a repository to carry — downloads and installs it with no prompt, **35,981 files and ~1.2 GB into `~/.rustup`**. Arm 9b runs the identical pin against the mirror and the identical 35,981 files land under `_shell/` instead, 0 in the operator's. The mirror was listed in the plan as optional; it turned out to be free, and it is the difference between Tier 1.1 holding and not.
- **Why not point `CARGO_HOME` at the operator's `~/.cargo`** (the shape the old spike proved): it hands four auto-approving workers write access to `~/.cargo/bin`, which is on the *operator's* login PATH. Measured rather than reasoned — arm 7b runs `cargo install` under that setting and `~/.cargo/bin/spikey` appears. The write guardrail cannot refuse it, because `cargo install X` names no path (D-065's own measured limit). This is accident-shaped, which is the threat model this repo committed to.
- **Why not add `~/.cargo/bin` to the worker PATH:** that is the category of rung D-052 removed on purpose, and worse than the two it removed — the directory holds real binaries, not only shims (`cargo-create-tauri-app`, 1 MB, verified), and its contents change whenever the operator installs anything. The seeded rung exposes exactly the eight names the fleet enumerated, in a diff.
- **All eight shims or none, and that is measured.** Seeding `cargo` alone fails at `could not execute process 'rustc -vV' (never executed)` (arm 5a): cargo resolves through the proxy, then looks for `rustc` by name and finds nothing. With `cargo`, `rustc`, `rustup`, `rustdoc`, `rustfmt`, `cargo-fmt`, `cargo-clippy` and `clippy-driver` all linked, the build is clean (arm 5b).
- **One shared pair of directories, not one per worker.** Arm 8 runs two workers building concurrently against one `CARGO_HOME`: both exit 0, serializing on cargo's own package-cache lock. Per-worker `target/` already lives in each worktree, so a split would buy only a duplicated registry. Footprint after eight builds: 616 KB.
- **Absent rather than pointing at nothing.** With no rustup on the machine, neither variable is set and the PATH is byte-for-byte what it was. A `RUSTUP_HOME` naming a directory that does not exist makes rustup try to *install* there, which is a worse failure than today's. The operator is told once, on the Activity feed, beside the missing-`fleet`-binary warning.
- **No write-guardrail root was added, and there is now a test saying so.** `_shell` is already every pane's second root, so `_shell/cargo` and `_shell/rustup` were never refused. WP-17's instruction was "do not widen the allowlist to work around this"; it is honoured structurally, and `guardrail.rs::the_fleets_toolchain_homes_are_inside_a_pane_root_so_a_build_cache_write_is_never_refused` asserts `roots.len() == 2` so a later reader who reaches for `[fence] allow` finds out here.
- **An existing pin changed letter, and it is stricter.** `worker_path_drops_the_operator_home_rungs_orch_keeps_them` asserted `!worker_path.contains("/Users/operator")` — a substring sweep that held by luck. The new rung *is* under the operator's HOME, because that is where `~/.fleetor` lives. `worker_path_drops_every_operator_tool_rung_and_adds_only_the_fleets_own_cargo_bin` replaces it: every operator tool rung forbidden **by name**, `.cargo/bin` among them (the old test never named it), at most one rung under the operator's HOME and it must be the fleet's own, and orch's half byte-identical.
- **What this does not stop, named rather than implied.** The shims reach the operator's `rustup` binary by absolute path and the mirrored toolchains are absolute symlinks into `~/.rustup/toolchains/` — the Fence never claimed to stop absolute paths, and that is what makes a 4 KB mirror possible instead of a 1.9 GB copy. `rustup` itself is on a worker's PATH and must be (the shim set is all-or-nothing), so `rustup toolchain install` still works — it now writes into `_shell/rustup`. A worker can delete or corrupt the mirror, since `_shell` is inside its roots by design; the cost is a re-seed at the next start, never the operator's toolchain.
- **One inference is left standing and is labelled as one.** What a Finder-launched app inherits was **not** confirmed. The probe — a minimal `.app` launched through `open` — came back inconclusive: a sentinel variable proved `open` forwards the calling shell's environment, so it measured a terminal. `launchctl getenv PATH` is empty, which supports the inference; `ps eww | tr ' ' '\n' | grep ^PATH=` is actively wrong on this machine, because a PATH rung contains a space and the splitter truncates there. The fix does not depend on the inference: arm 2b shows the login-PATH case is broken too.
- **What would reverse it.** Evidence that a worker needs a toolchain the mirror does not expose, which is a wider seed and not a wider `HOME`. A cargo or rustup release that stops honouring `CARGO_HOME`/`RUSTUP_HOME`, which is upstream's own documented contract and would be loud. Or `_shell/rustup` growing enough to matter, whose answer is D-058's: a size column and an operator-driven delete, since a delete costs a re-download and never correctness.

## D-070 — an improve run targets a clone, never the live checkout

- **What was settled.** When the fleet is pointed at FLEETOR's own source (the improve run), the target is a **clone** — `git clone <repo> ~/fleetor-improve` — not the working checkout the app is running from. Reviewed work still merges to `fleet/integration` inside that clone (D-050 unchanged); the operator pulls from the clone into trunk themselves, deliberately, after a restart.
- **The failure it avoids is the file watcher, not the build.** Workers cannot break the running app: each works in its own worktree with its own `target/`, and reviewed branches never reach trunk, so nothing the fleet compiles is ever what the operator is executing. `orch` is the exception — its cwd is the target repo itself, and `tauri dev` watches `src-tauri/` with no `--no-watch` anywhere in this repo's config. An `orch` that edits a `.rs` file directly rather than delegating restarts the app underneath itself.
- **And a restart ends the run.** Panes are ptys the app owns; they die with it and there is no reattach. What survives is bounded and already built: `orphans.rs` kills the leaked `claude` processes at the next launch, and the run log rotates into `runs/` (D-058). So the cost of the crash is the whole live fleet, which is exactly the cost worth designing out.
- **The alternative was `--no-watch` on the dev launch.** One flag, and it leaves `orch` writing into the tree the operator is developing in — the isolation would depend on a launch argument nobody re-checks. The clone also makes a bad generation `rm -rf` rather than a git recovery, and it is the same shape workers already have (their own checkout, merges reviewed before they travel).
- **Not implemented, and nothing in code enforces it.** This is an operator procedure today: point the target picker at the clone. If live running shows the wrong target chosen by accident, the fix is a refusal at the target picker when the target resolves to the running app's own source — cheap, and worth waiting for evidence rather than guessing at.

## D-071 — the target is fixed once a pane exists, and the backend is what says so

- **What changed, and it is a behaviour change.** `fleet_set_target` and `fleet_pick_target` now **refuse** when the pane registry holds any pane. Both take `State<Arc<PaneRegistry>>` and funnel through one new private `adopt_target`, which checks `ensure_target_settable` before `write_target` and `apply_target`. A command that used to succeed unconditionally now fails in one case. Nothing about the start gate moves: with an empty registry both commands do exactly what they did.
- **The rule is not new; only its address is.** `Fleet.target`'s own doc comment already said the target is "safe to update before panes exist (the start gate); once panes are running the UI hides the target input" — so the invariant was written down, believed, and enforced entirely by `App.tsx:221`'s `!started` latch. That is the interface deciding what the thing that owns the state may do. Half a fleet in one repository and half in another is incoherent, which is the same reasoning that makes the target resolved once at bootstrap rather than re-read (D14).
- **The condition is `PaneRegistry` non-empty — existence, not membership and not liveness.** `roster()` was rejected because it filters to `is_fleet_member()`, so a session holding only the evaluator would answer "no panes" and accept a target change under a pane reading a run. `accepts_input()` was rejected because a pane that has *exited* was still seeded — config dir, worktree, brief, guardrail roots — against the target that was current when it spawned, and `PaneRegistry::spawn` respawns it in place rather than treating it as new. The map is emptied only by `kill`/`kill_all`, which is exactly the moment nothing holds the old target: kill every pane and the target is settable again, by construction rather than by a second rule. A poisoned registry answers "a pane exists" — the caller is a guard and must fail closed.
- **The broader condition that lost: "the fleet is bootstrapped."** `FleetState` being `Some` is what the interface actually keys on (`started` flips when `fleet_bootstrap` resolves, before any pane spawns) and it refuses strictly more often. It was rejected because it is not a reading of "a pane exists" — it is a different rule, and the honest version of it belongs with WP-21's half of D14, where the target snapshot and the evaluator wake become one source. Between bootstrap and the first spawn, `apply_target`'s in-place update is still correct and still the documented behaviour; refusing there would have been a rule this entry did not argue for. **The window is checked and it is not a gap:** `PaneContext` holds the *unrendered* templates and the launch config (`prompts.rs:78`) — nothing target-dependent — and `fleet_bootstrap` reads `f.target` live at each spawn (`fleet.rs:362`), so a target set between bootstrap and the first spawn is honoured in full. That is why the narrower condition costs nothing here.
- **One funnel, not two guards.** The picker also calls `ensure_target_settable` up front, before the folder dialog opens — making an operator browse to a folder and only then refusing it is a worse way to deliver the same sentence — but it still goes through `adopt_target`, so the picker is not a second place the rule has to be right. The refusal precedes `write_target` deliberately: a `config.json` recording a target no pane will ever spawn against is worse than no change at all.
- **The sentence, held as a constant so the test asserts on what the operator reads.** "the target is fixed for a running fleet — every pane was configured against the current one when it spawned. Stop the fleet (close the window) and set the target again at the start gate." **An operator who relied on the old behaviour** — calling `fleet_set_target` mid-run and expecting the next spawn to land in a new repo — never actually got that: panes already up kept the old one, so the result was the split fleet this refuses. The replacement move is the one in the sentence: close the window (which is `teardown_fleet`, killing every pane and shutting the hub), relaunch, set the target at the start gate, start.
- **The interface guard stays, and no UI file was touched.** `!started` still unmounts `StartGate`, which is the only component that calls either wrapper. It is now belt and braces: the interface keeps the control out of reach earlier than the backend refuses, and the backend refuses whatever reaches it.
- **What would reverse it.** A pane kind that genuinely does not care which repository the fleet is in — the Critic reading an *archived* run is the near candidate (WP-23), and the fix would be a predicate on the spec rather than a count of the map. Or a supported target switch that tears the fleet down and brings it back up as one action, at which point the refusal becomes a confirmation prompt in front of that action instead of a dead end.
- **Verified:** **177** shell tests green, up from **176** at `f542888` — 146 lib (1 new: `fleet::tests::the_target_is_settable_until_a_pane_exists`, which drives a real `PaneRegistry` over a real pty and asserts accepted-before-spawn, refused-after with both the claim and the remedy present in the message, and settable again after `kill_all`), 4 dev-mode, 8 evaluator, 11 real-pty, 8 write-guardrail — all unchanged. **213** workspace tests green, unchanged; no `crates/` file was touched. `tsc --noEmit && vite build` clean. `cargo clippy --all-targets` introduces no new warning (the three it reports are at `fleet.rs:1039`, `pty.rs:355` and `spawn.rs:193`, all pre-existing). No prompt template changed, so `brief-cost` is 0 and D-068's 51-token headroom is untouched. **Not verified:** the refusal has never been seen in the running app — no fleet has been started since this landed, the same honest gap D-062, D-065, D-066 and D-069 each record. Nothing exercises the two `#[tauri::command]` wrappers themselves; a `State<'_, T>` is not constructible outside a Tauri runtime, so the test drives `ensure_target_settable`, the function both wrappers pass through, and the wiring between them is held by reading the diff. ## D-072 — the layout and the host: a pane's bring-up is a function of values, not of the operator's machine

- **What changed.** A new `src-tauri/src/placement.rs` owns the order a pane is brought up in, and `orch` — and only `orch`, this ticket — comes up through it. Two values arrive with it. **`Layout`** says where this fleet lives on disk: it is the one definition of the `~/.fleetor` tree, and `fleet.rs`'s nine location helpers are now each the operator's layout plus one accessor rather than nine independent re-derivations from `$HOME`. **`Host`** says what this machine has — the built `fleet` binary, the stand-in pane override, the operator's `HOME` and `PATH`, the Rust toolchain, the worker API key, the mission harness roots. `place(spec, &layout, &host, target, &context) -> Result<Placed>` returns the command, the notices and the gauge source. Workers and the evaluator keep the old sequence until tickets 03 and 04.
- **Why this is logged at all.** `building.md` puts internal module structure in Tier 3, and as a refactor this needs no entry. The entry is for the two values landing on the fleet's live state, because the next package will look for one — WP-22 and WP-23 both place panes, and "where does the layout come from" should have an answer that is not archaeology.
- **The rule that makes it worth doing: placement performs no process-global reads.** No home directory, no environment variable, no configuration path resolved inside `place`. Everything arrives in the layout, the host, the target or the context. That is not tidiness — it is the entire difference between a sequence that can be tested and one that cannot. The old path bottomed out in functions that read the operator's real `$HOME` at call time and took no argument, so it could only ever run against the operator's own installation. Each value has **two real constructors** so neither seam is hypothetical: `Layout::for_operator` / `Layout::under`, and `Host::discover` / `Host::bare`.
- **The host is discovered per spawn, not held on `Fleet` (D13).** This is what the code already did — binary, toolchain and key were each resolved at every spawn — so preserving it is what keeps this a pure refactor. It is also the better semantics: installing a toolchain mid-session takes effect on the next pane restart rather than being invisible until relaunch. The cost is a handful of filesystem checks, six times a session.
- **Notices are returned as `(level, text)` data, not written to the log from inside placement.** The same shape `prompts` and `guardrail` already use, and the reason placement needs no store. It is also what made "what does the operator actually read when orch comes up" assertable for the first time — before this, the only way to see those four lines was to run the application and read the Activity feed.
- **`PaneSpec` has one variant today, deliberately.** Stubbing `Worker`, `Evaluator` and `Critic` as arms that error was rejected: the live path for those kinds is still the old sequence, and `building.md` §6 is explicit that dead code implementing a pattern the design now bans is a trap, because the obvious next move on finding one is to re-point it at something live. Every variant that exists, works. Ticket 03 adds `Worker(slot)` in the commit that moves workers.
- **One duplicate implementation was refused rather than accepted.** `orch_command`, `augmented_path` and `base_command` each read the process, so placement could not call them. Each gained a `*_with`/`*_from` sibling taking those reads as arguments, and the reading function became a one-line wrapper onto it — one implementation, two entry points. `fleet.rs`'s `install_guardrail` likewise became the emitting wrapper over `placement::guardrail_notices`, so the evaluator's narrower roots have one home. Ticket 05 deletes the wrappers with their last callers.

## D-075 — the process-shaping module becomes an internal of placement, and the layout goes on the fleet

- **What changed.** `src-tauri/src/spawn.rs` is now `src-tauri/src/placement/spawn.rs`, a **child module of `placement`** rather than its sibling, and every seeding and command-building function in it is `pub(super)`. - **The seam `spawn.rs` presented was hypothetical, and the test for that is who calls it.** Every seeding and command-building function in it had exactly one production caller after ticket 04, and that caller was `placement`. ## D-076 — the Critic: a fourth pane identity, a fifth brief, and a sixth finding category the spike earned

- **What changed.** `PaneId::Critic` joins `Orch`, `Worker(n)`, `Operator` and `Evaluator`, and `PaneSpec::Critic { run: RunSource }` joins the three placement variants. A new `src-tauri/src/critic.rs` says what it is told and where it works; `prompts/critic.md` is its brief, baked in with `include_str!` and overridable from `~/.fleetor/prompts/critic.md` like every other brief; `PaneContext` carries a third template. - **The one fact every asymmetry falls out of: the Critic is a reader, not a participant.** `Operator` has no pty; `Evaluator` has a pty and is hidden; this has a pty and is simply not *in* the fleet. ## D-077 — `fleet reply` refuses a recipient at parse, and the discriminator is the argv element rather than the first word

- **What changed.** One match arm in `crates/fleetor-cli/src/main.rs` — `Command::Reply { text } => Op::Reply { text: reply_text(text)? }` — and the `reply_text` function it calls, which refuses when `text.first()` parses as a `PaneId` and otherwise returns `join(text)` exactly as before. **No verb was added, renamed or removed.** `crates/fleetor-core/src/brief.rs` (where `VERBS` lives), `crates/fleetor-core/src/wire.rs` (where `Op` lives), the clap `Command` enum, `prompts/orch.md` and `prompts/worker.md` are all byte-unchanged — `git diff` on the four files is empty and the only hunks in `main.rs` are at the match arm, at the new function, and in `mod tests`. `brief-cost` is **0**.
- **The defect is measured, and its shape is the reason it went unnoticed.** `Op::Reply { text }` has no recipient field, unlike `Op::Send { to, text }`, and `Command::Reply`'s `text` is `trailing_var_arg`. So `fleet reply worker-3 "Agreed — Rooftop Garden"` parses cleanly, prepends `worker-3` to the *message body*, and delivers the whole thing to whoever messaged the sender last. Nothing failed, so nothing was corrected. A 5m 40s run produced **nine** misdeliveries; two panes spent turns diagnosing "tangled cross-replies" and one re-sent three confirmations it had already sent. The panes were not being careless: `prompts/worker.md:23` teaches ``fleet reply "<text>"`` on the line *below* ``fleet send orch "<text>"``, and a name argument pattern-matched across. **The brief is correct and was not changed** — a verb whose only safe use requires the reader not to generalise from the line above it is the thing to fix, not the line.
- **The discriminator is the first argv element, not the first word of the joined string, and that is the whole of the care this needed.** `fleet reply worker-3 "Agreed"` arrives as `["worker-3", "Agreed"]` and is refused; `fleet reply "worker-3 said the annex is out"` arrives as one element that is not a pane name and goes through untouched. A pane must be able to open a message with a peer's name — quoting one, reporting on one, arguing with one — and **replacing a silent misroute with a silent refusal would be the worse trade of the two.** The first-word reading was mutation-checked, not merely avoided: swapping `text.first()` for `join(text).split_whitespace().next()` fails two tests.
- **It asks `PaneId::from_str` rather than matching spellings of its own**, so it is exactly as wide as `fleet send`'s recipient and cannot drift from it: `orch`, `orchestrator`, `lead`, `o`, `operator`, `critic`, the out-of-fleet grader's own name, and every worker as `3` / `w3` / `worker3` / `worker-3`, all case-insensitive and trimmed. `self` is deliberately *not* caught, because `fleet send self` is not a thing — only `fleet cmd` resolves that word, in `target()` — so a reply may start with it. A first token beginning with `-` never reaches the check at all; clap rejects it first, `-1` included.
- **Tier 1.4 holds because it refuses at parse, and that is not a matter of degree.** `reply_text` runs inside `run()`'s `let op = match cli.command`, in the same position as `Command::Send`'s `pane.parse::<PaneId>()` — **before** the tokio runtime is built, before `UnixTransport::new(socket()?)`, before `Client::connect`, before an `Op` exists. Nothing between a `fleet send` and a pty gained the ability to delay, refuse, reorder, drop or alter anything; this is the same shape of failure `fleet send worker-9` produces today. A check downstream of the socket would have been the wrong implementation of the same sentence.
- **WP-15's Tier 1.4 grep caught this ticket while it was being written**, which is worth recording because it is the second time (D-076 records the first): `the_delivery_path_cannot_see_the_evaluator` failed on two test-data literals in `main.rs`. The literals moved to `crates/fleetor-cli/tests/reply_recipient.rs`, which is not a file a message passes through; the grep was not touched. **The refusal message echoes back only the word the pane itself typed**, so it teaches no name to a pane that did not already have one — the same property `ParsePaneIdError` keeps by listing the fleet's names and nothing else.
- **What would reverse it.** A measured case of a pane wanting to send a one-token message that is exactly a pane name (`fleet reply orch`, `fleet reply 3`) — those are refused today and the refusal is the cost of the rule, unmeasured. Or a recipient field arriving on `Op::Reply`, at which point the refusal becomes a redirect and this entry is superseded rather than amended.

## D-078 — `fleet broadcast` refuses a recipient too, and the two message verbs move together

- **What changed.** `Command::Broadcast` routes through a new `broadcast_text`, the twin of D-077's `reply_text`: if the first argv element parses as a `PaneId`, it refuses at parse rather than gluing the name onto the body. Both verbs ask `PaneId::from_str` rather than matching spellings, so neither can drift from `fleet send`'s recipient or from each other — pinned by `broadcast_and_reply_refuse_exactly_the_same_set_of_names`, which asserts the two verbs agree on twenty candidates.
- **The severity is *not* D-077's, and the entry says so rather than borrowing its evidence.** A misaddressed `reply` is a misroute — the wrong pane gets the message and the right one never does, which is the measured defect: nine silent misdeliveries in one 5m 40s run. A `broadcast` has no recipient to get wrong; everyone receives it either way, so the unfixed cost is a stray leading word. **No measurement says it has ever happened.** It is caught because the *other* reading is expensive: `fleet broadcast worker-3 "…"` from a pane that meant to reach one peer tells all four, which `prompts/worker.md` already calls "almost never the right call".
- **A false positive is created here that D-077 does not have, and it was accepted deliberately.** A broadcast plausibly opens with a peer's name — "worker-3 is blocked on the schema" is an ordinary announcement, and a pane typing it unquoted is now refused for writing correct prose. A reply has no such shape in practice. **So the refusal names both remedies** — send to one pane, or quote the message — instead of assuming which was meant, and either correction is one line in the turn the pane is already in. Rejected: refusing with only `fleet send`'s spelling, which would tell a pane making a legitimate announcement to do the one thing it did not want.
- **Tier 1.4 holds for the same reason D-077's does.** The check runs in `run()`'s `let op = match cli.command` block, where `Command::Send`'s own `pane.parse::<PaneId>()` runs — before the runtime is built, before the socket is dialled, before any `Op` exists. Nothing between a `fleet send` and a pty gained the ability to refuse anything.
- **No verb moved.** `VERBS`, the clap `Command` enum, `Op`, `prompts/orch.md` and `prompts/worker.md` are byte-unchanged; the briefs already teach `fleet broadcast "<text>"` with quotes, so no pane is taught anything new.
- **What would reverse it.** A measured case of a pane wanting to broadcast a message whose first word is a bare pane name often enough that quoting is a real cost. Nothing observed suggests it.
- **Verified.** 226 workspace tests green, up from 222 at `97bfd43` — four added, none changed or deleted.
