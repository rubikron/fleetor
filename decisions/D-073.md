id: D-073
title: "the evaluator is a view in the rail, not a second window (supersedes the window half of D-066)"
phase: "meta"
status: alive
---

- **What changed.** The evaluator's terminal moved out of its own OS window and into the main window's rail, beside Terminals, Messages, Tasks, Activity and History, present only in dev mode. Four things went with the window: the `?window=evaluator` branch in `main.tsx` that chose which React root to mount (and `ui/src/EvaluatorWindow.tsx`, the root it chose), the `CloseRequested` interception in `lib.rs` that turned a close into a hide, the `"evaluator"` label in `capabilities/default.json`, and `fleet::open_evaluator_window` together with `evaluator::WINDOW_LABEL`. `wake_evaluator` keeps every line that decides *whether* there should be an evaluator — readiness, the answer key, the notices — and its tail now emits `evaluator://wake` to the one webview instead of building a window.
- **Why the default lost, and it is the same argument D-066 made, finished.** D-066's stated justification was that mounting `App` twice would give the app two webviews racing for one fleet. That is a true claim about the *root* and never was an argument for a *window*: it says the second window must not be a second `App`, not that a second window must exist. A view inside the single root has no race to lose, because there is no second webview. What the window cost was real — a close handler that could not tell which window it was closing (and for a while tore down all six ptys either way), capability scoping whose failure mode is silent, and a second root that had to re-derive the theme.
- **§7 rule 5 did not move; the level it is enforced at did.** The window survived being closed because the close was intercepted. The view survives being switched away from because it is hidden with `.is-hidden`, which is the mechanism every other view has always used. The terminal is mounted from launch and hidden until the wake, rather than mounted at the wake — both survive a switch, but only this one has no mount-once latch for a later session to reason about wrongly, and `TerminalPane`'s existing `started` prop (the start gate's own spawn gate) is what keeps a pty from existing before the handoff. The evaluator view hides three things and unmounts none, and the test asserts that as a count.
- **The wake is a new event rather than the `Handoff` the webview already receives.** Most handoffs must wake nothing — the mode is off, no grader is compiled in, or the target is not a prepared mission — and only Rust knows which. Deriving the wake frontend-side from `FleetEvent::Handoff` would have spawned an evaluator the readiness check had just refused. `evaluator://wake` carries that decision and nothing else. It is emitted from the same place `open_evaluator_window` was called, so the wake stayed downstream of the log: `spawn_evaluator_wake` is untouched, and `the_wake_is_a_bus_subscriber_and_not_something_the_hub_calls` is untouched and green.
- **What of D-066 survives, and it is most of it.** `PaneId::Evaluator` as a sixth variant in no enumeration; `is_fleet_member()` and the roster filter; the veil and both its tripwires; the `devmode` cargo feature and the brief compiled in from a separate repo through `OUT_DIR` with no override path; the three readiness conditions and their sentences; laying the live run out read-only under `~/.fleetor/dev/`; the config dir kept outside `_shell/pane-config/`; the narrowed guardrail roots and `--permission-mode auto`. **Only the window half is superseded.** D-066 also recorded the two bugs the second window exposed: the `channel_key` fix stands, and the `on_window_event` fix is now moot rather than reverted, because a single-window app has one meaning for a close.
- **The rail's ordering is load-bearing and cost one line.** The evaluator sits last among the workspace rows, after History and before Settings, because it is the only row that appears and disappears — putting it anywhere else means turning dev mode on shifts every row beneath it and the rail the operator has learned moves under them. Turning dev mode *off* while the evaluator view is selected is corrected in `App.tsx` rather than prevented, and on `=== false` rather than `!== true`, so nothing bounces off the view while the backend has not yet answered.
- **The view-restore list was already wrong, and about a view that predates this ticket.** `usePersistedNav.ts`'s `VIEWS` omitted **`history`** from the day History shipped: selecting it and relaunching parsed `"history"` back out of localStorage, failed `isValidView`, and landed on Terminals having said nothing — the identical fallback a genuinely corrupt value gets, which is why it survived a release. Both `history` and `evaluator` are on the list now, and `src-tauri/tests/views.rs` reads the `View` union in `Sidebar.tsx` and the `VIEWS` array in `usePersistedNav.ts` and fails, naming the missing views in both directions, if they stop agreeing. A Rust source-reading tripwire rather than a frontend test because the arc rules a frontend runner out by name; this is the one exception it reserved.
- **Two existing tests changed their letter and are stricter for it** (the move D-066 itself made). `the_evaluator_windows_terminal_is_never_conditionally_rendered` read a file this ticket deletes; its successor reads the evaluator's stage-view block in `App.tsx` and additionally asserts there is **no start control** (no `<button>`, no `onClick`) and that the stale `review` label is gone — two claims the old test could not make. `closing_the_evaluator_window_hides_it_and_does_not_kill_the_fleet` asserted the label branch, the close interception and the capability scoping; its successor asserts all three are **absent**, plus that no `WebviewWindowBuilder` or `get_webview_window` survives in `fleet.rs`, that `WINDOW_LABEL` is deleted rather than kept, and that `main.tsx` has no root branch. Net for the file: 8 tests to 9, and no assertion was dropped without a stronger one taking its place.
- **The `review` label is retired (D7).** The terminal was labelled `review`, which collides with peer review — the one thing about review the briefs actually teach a worker. It reads `evaluator` now. This is UI chrome the operator sees and no part of any brief, so the veil is untouched; `no_pane_is_briefed_about_the_evaluator` scans prompts and `brief.rs`, not `ui/`.
- **What would reverse it.** A measurement showing the operator genuinely needs the retro and the fleet on screen at once — which is a second window again, but then for a stated reason rather than an inherited one, and it would need its own root for D-066's original argument, which remains correct. Or the evaluator growing chrome that does not fit a stage view. Neither is evidence anyone has.
- **Verified:** **213** workspace tests green, unchanged, and no file under `crates/` was touched. **180** shell tests green, up from 176: 145 lib (unchanged), 4 dev-mode (unchanged), **9** evaluator (was 8), 11 real-pty (unchanged), **3 new in `tests/views.rs`**, 8 write-guardrail (unchanged). `cargo test --features devmode` green at 180 as well. `cargo build` produces no warnings. `npm run build` (`tsc --noEmit && vite build`) clean. The new tripwire was checked against the bug it exists for rather than only asserted: deleting `"history"` from `VIEWS` fails `the_rail_and_the_restore_list_name_the_same_views` and `history_is_restorable_which_it_was_not_before_d073`, printing both lists and naming `history`, and the file was restored and re-run green.
- **Not verified:** the frontend has no test runner and this arc adds none, so **nothing about the view's runtime behaviour is tested**: that the rail entry appears and disappears with dev mode, that the terminal and its scrollback survive a switch away and back, that the pre-handoff prose gives way to a live terminal on `evaluator://wake`, and that turning dev mode off while on the view moves the operator to Terminals — all four are source-read at best and are in the operator's by-hand list. No fleet has been started, so no handoff has fired the new event, no evaluator has reached a prompt in a view, and no retro has happened — the same gap D-062, D-065, D-066 and D-069 each record. `rustfmt` is not installed on this machine, so formatting was not checked. No live spend.
