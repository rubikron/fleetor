title: "Phase 4h: the shell types worker→lead traffic into the orchestrator TUI (a free pump owns lead ingestion; the app owns the pty, so the \"human owns stdin\" limit doesn't bind)"

- **What:** Fleet messaging was push one way, pull the other — lead→worker mail is *delivered* into a worker's context (D-026's three paths), but worker→lead traffic (`notify_lead`/`ask_lead`) only sat in the hub's in-memory lead-event queue until the lead *polled* `await_events`. In the shell the lead is the operator's real `claude` TUI, so that meant the Opus burning turns to poll — or missing traffic. This adds the *incoming* half: a **lead inbox pump** in `src-tauri/src/fleet.rs` — a plain `Party::Lead` socket client (not the Opus) that long-polls `await_events` and emits each item as a `lead://inject` Tauri event; `TerminalPane.tsx` queues those and, once the session is live and the operator has been quiet for `INJECT_IDLE_MS`, types the next one into the pty via the existing `pty_write` with a trailing `\r` — an **auto-submitted turn**. Questions are framed with their `event_id` so the Opus can `reply` straight from the injected line (`render_lead_event`, unit-tested).
- **Why:** handoff §5 assumed the lead "can't be injected into because the human owns its stdin" — true for a plain terminal, **false here**: the Tauri backend owns the pty master writer (`pty.rs` `Session.writer`). So the platform can genuinely type into the orchestrator's TUI, closing the messaging asymmetry. The pump does the *ingestion* for free (a socket client, zero Opus tokens); the Opus spends only when it reacts to an injected turn — the token-waste fix for the poll loop. Affordable per-turn because workers are prompted to message the lead only *when required* (the tool framing already makes `ask_lead` the sole blocking op and `notify_lead` meaningful-progress, not chatter), so volume is low and no batching is needed. The idle guard (a keystroke-recency heuristic — the first input-activity signal in the pane) keeps an injection from clobbering a line the operator is composing.
- **Benign single-consumer race (documented):** the pump and the operator's own `claude` lead are both `Party::Lead` against the hub's single-consumer `lead_events` queue. Because the pump polls continuously it is the de-facto consumer (events reach the Opus via injection); the rare event the operator's lead drains itself arrives via that tool result instead — no loss, no duplicate. So `await_events`/`inbox` stay on the lead face as a harmless manual fallback and **nothing in `crates/` changes** — the whole feature is `src-tauri` + the React pane.
- **Verified (no live spend):** `render_lead_event` unit tests — a notice renders as one sender-attributed `[fleet · worker-N] …` line; a question carries its `event_id` + reply hint + options. `cargo test`/`cargo check` on `src-tauri` clean (4 tests, 0 warnings); `tsc --noEmit && vite build` clean. The injection UX (message types itself in as a turn, only when idle, multiples queue in order) is the operator's visual gate, as with prior shell phases.
- **Deferred (stated):** a precise "is the operator typing" model (v1 is keystroke-recency, so a rare mid-flush race can still interleave); retiring the lead's `await_events`/`inbox` tools (kept as fallback); enforcing sparse worker messaging in the worker prompt (a complementary follow-up — the pump injects whatever arrives); batched/coalesced injection (unnecessary at low volume).
