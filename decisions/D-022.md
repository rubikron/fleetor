- **What:** The observable shell. `src-tauri` gains plain **path deps** on the proven crates (`fleetor-core/-db/-server/-ipc`) and a new `fleet` module that, once per app, opens the SQLite store, wraps it in the 4c `BroadcastStore`, binds the hub on the fleet socket (idle — no clients until 4e-2), and spawns an `EventFollower` that pushes every appended `(seq, FleetEvent)` to the webview as the `fleet://event` Tauri event. Invoke commands: `fleet_bootstrap` (idempotent start → board snapshot), `fleet_board` (refetch), `fleet_assign` (a real store write that streams back), `fleet_demo` (kick the stand-in). The frontend migrates from the 0.5 plain-TS terminal to **React** (`@vitejs/plugin-react`, `jsx: react-jsx`): a `useFleet` hook seeds the board from the snapshot and reduces the event stream into the dashboard band + feed; components render the top bar, navigation spine, always-visible band (orchestrator + 4 workers + queue), ticket board, live event feed, and the retained pty terminal pane. The 0.5 pty bridge (`pty.rs`, `TerminalPane`) is carried over unchanged.
- **Why:** 4e is the biggest, first product-shape *and* real-token phase, so it was split at the token line (operator's call): 4e-1 builds everything observable with **zero token spend**, 4e-2 embeds the real `claude` lead and runs the live Opus gate. The event path is the real 4c seam — `BroadcastStore` → `follow(0)` → `fleet://event` — just terminating in React instead of `println!`, so 4e-2 changes nothing about how the UI observes; it only swaps what *drives* the store. `src-tauri` stays thin (BUILDING §3): all logic remains in `crates/`, the shell adds window + wiring only. The board is refetched from `store.tickets()` on every `ticket-state` event rather than reduced from event fields, because ticket **metadata** (title, files) isn't in the event — the store stays the board's source of truth, events only trigger the refetch. The hub is bound but idle now so 4e-2's lead/worker shims connect with no backend change; a bind failure degrades gracefully (the observable shell doesn't depend on it). Path deps (not a workspace merge) keep tauri's heavy tree out of the clean crates lockfile, as the 0.5 standalone `[workspace]` already intended.
- **The `demo` stand-in (stated, not silent — BUILDING §9):** `fleet::demo` is a pure `plan()` (a `Vec<DemoStep>`: ticket moves, worker states, tool calls, mail, gate/review verdicts, a report, notices) applied through the same store on a timer — it animates the whole shell with **no child processes and no tokens**. It is explicitly a 4e-1 harness: 4e-2 deletes it and lets the real orchestrator pty drive `run_dynamic_fleet` over the hub already bound here.
- **Deferred to 4e-2:** embedding `claude` as `Party::Lead` (the pane is retained but runs a plain idle session, not yet the wired lead); the live **Opus-in-the-seat** confirmation gate; and real repo/branch/gate/cost values in the top bar (static placeholders now).
- **Verified:** `cargo check` + the `fleet::demo` unit test (`demo_plan_drives_the_store_to_the_scripted_board` — every step appends exactly one event; the board ends T-101 `Done`, T-102 `InReview`) prove the backend integration and that the stand-in exercises the real store paths; `tsc --noEmit && vite build` (43 modules) proves the React shell typechecks and bundles against the wire types. The 55 crate tests are untouched (no `crates/` changes). The **live visual check** — `npm run tauri dev`: band animates, board fills, feed streams on "Run demo lifecycle" — is the operator-run gate for 4e-1, like the 0.5 pty visual gate.
- **Reverses if:** the shell should subscribe to a *daemon* fleet server over the socket instead of hosting it in-process (then `fleet.rs` connects a follower over IPC rather than owning the store) — the `fleet://event` contract to the webview is unchanged either way; or if React proves heavier than the thin UI needs (the components are small and framework-swappable, BUILDING §2).
