---
id: D-048
title: "WP-06: the worktrees stay, because the object database was already shared"
phase: "WP-06"
status: alive
---

- **The default that lost was "peer review needs a shared checkout."** The worktree reconsideration was open since the fleet grew a review phase: four workers in four checkouts looked like the thing standing between a reviewer and a peer's code. It is the opposite. `git worktree add -B` gives each worker a **private** `git-dir` — its own `HEAD` and index, which is the whole reason four workers can commit concurrently — while `--git-common-dir` points every one of them at **one** object store. A peer's commit is already local; `git log --oneline HEAD..fleet/worker-3` and `git diff HEAD...fleet/worker-3` work from the reviewer's own directory with no fetch, no remote and no second checkout. Validated live against plain git rather than argued: `docs/peer-review-notes.md` is the transcript, built with the exact command `fleet.rs::ensure_worktree` runs, with both branches genuinely diverged.
- **This is what keeps Tier 1.7 out of the way.** The alternative designs both cost something the builder is not allowed to spend: a shared checkout collapses review semantics (one working tree reported five times — a reviewer looking at its own edits), and cross-worktree access widens auto-approve past a worker's own worktree, which `building.md` §9.2 puts above the builder. The arrangement that was already there needs neither. Read-only is worth stating precisely, though: it is auto-approve's scope plus a brief rule, **not** a git guarantee — nothing in git stops a worker writing into a peer's directory, and calling this sandboxing would be the L3 failure in a new costume.
- **Three dots, and the reason travels with it.** Two-dot diff renders everything the *reviewer* has committed since the fork as a deletion by the *author* — reproduced in the transcript, where worker-2 reading worker-1 two-dot sees its own `lexer.rs` as deleted. A reviewer opening with "you deleted my lexer" is wrong in a way a peer cannot easily argue back from. `prompts/worker.md` teaches the three-dot form *with* the reason, and both are pinned as literals, because the rule without the reason is what a rewrite deletes first.
- **Merging is a worktree, not a checkout.** `orch` merges reviewed branches into `fleet/integration` from `~/.fleetor/_shell/worktrees/integration`, so it never moves the branch the operator is standing on. Verified: after two `--no-ff` merges the target is still on `master` at its original commit with zero changed files, and `rm -rf` + `git worktree prune` leaves the repo clean minus `fleet/*` — exactly the carve-out Tier 1.1 already names. Never trunk; the operator merges trunk themselves.
- **The fallback got louder rather than safer.** When the target is not a git repo, `worker_cwd` still shares the target directory — a fleet that refuses to start over a worktree is worse than one sharing a checkout. But WP-06 raised what that costs: there are no per-worker branches, so `git diff fleet/worker-N` has nothing to compare and review stops meaning anything. The notice now says that in words and says what to do about it (`treat a reviewed done as unreviewed`), pinned by a test — an operator reading "sharing the target checkout instead" had no way to know the review step had quietly become theatre.
- **What would reverse it.** A git version or filesystem where worktrees stop sharing objects (nothing suggests one), or live evidence from WP-09 that workers cannot use branch review from their own directory — which would be a prompt problem before it was an architecture one. Per-task worktrees remain out of scope and are still on WP-05's tripwire list.
