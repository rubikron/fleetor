---
id: D-020
title: "Phase 4c: the live event bus is a `Store` decorator (`BroadcastStore`) in `fleetor-server`, not a new emit path; persist-then-publish; lag recovers from the DB"
phase: "4c"
status: alive
---

- **What:** The UI's live event feed (README roadmap "4c") is delivered by wrapping the [`Store`] seam. `fleetor-server::bus` adds `EventBus` (a `tokio::sync::broadcast` fan-out of `(seq, FleetEvent)`), `BroadcastStore` (a `Store` decorator that delegates every method and, right after a successful `append_event`, publishes the row's real `seq`), and `EventFollower` (`EventBus::follow(store, after)` → an async `next()` that yields the DB snapshot then live events, gap-free and dup-free). Wrap the inner store once and **both** emitters — the sync supervisor (`supervisor::emit`) and the async hub (`Hub::emit`) — publish for free; neither loop is touched. `fleetor run` now wraps its store and prints events live via a follower task (replacing the post-hoc `print_event_tail` dump). Capacity is `BUS_CAPACITY = 1024`.
- **Why:** Every event already funnels through the one chokepoint `Store::append_event`; a decorator there captures all of them with zero change to the proven Phase 1–4b code (KISS + reversible — unwrap and you have a plain store, BUILDING §8). The bus lives in `fleetor-server`, not `fleetor-core`, because it needs `tokio` and core must stay tokio-free (D-012). **Persist-then-publish** keeps the DB the single source of truth (matching the 4b "shared, persisted log" bridge, D-019): publish is best-effort (no subscribers = no-op; the event is already durable), and a follower that joins late or lags the bounded ring recovers by re-reading `events_since(cursor)` — the channel only *accelerates* delivery, it never becomes a second source of truth. `broadcast::Sender::send` is sync and runtime-free, so the sync supervisor thread publishes without a handle to the runtime. This is the substrate 4d (orchestrator feed) and 4e (Tauri event pump) consume.
- **Verified:** `event_bus.rs` (4 tests) — a subscriber live for a whole `run_fleet` receives *exactly* the persisted log (same seqs, strictly increasing, no gaps/dupes); a late subscriber gets the full DB history then live events seamlessly across the snapshot boundary; a follower flooded past `BUS_CAPACITY` without reading recovers **every** event from the DB, contiguous and in order; and a bare `EventBus` fans one publish to all subscribers. Full suite 48 tests, 0 warnings. No live-CC spend (deterministic at the store/bus layer).
- **Reverses if:** a second transport for the feed never appears and `broadcast` proves heavier than needed — collapse to a plain `Vec<Sender>` or a single mpsc; or if per-event fan-out is too coarse for the UI, batch in the follower. If the Tauri app (4e) would rather subscribe from inside the app process than through the CLI, `BroadcastStore::bus()`/`follow()` are already the public handles it consumes.
