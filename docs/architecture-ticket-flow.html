FLEETOR · architecture reference

One ticket through three layers

The lifecycle of a single ticket, tracing which of the three layers each step belongs to. The point to keep straight: messaging is how agents coordinate, the event bus is one-way telemetry to the human's UI (agents never read it), and context strategy is how each agent's working context is kept clean. They are separate systems that happen to share the same event log.

Layers Context strategy — keep each agent's context clean Messaging — agent ↔ agent coordination Telemetry (event bus) — server → UI, read-only
Channels stdin/stdout (NDJSON) MCP → socket → hub Stop hook await_events event log → bus
The telemetry rail runs under every step. Each event below is written by Store::append_event, then BroadcastStore publishes it to every EventFollower — the live feed the UI renders (Phase 4c). Persist first, publish second; the DB stays the single source of truth. No worker or orchestrator subscribes to this.

The three layers, side by side

Messaging

How teammates talk while working. Carries facts that change someone's work — not status narration, not context dumps.

  • ask_lead — the one worker→lead blocking call
  • reply / send — lead answers / steers
  • dm / broadcast — async peer mail
  • report / notify_lead — completion & progress

Transport: the worker's MCP shim → unix socket → hub. Async everywhere except ask_lead.

Telemetry — the event bus

A one-way feed of "what just happened" so the UI can render live. Built in Phase 4c as a decorator on the persistence path.

  • BroadcastStore — wraps Store, publishes each append
  • EventBus — broadcast fan-out of (seq, event)
  • EventFollower — snapshot + live, gap-free

Agents never read it. It is telemetry for the human, not a message channel.

Context strategy

Keeps each agent's working context clean — the opposite of "stream context through an inbox".

  • Minimal ticket — AC, owned files, contracts. Not a file dump.
  • Workers explore — grep/read the repo themselves
  • Session = ticket — respawn is the wipe; no /clear
  • Knowledge store — path-scoped notes auto-inject (Phase 5)

Small tickets fight context rot, not capacity — Flash's 1M window would fit everything; attention degrades first.

Invariants this flow must uphold (Tier 1 — ask max before violating)

  • blocking Blocking calls point worker→lead only (ask_lead). No worker↔worker blocking primitive exists — it would deadlock a 4-agent fleet.
  • session Session lifetime = ticket lifetime. Replacing the process is the only context wipe.
  • blast radius A worker writes only inside its worktree + declared files (PreToolUse guard). Auto-approve never widens past that.
  • merge Merges land on an integration branch, never trunk. The human opens the real PR by hand.
  • source of truth Persist-then-publish: the DB is authoritative; the event bus only accelerates delivery, never becomes a second source.
  • real CC Every agent is a real, unmodified Claude Code process. The harness lives around it — never forks or patches it.
  • repo CLAUDE.md is read for guidance, never written. What workers learn goes to fleet-owned knowledge, merged only after review.

What's built vs. pending (audit against reality)

Built (Phases 1–4e-2)
  • Supervisor loop: spawn → assign → turn-end → report
  • Hub + socket: ask_lead/reply, dm/broadcast, Stop-hook mail
  • Quality loop: gate → auto-bounce → peer review
  • Report-over-MCP as the primary done-signal
  • Live event bus (this doc's telemetry rail)
  • Lead MCP face + dynamic assign: the orchestrator dispatches over the hub, workers spawn on demand
  • The React shell: fleet server embedded in Tauri, fleet://event → dashboard band + board + live feed
  • The real lead in the pty: claude spawns as FLEETOR_ROLE=lead wired to the dynamic hub; workers spawn per assign via a backend-selectable factory (4e-2)
Stand-in today
  • Wired, zero live spend: the lead pty, the dynamic hub, and the worker factory are all connected, but the first live Opus + worker run is an operator-triggered gate (start-session confirm) — not yet exercised
  • Workers default to fake (a free proof path); real DeepSeek Flash rides behind FLEETOR_WORKER_BACKEND=real
  • No cost/token metering in the top bar yet — shown as absent, not faked
  • Merge approval / diff viewer live in the CLI for now
Not yet
  • Knowledge store + review queue + auto-inject — Phase 5
  • interrupt / worker_restart — yank or respawn a busy worker
  • Idle→stdin & opportunistic-piggyback mail paths (D-015)
  • Profiles (per-slot skill/tool/model diffs)
  • Gate discovery (scan CLAUDE.md/package.json) — config today
