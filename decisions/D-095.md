---
id: D-095
title: "a reopened run comes back on the harness, model and credential it recorded, not on what the gate holds"
phase: "WP-27"
status: alive
---

- **What.** Reopening a run places each seat from the lineage's manifest record (`harness`, `model`, and now `credential`) instead of the gate's current selection. The gate's selection is left untouched for the next new fleet. The recorded seats are checked against this machine's logins in `run_reopen`, before teardown (R8). `lineage_panes` now prefers a record that names a session over a nearer one that does not, amending R20's "nearest record wins".
- **Why.** The session id came from the manifest and the harness from the gate, so a codex run reopened with the gate on Claude Code ran `claude --resume <codex id>` — "No conversation found" on all five panes (2026-10-02, lineage `2026-09-13T00-03-27Z`). That reopen then recorded `claude-code` with no session for every seat, which under R20 hid the codex sessions from every later reopen; the amended rule is what un-hides them.
- **Not verified.** Driven through unit tests only (`recorded_seats_replace_the_gates_pick`, `a_seat_reopened_on_the_wrong_harness_still_resolves_to_what_it_ran`), not through a live codex reopen — that is still WP-29's open test. A run recorded before this entry carries no credential, so its seats keep the gate's.
- **Reverses if.** The operator wants a reopen to be able to change harness deliberately — which would need a fresh session for that seat, not a resume.
