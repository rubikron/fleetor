---
id: D-078
title: "`fleet broadcast` refuses a recipient too, and the two message verbs move together"
phase: "meta"
status: alive
---

- **What changed.** `Command::Broadcast` routes through a new `broadcast_text`, the twin of D-077's `reply_text`: if the first argv element parses as a `PaneId`, it refuses at parse rather than gluing the name onto the body. Both verbs ask `PaneId::from_str` rather than matching spellings, so neither can drift from `fleet send`'s recipient or from each other — pinned by `broadcast_and_reply_refuse_exactly_the_same_set_of_names`, which asserts the two verbs agree on twenty candidates.
- **The severity is *not* D-077's, and the entry says so rather than borrowing its evidence.** A misaddressed `reply` is a misroute — the wrong pane gets the message and the right one never does, which is the measured defect: nine silent misdeliveries in one 5m 40s run. A `broadcast` has no recipient to get wrong; everyone receives it either way, so the unfixed cost is a stray leading word. **No measurement says it has ever happened.** It is caught because the *other* reading is expensive: `fleet broadcast worker-3 "…"` from a pane that meant to reach one peer tells all four, which `prompts/worker.md` already calls "almost never the right call".
- **A false positive is created here that D-077 does not have, and it was accepted deliberately.** A broadcast plausibly opens with a peer's name — "worker-3 is blocked on the schema" is an ordinary announcement, and a pane typing it unquoted is now refused for writing correct prose. A reply has no such shape in practice. **So the refusal names both remedies** — send to one pane, or quote the message — instead of assuming which was meant, and either correction is one line in the turn the pane is already in. Rejected: refusing with only `fleet send`'s spelling, which would tell a pane making a legitimate announcement to do the one thing it did not want.
- **Tier 1.4 holds for the same reason D-077's does.** The check runs in `run()`'s `let op = match cli.command` block, where `Command::Send`'s own `pane.parse::<PaneId>()` runs — before the runtime is built, before the socket is dialled, before any `Op` exists. Nothing between a `fleet send` and a pty gained the ability to refuse anything.
- **No verb moved.** `VERBS`, the clap `Command` enum, `Op`, `prompts/orch.md` and `prompts/worker.md` are byte-unchanged; the briefs already teach `fleet broadcast "<text>"` with quotes, so no pane is taught anything new.
- **What would reverse it.** A measured case of a pane wanting to broadcast a message whose first word is a bare pane name often enough that quoting is a real cost. Nothing observed suggests it.
- **Verified.** 226 workspace tests green, up from 222 at `97bfd43` — four added, none changed or deleted. Refusal and pass-through both exercised against the built binary through `cargo run`, not only in-process: `broadcast worker-3 is blocked`, `broadcast 3 hi` and `broadcast orch done` refuse; `broadcast "worker-3 is blocked on the schema"` and `broadcast heads up worker-3` go through. `cargo clippy --all-targets --workspace` output is byte-identical before and after (the same three pre-existing `fleetor-core` lib-test warnings). `cargo build` clean.
- **Not verified.** No fleet has been started since this landed, so no pane has met the refusal in a live run. The claim that broadcasting to four panes what belonged in one message is the expensive error is an argument from the brief's own wording, not a measurement — unlike D-077's nine misdeliveries, which were counted.
