---
id: D-032
title: "Delivery-path audit: only a dead pane may refuse a message, and membership has exactly one source of truth"
phase: "1"
status: alive
---

- **What:** Two guards removed from the send path, both introduced in Phase 1 and both capable of silently refusing a healthy pane. (1) `PaneState` no longer gates delivery on `Live`. `is_live()` stays as a *display* predicate for the roster and band; the delivery path uses the new `accepts_input()` — `!Dead`. (2) `pane_send` no longer validates its target against `HubConfig.slots`, and `pane_broadcast` takes its targets from the app's roster rather than config. `roster_ids()` is gone; `app_roster()` is the single read of fleet membership.
- **Why (1):** nothing tells us when `claude` reaches its prompt. `Spawning` is a *guess about a running process*, so gating sends on `Live` means a perfectly healthy pane refuses every message until the guess flips — and if the flip is never implemented, or is implemented against a banner string that changes next `claude` release, the fleet goes mute while reporting exactly the error it was designed to report. That is L1's shape: it looks like it works and it doesn't. Writing into a still-booting pty is buffered by the kernel and read when the TUI starts reading; that is a failure we can live with, whereas refusing a live pane is not. The asymmetry decides it — a delivery gate should only fire on a fact (the process is gone), never on an inference.
- **Why (2):** `HubConfig.slots` and the pty registry were two answers to "who is in this fleet", and they can disagree — a pane the app is running would have been rejected as `unknown pane worker-4` with no way for the model to correct it, and a config entry never spawned would have looked reachable. The machine holding the ptys is the only one that knows, so it is now the only one asked. Config is not allowed to veto it (tested: a pane outside `SLOTS` is reachable if the app runs it). The self-send check stays, because it compares the sender to itself and cannot be wrong.
- **Verified:** `cargo test --workspace` — 98 tests, 24 binaries, 0 failures, 0 warnings; `cargo check` clean in `src-tauri`. New/changed tests: a spawning pane accepts while a dead one is rejected and logged; membership is the app's answer; a pane outside the hub config is still reachable.
- **Standing rule this establishes:** nothing may sit between `fleet send` and the pty that can refuse on an inference, a prediction, or a second copy of state. The remaining refusals in the path are the app saying a process is gone, the app being absent, and the 2s ack ceiling — which protects the caller (a wedged app would otherwise park the agent's Bash call forever) rather than policing it.
