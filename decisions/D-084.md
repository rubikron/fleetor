id: D-084
title: "a target that is not a git repository is `git init`-ed when its first worker starts, instead of sharing one checkout"
phase: "meta"
status: alive
---

- **What.** Operator's call, 2026-09-11, after a live fleet on `~/harness/harness-test` (no `.git`) sent all four workers into the shared checkout. Placing a worker now runs `git init`, `git add -A` and an initial commit (`fleet: initial commit`, authored FLEETOR, empty if the directory is) when the target is not inside any repository, then creates the worktree as usual; the feed says it happened and how many files went in. The first worker does it, the rest find a repository, and a restart does nothing new.
- **This overrides two recorded positions, knowingly.** Tier 1.1 ("the operator's own directories are not reached into") — the testbed was the only directory FLEETOR initialized, because FLEETOR owns it; this reaches into the operator's own. And D-048's "a fleet that refuses to start over a worktree is worse than one sharing a checkout" stays true but now applies only to a target that *cannot* be initialized.
- **Everything is committed, not an empty commit.** An empty first commit would give every worktree none of the project's files, which is the fallback's failure in another shape. The cost, accepted: whatever is in the directory — including secrets or large files, minus anything an existing `.gitignore` excludes — lands in the local object database, and in each worktree's checkout.
- **Never the operator's home directory or `/`.** `git add -A` there would commit a whole machine; those fall back to the shared checkout with the existing warning. A repository with no commits (`stockTrading`) is still a repository and is left alone.
