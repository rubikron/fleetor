---
id: D-069
title: "the Fence learns about rustup: both toolchain homes are the fleet's own"
phase: "meta"
status: alive
---

- **What changed.** A worker is now launched with `CARGO_HOME=~/.fleetor/_shell/cargo` and `RUSTUP_HOME=~/.fleetor/_shell/rustup`, plus one PATH rung (`_shell/cargo/bin`) holding eight shims symlinked to the operator's real `rustup` binary. `_shell/rustup` is a **mirror**: `settings.toml` copied, one symlink per installed toolchain into the operator's real `~/.rustup/toolchains/`. 4 KB seeded, against the 1.9 GB it points at. Both are seeded at spawn beside the private HOME (`spawn::seed_fleet_toolchain`), shared by all four workers, and set only when this machine actually has a rustup. `orch` gets neither — it is the operator's own `claude` (D-030).
- **This is D-052's own reversal condition, exercised as written.** D-052 reserved "live evidence that a worker legitimately needs … a version manager mid-task — the fix is scoping and seeding that tool's config for the worker specifically, **not** loosening `HOME` generally." `HOME` is untouched. `docs/notes/fence-notes.md` gains the 8th catalogue row and thirteen arms behind it.
- **The recorded bug was smaller than the real one.** WP-17 open question 1 recorded `rustup could not choose a version of cargo to run`. That measurement, and every arm in `examples/write-guardrail-spike/allowlist.sh`, ran with `PATH="$PATH"` — the operator's *login* PATH, which carries `~/.cargo/bin` — so it never asked whether a worker can find `cargo` at all. It cannot: `/opt/homebrew/bin/cargo` and `/usr/local/bin/cargo` are both absent, and those are the only two non-fleet rungs `worker_augmented_path` supplies. Under any PATH but an inherited login one the failure is `cargo: command not found`, exit 127, *before* rustup is reached. That is why the fix is a PATH rung and not two environment variables.
- **The plan going in was wrong about `RUSTUP_HOME`, and the spike won (`building.md` §4).** It proposed pointing `RUSTUP_HOME` at the operator's real `~/.rustup` on the grounds that it is read-only in practice, with the residual gap named. Arm 6b falsifies that: a `rust-toolchain.toml` naming an **uninstalled** channel — an ordinary thing for a repository to carry — downloads and installs it with no prompt, **35,981 files and ~1.2 GB into `~/.rustup`**. Arm 9b runs the identical pin against the mirror and the identical 35,981 files land under `_shell/` instead, 0 in the operator's. The mirror was listed in the plan as optional; it turned out to be free, and it is the difference between Tier 1.1 holding and not.
- **Why not point `CARGO_HOME` at the operator's `~/.cargo`** (the shape the old spike proved): it hands four auto-approving workers write access to `~/.cargo/bin`, which is on the *operator's* login PATH. Measured rather than reasoned — arm 7b runs `cargo install` under that setting and `~/.cargo/bin/spikey` appears. The write guardrail cannot refuse it, because `cargo install X` names no path (D-065's own measured limit). This is accident-shaped, which is the threat model this repo committed to.
- **Why not add `~/.cargo/bin` to the worker PATH:** that is the category of rung D-052 removed on purpose, and worse than the two it removed — the directory holds real binaries, not only shims (`cargo-create-tauri-app`, 1 MB, verified), and its contents change whenever the operator installs anything. The seeded rung exposes exactly the eight names the fleet enumerated, in a diff.
- **All eight shims or none, and that is measured.** Seeding `cargo` alone fails at `could not execute process 'rustc -vV' (never executed)` (arm 5a): cargo resolves through the proxy, then looks for `rustc` by name and finds nothing. With `cargo`, `rustc`, `rustup`, `rustdoc`, `rustfmt`, `cargo-fmt`, `cargo-clippy` and `clippy-driver` all linked, the build is clean (arm 5b).
- **One shared pair of directories, not one per worker.** Arm 8 runs two workers building concurrently against one `CARGO_HOME`: both exit 0, serializing on cargo's own package-cache lock. Per-worker `target/` already lives in each worktree, so a split would buy only a duplicated registry. Footprint after eight builds: 616 KB.
- **Absent rather than pointing at nothing.** With no rustup on the machine, neither variable is set and the PATH is byte-for-byte what it was. A `RUSTUP_HOME` naming a directory that does not exist makes rustup try to *install* there, which is a worse failure than today's. The operator is told once, on the Activity feed, beside the missing-`fleet`-binary warning.
- **No write-guardrail root was added, and there is now a test saying so.** `_shell` is already every pane's second root, so `_shell/cargo` and `_shell/rustup` were never refused. WP-17's instruction was "do not widen the allowlist to work around this"; it is honoured structurally, and `guardrail.rs::the_fleets_toolchain_homes_are_inside_a_pane_root_so_a_build_cache_write_is_never_refused` asserts `roots.len() == 2` so a later reader who reaches for `[fence] allow` finds out here.
- **An existing pin changed letter, and it is stricter.** `worker_path_drops_the_operator_home_rungs_orch_keeps_them` asserted `!worker_path.contains("/Users/operator")` — a substring sweep that held by luck. The new rung *is* under the operator's HOME, because that is where `~/.fleetor` lives. `worker_path_drops_every_operator_tool_rung_and_adds_only_the_fleets_own_cargo_bin` replaces it: every operator tool rung forbidden **by name**, `.cargo/bin` among them (the old test never named it), at most one rung under the operator's HOME and it must be the fleet's own, and orch's half byte-identical.
- **What this does not stop, named rather than implied.** The shims reach the operator's `rustup` binary by absolute path and the mirrored toolchains are absolute symlinks into `~/.rustup/toolchains/` — the Fence never claimed to stop absolute paths, and that is what makes a 4 KB mirror possible instead of a 1.9 GB copy. `rustup` itself is on a worker's PATH and must be (the shim set is all-or-nothing), so `rustup toolchain install` still works — it now writes into `_shell/rustup`. A worker can delete or corrupt the mirror, since `_shell` is inside its roots by design; the cost is a re-seed at the next start, never the operator's toolchain.
- **One inference is left standing and is labelled as one.** What a Finder-launched app inherits was **not** confirmed. The probe — a minimal `.app` launched through `open` — came back inconclusive: a sentinel variable proved `open` forwards the calling shell's environment, so it measured a terminal. `launchctl getenv PATH` is empty, which supports the inference; `ps eww | tr ' ' '\n' | grep ^PATH=` is actively wrong on this machine, because a PATH rung contains a space and the splitter truncates there. The fix does not depend on the inference: arm 2b shows the login-PATH case is broken too.
- **What would reverse it.** Evidence that a worker needs a toolchain the mirror does not expose, which is a wider seed and not a wider `HOME`. A cargo or rustup release that stops honouring `CARGO_HOME`/`RUSTUP_HOME`, which is upstream's own documented contract and would be loud. Or `_shell/rustup` growing enough to matter, whose answer is D-058's: a size column and an operator-driven delete, since a delete costs a re-download and never correctness.
- **Verified:** **176** shell tests green, up from 165 — 11 new: 10 in `spawn` (the D-069 block plus the rewritten PATH pin) and 1 in `guardrail`. 213 workspace tests green, unchanged; no `crates/` file was touched. 4 dev-mode tripwires green. Thirteen spike arms in `examples/fence-toolchain-spike/toolchain.sh`, transcripts in `docs/notes/fence-notes.md`. No prompt template changed, so `brief-cost` is 0 and the 51-token headroom D-068 recorded is untouched. **Not verified:** no fleet has been started since this landed, so no interactive worker has run `cargo build` in a real pane — the same honest gap D-062, D-065 and D-066 each record. The spike's arms are real shells with real builds, not a pane. No live spend.
