---
id: D-039
title: "concurrent messages to one pane: a serial writer that drains"
phase: "meta"
status: alive
---

- **The trigger was observed, not predicted.** With the fleet running, several workers messaging the orchestrator at once "glossed over" some of them. Two separate causes, one of them ours.
- **Ours: ordering.** Every `Deliver` got its own `spawn_blocking` task, and those raced for the pane's writer lock in whatever order the blocking pool scheduled them. Nothing was dropped — the mutex and the kernel buffer see to that — but a pane could see messages in an order the log disagreed with. That is a defect, not a tradeoff.
- **Not ours: the merge.** A `claude` input box is one text field. Message A submits and starts a turn; B's paste lands mid-turn and is queued by CC; C lands on the same buffer. What the model reads is a blend of the three. We cannot reach inside the TUI.
- **One writer task per pane, draining.** When the writer is free it takes *everything* currently queued for that pane (`try_recv`, never `recv`) and sends it as one bracketed paste, each message still framed with its sender and separated by a blank line. Ordering becomes the hub's order by construction, and the merging the TUI was doing invisibly and badly is now ours, done where the framing still says who sent what.
- **This is not the batching the pivot bans.** That was an idle guard plus a flush ticker that could withhold a message indefinitely while the operator typed. This adds **zero** delay to a message arriving at a free pane — nothing ever waits for more to accumulate. It groups only messages that were already concurrent, which is exactly the set the TUI was going to merge anyway. Every message keeps its own log row, its own `accepted`, and its own ack: batching groups the write, never the accounting.
- **What it does not fix, stated plainly.** A pane thirty seconds into a turn still receives messages into CC's own queue, at CC's mercy. Nothing on this side of the pty can change that, and it is the reason `accepted` has never meant "delivered" (L3).
- **Verified:** `a_burst_from_four_peers_arrives_whole_in_order_and_in_fewer_writes` fires four concurrent deliveries at one real pty, asserts all four are answered and accepted, that the pane saw them in the hub's order, and that they reached it as **fewer bracketed pastes than there were messages** — the property that would silently regress if the drain ever became a per-message write again. Deterministic rather than lucky: the 30 ms submit gap guarantees messages 2–4 are queued while 1 is in flight.
