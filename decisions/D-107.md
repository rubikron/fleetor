---
id: D-107
title: "a receipt is a chain entry recorded after `fleet done` sends its message; the latest one tells a release where the work sits"
phase: S3
status: alive
---

- **What.** `fleet done <n> "<check>"` sends orch the receipt message exactly as before, then makes a second call on the same connection that appends a `receipt` chain entry: the check command, its status as the message words it (`exit 0`, `killed by a signal`), branch, commit, an uncommitted flag, and whether orch's pane accepted the message. A receipt moves neither status nor owner. The exit code still means delivery only; a record that fails, or a task argument that is not a number, prints a warning.
- **Release.** A release by someone other than the owner in their checkout now takes "where" from the task's latest receipt before requiring `--where`. This closes D-105's deferral.
- **Why status is text.** A check killed by a signal has no exit code, and the receipt message already words it this way.
- **Reverses if.** The second call proves unreliable enough that receipts should be recorded by the hub when it sees the send.
