id: D-079
title: "the Critic gets a socket and a switch, and the switch is in the hub"
phase: "meta"
status: alive
---

- **What changed.** `spawn::critic_command_with` now calls `apply_pane_env(&mut cmd, PaneId::Critic, socket, path)` exactly as `evaluator_command_with` does, so the Critic holds `FLEETOR_PANE` and `FLEET_SOCKET` unconditionally. The operator's control over whether it may *use* them is a `bool` on the hub (`hub::Interview`, a handle on one cell shared with `Fleet.interview`), read at the top of `Hub::handle`: while the interview is closed, an op whose `from` is `PaneId::Critic` returns `OpResult::Error` before the `match op`. Two Tauri commands move and read it — `critic_interview_open(open) -> bool` and `critic_interview_is_open() -> bool`, both registered in `lib.rs` — and the setter writes a `Notice` on each edge naming which it was. Default: closed.
- **Why the switch is not at spawn, which is where the arc doc's first reading puts it.** `FLEET_SOCKET` is fixed on the `CommandBuilder` when the pty is created. "Hand it a socket when the operator opens the interview" is therefore not buildable without respawning the pane — destroying the operator's conversation with the pane they just decided to let speak. The socket had to become unconditional and the gate had to move. Rejected: an operator control that respawns the Critic, for that reason; and gating on `fleet handoff` instead of on the operator, which WP-21 already rejected because some lapses are only visible while they are happening.
- **Tier 1.4 — refused at accept time, never accepted-then-dropped.** `building.md` §9.3 records this argument as had and lost twice, so the compliance claim is stated as what the early return *skips*: no `Message` is constructed, no `AppCommand` is sent, `self.app` is not touched, `self.store` is not touched, and `last_inbound_from` is not written — so no pane's next `fleet reply` is silently redirected either. This is the class `Hub::cmd`'s allowlist check already is (its own comment: "nothing enters the delivery path"), not a mute on a live route: open, the line is not reached and the Critic's ops take the identical path every other sender's do. The property is tested rather than asserted — `panes.rs::a_closed_interview_refuses_the_critic_and_leaves_the_event_log_untouched` reads the whole event log either side of a refused send and requires it not to have moved, on a real pty with a real store.
- **The refusal names the switch, not the addressee.** The arc doc's shorthand is that a closed interview fails "with 'no such pane'", copying WP-19's cross-fleet cutoff. Taken literally here it would be false: `orch` exists, and blaming it for a state of the operator's control is the log-lie L3 is about, one layer up. The sentence is instead *"the interview is closed, so no pane is an address from here and nothing was sent — the operator opens it with the control in the Critic view"*: the same fact — the Critic has no addresses right now — said without a false claim about the pane it named. The `fleet` CLI prints it to stderr and exits 1.
- **`is_fleet_member` did not move, and the test now asserts that with the socket present.** `tests/placement.rs::the_critic_is_given_no_socket_so_fleet_send_inside_it_reaches_nothing` was inverted rather than deleted, as `the_critic_is_given_a_socket_and_is_still_not_a_member_of_the_fleet`: it keeps the `orch` comparison (a bench that stopped setting sockets for everyone would now fail rather than pass), asserts both variables are present and equal to `orch`'s socket, and then asserts `!PaneId::Critic.is_fleet_member()` and its absence from `PaneId::roster` — no roster row, no broadcast leg, no peer list, with a socket in hand. That is the design: addressable, never enumerated. The write guardrail is untouched: the Critic's roots are still its own working directory alone. It gained a voice, not a pen.
- **One consequential side effect, taken deliberately.** `machine_notices` excluded the Critic because the `fleet`-binary warning "would be false for it" (D-076's own words). It is true of it now, so the exclusion is gone and a Critic on a machine with no `fleet` binary warns like any other pane. `orch` stays excluded, because `place_orch` emits that line itself.
- **No verb moved.** `VERBS`, the clap enum, `Op`, `prompts/orch.md` and `prompts/worker.md` are byte-unchanged — `git diff --exit-code` on all of them, plus `prompts/critic.md`, exits 0. No brief teaches the Critic to anyone: a pane meets the name when a message arrives and answers with `fleet reply`, which it already knows (WP-21 guardrail 4).
- **What would reverse it.** A measurement that the interview's answers do not earn their turns — the arc doc sets the bar as converting fewer than three of the first report's six UNCITED items. Or evidence that a pane, having been messaged by `critic`, starts writing for it: that is the failure the veil prevents for the evaluator and cannot prevent here, because the Critic is openly named.
- **Verified.** 226 workspace tests green (unchanged — nothing was added to the workspace crates); `src-tauri` 222 with `--features devmode`, up from 219, and 217 without, up from 214 — three added in `tests/panes.rs`, one renamed in `tests/placement.rs`, none deleted. The three new ones are real processes on real ptys through `placement::place`: a closed interview refuses and moves neither the log nor orch's terminal; an open one is `accepted`, arrives framed `[fleet · critic]`, and closes again with no respawn; and orch's `fleet send critic` reaches the Critic's pty and is logged with it as the recipient. **The refusal was mutation-checked**: adding a single `Notice` append beside the early return makes the log test fail with the two rows against one, so the assertion is load-bearing rather than decorative. The four veil tripwires pass and still match the evaluator only; `hub.rs` contains no needle of either tripwire. `cargo clippy --all-targets --workspace` shows the same three pre-existing `fleetor-core` warnings and `--features devmode` from `src-tauri` the same two — no new warning. `cargo build --features devmode` and `npm run build` clean.
- **Not verified.** **No fleet has been started since this landed** — the same gap D-062 through D-078 each record. So: no live `claude` has met the refusal sentence, and nothing measures whether a model reading it opens a `fleet roster` and argues rather than waiting. **The interview has never been run.** Whether asking a pane about its own conduct produces anything the archive did not already contain is the arc's central bet and is entirely unmeasured here; the three-of-six bar is a criterion, not a result. The `Notice` on each edge is asserted by no test — I wrote the two commands and read the `note` helper they call, but nothing pins that an open and a close leave two distinguishable rows, and I did not verify how the Activity feed renders them. **The dev-mode leak the arc doc sharpens is untouched and is now reachable**: a Critic that has read a dev-mode run's `events.json` can, with the interview open, ask `orch` about what it found there. WP-21's open question 2 recommends refusing to open an interview on a dev-mode run; that refusal is *not* built, and this entry is where a future session should find that out. `rustfmt` is not installed on this machine, so formatting was not checked. No live spend.
