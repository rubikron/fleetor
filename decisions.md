## D-001 — Working name: FLEETOR

- **What:** Project branded FLEETOR (was: Fleet).
- **Why:** max's call; "for now" — expect a possible rename before any public artifact.
- **Reverses if:** a real name is chosen; grep-friendly, so a rename is one pass.

## D-002 — DeepSeek reached via Anthropic-compatible endpoint, not LiteLLM

- **What:** Workers point at `ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic` with `ANTHROPIC_MODEL=deepseek-v4-flash`, auth via `ANTHROPIC_AUTH_TOKEN`. No LiteLLM/OpenRouter proxy (handoff cited those from memory).
- **Why:** DeepSeek ships a native Anthropic-compatible endpoint; removes a proxy hop and a dependency. Verified working in Phase 0.
- **Reverses if:** the endpoint drops tool-use fidelity or a model not on it is needed — slot a proxy behind the same `AgentProcess` seam.

## D-003 — Workers run under an isolated `CLAUDE_CONFIG_DIR`

- **What:** Every worker spawns with `CLAUDE_CONFIG_DIR` pointed at a fleet-owned dir, never the operator's `~/.claude`.
- **Why:** Phase 0 measured the operator's global config leaking in (28 tools, personal MCP servers, global CLAUDE.md) at ~36k input tokens/call and a polluted tool surface; isolation drops it to vanilla CC (~26k, 25 tools, 0 MCP). Also upholds the Tier-1 zero-footprint boundary. Profiles (handoff §7) layer on top of this clean base.
- **Reverses if:** we deliberately want the operator's project `.claude/` to flow through — then inherit that dir explicitly rather than the personal global one.

## D-004 — `total_cost_usd` ignored; cost computed from token counts

- **What:** Real cost = tokens × DeepSeek Flash rates ($0.14 in / $0.28 out per M, cache-read ~0.1×), computed in `fleetor-cli`. The `result.total_cost_usd` field is kept for reference only.
- **Why:** Claude Code computes `total_cost_usd` from its built-in Anthropic price table via model-name mapping — off by ~30× against DeepSeek ($0.13 reported vs ~$0.004 real).
- **Reverses if:** DeepSeek's endpoint starts returning a trustworthy cost field, or published rates change (update the constants in `report.rs`).

## D-006 — Phase 0.5 pty spike: PASS (GO); no companion-window fallback

- **What:** Real `claude` TUI renders faithfully through `portable-pty` + `@xterm/xterm` in a bare Tauri 2 window. Operator-verified exit test: colors, alternate screen (slash-command menus), resize/reflow, scrollback, paste all behave. The WKWebView terminal-fidelity risk (BUILDING §8, risk row 2) is retired; the embedded-orchestrator product shape holds — the companion-window fallback is **not** needed.
- **Why:** This was the one Tauri-specific platform risk (handoff §12). De-risked early, before the shell phase, exactly as the risk register prescribes.
- **Reverses if:** a later CC version or macOS webview regression degrades the TUI unfixably — then escalate to max (product-shape change), not a silent workaround.

## D-007 — Spike shell: standalone `src-tauri` package, plain-TS frontend

- **What:** `src-tauri/` is its own cargo workspace (empty `[workspace]`), deliberately **not** a member of `crates/*` — keeps tauri's dep tree and build profile out of the clean fleetor-cc/cli lockfile. The spike frontend is plain TypeScript + xterm.js (no React), single Vite host at repo root with source under `ui/`.
- **Why:** YAGNI + isolation. A one-terminal spike needs no framework; a framework would be dead weight. Isolating the tauri workspace means a UI-layer build problem can never hold the headless core hostage (BUILDING §3).
- **Reverses if:** Phase 4 (the real shell) folds `src-tauri` into the main workspace and adopts React per BUILDING §2 — expected, and cheap since the spike is throwaway-grade.

## D-010 — Assign-first: don't gate the first stdin write on the `init` event

- **What:** The supervisor writes the ticket to the worker's stdin *immediately* after spawn, then reads the event stream (consuming `init` inline). It does **not** "read stdout until init, then send" as handoff §5 step 2–3 prescribes.
- **Why:** Verified against real Claude Code: in `-p --input-format stream-json` mode, `claude` emits `system/init` only *after* it begins processing the first stdin message. Gating the first write on `init` deadlocks (server waits for init; CC waits for input) — the symptom was a real-CC run that produced zero events until the wall-clock kill. The handoff explicitly said to verify event ordering against the installed CC rather than trust the doc; this is that correction. Multi-turn streaming confirmed in the same probe (the process stays alive after `result`, awaiting more input), which the no-report reprompt relies on. `session_id` is still captured from `init` when it arrives; it just isn't needed to send the first message.
- **Reverses if:** a future CC emits `init` eagerly at startup — the assign-first path still works (init consumed earlier), so no revert needed; only revisit if streaming multi-turn semantics change.

## D-008 — Phase 1 report ingested from a transcript block, not MCP

- **What:** In Phase 1 the worker files its report by ending its final message with a fenced ```` ```fleet-report ```` JSON block; the supervisor extracts and parses it from the transcript (`Report::from_transcript_text`). The assignment message carries the schema and an example. The real `report()` MCP tool (handoff §4) is **not** built yet.
- **Why:** The MCP `report()` channel needs the stdio-shim + unix socket, which is Phase 2's deliverable. Transcript-block ingestion makes the full ticket lifecycle testable end-to-end *now* (against fake-claude and one real-CC run) without pulling Phase 2 forward. Reversible: when the shim lands, `report()` becomes primary and this parser stays as the "no report filed" backstop (handoff §5).
- **Reverses if:** Phase 2 wires the MCP surface — then reports arrive as structured tool calls and the transcript scrape demotes to a fallback (or is dropped if the tool proves reliable).

## D-009 — Phase 1 crates: added `fleetor-core`, `fleetor-db`, `fleetor-server`

- **What:** Grew the workspace from 2 crates to 5, per BUILDING §3's layout: `fleetor-core` (frozen contracts — envelope, events, report, ticket, `Store`/`AgentProcess` seams), `fleetor-db` (rusqlite + migrations, the 5-table sketch), `fleetor-server` (the supervisor loop). `fleetor-cc` gained the streaming `supervised_command`, the `AgentProcess` seam, and the persistent stdin/stdout `Session` driver.
- **Why:** Phase 1 is when supervision, persistence, and the contract layer are first needed (D-005 said add crates when their phase needs them). Only two of the four sanctioned seams are introduced — `AgentProcess` and `Store`; `Transport` and `GateRunner` are deferred to their phases (2, 3) to avoid speculative abstraction (BUILDING §8).
- **Reverses if:** a crate proves to carry no weight — collapse it back. `fleetor-server` in particular is a lib so Phase 4's Tauri app can consume it directly.

- **What:** Created just the two crates Phase 0 needs (not the full 6-crate layout), and the spawn/stream path uses `std::process` + threads, not tokio.
- **Why:** YAGNI + reversible. `fleetor-cc`'s spawn builder returns a `Command` whose env/arg logic ports to `tokio::process` unchanged; remaining crates (core/db/server/shim) get added when their phase needs them.
- **Reverses if:** Phase 1 supervision needs async multiplexing — promote spawn to tokio and add crates then.

## D-011 — Phase 2 adopts tokio for the socket + hub (D-005/D-009 deferral resolved)

- **What:** `fleetor-ipc` (the new `Transport` crate) and `fleetor-server`'s hub run on **tokio**. The Phase 1 sync supervisor (`std::process` + threads + mpsc) is untouched and still passes; only the new Phase 2 surface is async.
- **Why:** Phase 2 multiplexes a socket accept loop + N worker connections + a blocking lead long-poll (`await_events`) + blocking `ask_lead` waiters — the exact "async multiplexing" D-009 said would trigger the promotion, and the runtime BUILDING §2 already names. `tokio::sync::{oneshot, Notify}` model the ask/reply and long-poll cleanly; hand-rolling them on `Condvar` would diverge from §2 for no gain.
- **Reverses if:** the async surface proves not to earn its keep — unlikely now that the hub, shim, and CLI all consume it.

## D-012 — New `Transport` seam lives in its own crate `fleetor-ipc`; wire types in `fleetor-core`

- **What:** The socket **wire contract** (`Request`/`Response`/`Op`/`OpResult`/`LeadEvent`/`Hello`, versioned `WIRE_VERSION=1`) is pure serde in `fleetor-core::wire`. The **transport** (the `Transport` trait — the 3rd sanctioned seam — plus `UnixTransport`, framed `Conn`, and a `Client` helper) is a new crate `fleetor-ipc`, depended on by both `fleetor-server` and `fleetor-shim`.
- **Why:** Contracts belong in core (BUILDING §4) and must stay tokio-free; the I/O belongs behind the seam. A shared crate keeps the shim from depending on the whole server, and isolates the socket in one module (BUILDING §2 IPC row) so a Windows named-pipe impl slots in behind the same trait. Framing is newline-delimited JSON over any async duplex, so the transport can change without touching the framing.
- **Reverses if:** a second transport never materializes and the trait carries one impl forever — collapse `Transport` to the concrete `UnixTransport` (BUILDING §8 over-abstraction guard).

## D-013 — One socket, two faces; worker/lead op split enforced structurally

- **What:** The hub serves workers and the lead on one socket; a connection declares its `Party` via `Hello`. The wire `Op` enum holds both faces, and the hub **rejects** a lead op from a worker connection and vice-versa. `ask_lead` is the *only* worker blocking op; there is no worker↔worker blocking op in the enum at all.
- **Why:** Makes Tier-1.5 (blocking is worker→lead only; no worker↔worker deadlock primitive) a property of the type surface, not a convention. Mail (`dm`/`broadcast`/`send`) is always async and persisted to the `mail` table (source of truth, survives a crash — handoff §11); questions/notices and `ask_lead` reply-waiters are in-memory and transient (a crash drops an in-flight ask, which times out to the park answer).
- **Reverses if:** a future need for lead↔lead or a second blocking worker op appears — revisit the split, but never add a worker→worker blocking op (Tier-1.5 is max's).

## D-014 — Mid-turn mail framing: coordination, not commands (spike-derived)

- **What:** The Stop-hook injects queued mail as a `block` decision whose `reason` is explicitly framed as *in-band teammate coordination that augments the current task*, never as a new instruction. Delivery is via the shim binary's `stop-hook` mode; an empty queue emits nothing (turn ends), and the queue emptying is the loop terminator (no `stop_hook_active` bookkeeping needed).
- **Why:** The Phase 2 spike (`docs/phase2-spikes.md`) showed real Flash **refuses** injected text that reads as an override of its task ("treating it as data, not a command") — correct model behavior. The delivery *channel* is proven; only the *framing* needed care. The MCP + Stop-hook mechanisms themselves passed against installed CC 2.1.220 (fixtures in `tests/fixtures/`), so no escalation to max was needed.
- **Reverses if:** a later CC changes Stop-hook re-injection semantics — the fixtures are version-stamped; re-capture and diff.

## D-015 — Report-over-MCP and the idle/opportunistic delivery paths deferred within Phase 2

- **What:** Phase 2 builds the messaging *core* — `ask_lead`/`reply`, `notify_lead`, `dm`/`broadcast`, `await_events`/`inbox`, and turn-boundary (`drain`) delivery. Deferred: (a) `report()` as an MCP tool (still transcript-scraped per D-008); (b) the "idle → server writes to stdin" and "opportunistic piggyback on a tool result" delivery paths (handoff §5) — only turn-boundary drain is wired; (c) `whos_working_on`/`claim_file`/`backlog_add` (handoff §4), which serve the Phase 3 ownership/quality loop.
- **Why:** YAGNI against the exit test (BUILDING §6): the scripted 3-agent conversation with a mid-turn delivery needs exactly the core above. The deferred items are additive behind the same wire surface.
- **Reverses if:** their phase arrives — report-over-MCP and ownership tools are natural Phase 3 companions; idle/opportunistic delivery lands when the multi-worker supervisor (Phase 4 shell) drives real turn boundaries.

## D-016 — Phase 3 quality loop is supervisor-level; report-over-MCP wired at the hub, primary in Phase 4

- **What:** The quality loop (gate → auto-bounce → peer review → done) lives in `fleetor-server::quality`, driving one worker session over stdin/stdout (reusing the Phase 1 `assign`/`drive_to_report` primitives, now kept alive across bounces) plus a **fresh reviewer session** per review round. Report/verdict are transcript-scraped (`fleet-report` / new `fleet-review` fenced blocks). Separately, `report()` is promoted onto the MCP surface (`Op::Report`, shim `report` tool, hub persists + emits `report-filed` + notifies the lead), proven at the hub layer — but the *supervisor's* ingestion stays transcript-scrape.
- **Why:** The supervisor (stdin/stdout) and the hub (socket) are deliberately unwired until Phase 4's multi-worker runner (BUILDING §6 table; D-015). Making report-over-MCP the supervisor's primary path now would require the supervisor to consume hub events — pulling Phase 4 forward. Keeping the loop supervisor-driven makes the exit test ("buggy ticket bounces, gets fixed, passes review") fully testable against fake-claude + a real shell gate with zero tokens, exactly as Phases 1–2 were.
- **Reverses if:** Phase 4 unifies the runner with the hub — then `report()`-over-MCP becomes the supervisor's primary ingestion and the transcript scrape demotes to the "no report filed" backstop (handoff §5); the `fleet-review` verdict can move onto an MCP tool the same way.

## D-017 — GateRunner seam takes config, not discovery; two retry caps default 3; `claim_file` carries the ticket

- **What:** `GateRunner` (the 4th sanctioned seam) is `run(cwd) -> GateReport`; *which* commands is `GateSpec` config on the concrete `ShellGateRunner` (`sh -c` per check, exit 0 = pass, combined output tailed to 4 KB for the bounce). Gate *discovery* (reading CLAUDE.md/package.json/Makefile — handoff §3) is left to Phase 4. The loop uses two retry caps — `gate_retry_cap` and `review_retry_cap`, both default 3 — escalating to the lead (ticket → `Blocked`) after the cap rather than grinding. Added a `ReviewResult`/`ReviewOutcome` event variant and a `backlog` table (migration 0002); `whos_working_on`/`claim_file`/`backlog_add` route through the hub against the existing `leases` table + the new `backlog` table. `claim_file(path, ticket)` carries the worker's ticket id (a Tier-2 tweak over handoff §4's `claim_file(path)`) so the hub records the lease without tracking slot→ticket state it doesn't yet own.
- **Why:** The seam stays model-agnostic (a future non-shell runner keeps the same face); config-not-discovery is YAGNI for the exit test. Separate caps because gate and review failures are independent loops. Escalate-to-Blocked matches handoff §8 ("capped at ~3 retries then escalate"). Carrying the ticket on `claim_file` avoids inventing hub-side assignment state before Phase 4 wires it.
- **Reverses if:** Phase 4 gives the hub real slot→ticket assignment (drop the `ticket` arg, infer it) or discovery lands (the spec is populated by a scan instead of a literal).

## D-018 — Phase 4a fleet runner lives in `fleetor-server::runner`; sync supervisor bridged to the async hub via `spawn_blocking`; `WorkerSpec` carries the `AgentProcess` seam so fake and real share one path

- **What:** The multi-worker fleet runner is a module in `fleetor-server` (`run_fleet`), not a new crate. It boots the hub on a tokio runtime, connects a stand-in lead `Client`, spawns a `run_lead_loop` (long-polls `await_events`, answers `ask_lead`, sends mid-turn mail), and runs each worker's **sync** supervisor (`run_ticket`, the Phase 1 std-process/threads loop) on `tokio::task::spawn_blocking`. Worker fleet-wiring (the `--mcp-config`/`--add-dir`/`mcp__fleet` allow-list, the `fleet-mcp.json` + `settings.json` Stop hook, and `FLEET_SOCKET`/`FLEETOR_SLOT` env) is written by `WorkerConfig::write_fleet_config()` and lives entirely in `fleetor-cc::spawn` — the one place that knows how a fleet worker differs. `WorkerSpec` holds a `Box<dyn AgentProcess + Send>` with `::real(config,…)` / `::fake(agent,…)` constructors, so the fake-claude integration test and the live `fleetor run --real` drive the identical runner.
- **Why:** The sync↔async seam is the core Phase 4 problem (BUILDING §6 table: supervisor and hub were deliberately unwired through Phase 3). `spawn_blocking` bridges them without rewriting the proven sync supervisor to async or hand-rolling a second event loop — the two channels stay decoupled for 4a (report-over-MCP as the supervisor's *primary* signal, and idle/piggyback delivery, are still deferred; see below). Routing `WorkerSpec` through the `AgentProcess` seam (rather than hardcoding `RealClaude`) is what lets the whole runner be exercised for free against fake-claude's dual-personality worker (stdin-driven **and** socket-speaking at once), keeping the live-CC run a confirmation gate rather than the only test. Runner-in-server (not a 7th crate) because Phase 4's Tauri app consumes `fleetor-server` directly (D-009); a crate would carry no weight (BUILDING §8).
- **Live confirmation (the 4a gate, cost ~cents):** `fleetor run --real` drove one real Flash worker fully wired. Event log showed the full loop: `mcp__fleet__ask_lead` → worker **blocked** → lead answered → worker **working** → `mail` (lead→worker-1) → `Write`/`Bash`/`mcp__fleet__report` → ticket **done**. Two independent proofs the messaging landed in-model: (1) the worker named the file `hello.sh` — exactly the lead's reply, not the decoy `greet.sh` — so the blocking `ask_lead` answer was consumed, not ignored; (2) the transcript shows the Stop-hook mail delivered and the model reasoning *"coordination only, keep to my ticket… my ticket is already done"* — the D-014 framing worked against real CC 2.1.220, not just fixtures.
- **Followups (not bugs):** (a) the worker called `mcp__fleet__report` **twice** (once before, once after acknowledging the mail), yielding two `report-filed` events; ticket state transitions once (idempotent), so it's benign — but mail-arriving-after-a-report can prompt a redundant report, worth smoothing when 4b makes report-over-MCP primary. (b) `fleetor run` has no free fake path (it `bail!`s without `--real`); the fake path is the `fleet_runner` integration test, by design.
- **Reverses if:** 4b lands the D-015/D-016 reversals — report-over-MCP becomes the supervisor's primary ingestion (transcript scrape demotes to the "no report filed" backstop) and idle→stdin / opportunistic-piggyback delivery join turn-boundary drain. If the sync supervisor is ever rewritten to async, `spawn_blocking` drops out; until then it is the seam.

## D-019 — Phase 4b: report-over-MCP is the supervisor's primary done-signal; the sync↔async bridge is the shared event log; quality loop stays transcript-scrape; D-015 idle/piggyback deferred to 4c/4d

- **What:** The base supervisor (`run_ticket`) now treats the worker's `fleet.report` MCP call as its **primary** terminal signal (the D-016 reversal). The hub already persists the report and appends `ReportFiled`; the supervisor watches the shared event log — a new `Store::latest_seq()` cursor captured at assign, scanned via `events_since` at each turn boundary (`mcp_report_step`, with a bounded ~500ms `grace_poll_mcp_report` for the hub task's commit lag) — and finishes on that event *without re-saving or re-emitting*. It's a plain `ReportStep::Terminal { Reported }`, so no new outcome variant. The transcript `fleet-report` scrape (D-008) is demoted to the backstop for a turn that ends with a block instead. Gated behind a `prefer_mcp` flag on `drive_to_report`: `run_ticket` passes `true`; the **quality loop passes `false`** and is unchanged.
- **Why:** This is the tight coupling Phases 1–3 deliberately left open (the runner doc's "4b"). The key design move: the sync supervisor (`spawn_blocking`) and the async hub (tokio) are bridged through the **shared, persisted event log they both already hold** — no cross-runtime channel, no rewrite of either loop (KISS). Report-over-MCP being primary also removes the supervisor's transcript-scrape *duplicate* — note the 4a live double-`ReportFiled` was actually the model invoking `fleet.report` **twice** (two hub emits), a separate worker-behavior/hub-idempotency concern the supervisor can't and shouldn't police; 4b guarantees only that the *supervisor* adds no duplicate (deterministically proven by the `mcp-report` fake: exactly one `report-filed`, no scrape).
- **Quality loop stays transcript-scrape:** it needs the full `Report` **body** to attach gate results and drive bounces; the event-only primary path carries just `status`. Unifying it needs a `Store` report-load read + a `fleet-review` MCP tool — a natural 4c/4d companion (D-016's own reversal note). `prefer_mcp = false` keeps it byte-for-byte as Phase 3 shipped.
- **D-015 idle/opportunistic delivery deferred (again, deliberately):** idle→stdin and piggyback-on-tool-result have no live consumer yet — no idle detection and no real orchestrator — and turn-boundary Stop-hook drain already covers the headless worker (proven in 4a). YAGNI: they land in 4c/4d where live turn boundaries and the orchestrator TUI make them meaningful. Only the D-016 half of the "4b" plan is delivered here.
- **Verified:** `runner_terminates_on_report_over_mcp_no_double_log` — a worker that files only over the socket (no transcript block) closes `Done` via the hub event with exactly one `report-filed`; the existing `fleet-ask` test now exercises the backstop (transcript block) path. Full suite 44 tests, 0 warnings. No live-CC spend: the fix is deterministic at the supervisor layer; a real re-run is confounded by model nondeterminism (a worker may still call the report tool twice).
- **Reverses if:** the quality loop is unified onto report-over-MCP (drop `prefer_mcp`, add the report-load read) — then transcript-scrape becomes a pure backstop everywhere; or if `latest_seq`/`events_since` polling proves too coarse under a busy multi-worker log (promote to a per-slot notify channel from the hub).

## D-020 — Phase 4c: the live event bus is a `Store` decorator (`BroadcastStore`) in `fleetor-server`, not a new emit path; persist-then-publish; lag recovers from the DB

- **What:** The UI's live event feed (README roadmap "4c") is delivered by wrapping the [`Store`] seam. `fleetor-server::bus` adds `EventBus` (a `tokio::sync::broadcast` fan-out of `(seq, FleetEvent)`), `BroadcastStore` (a `Store` decorator that delegates every method and, right after a successful `append_event`, publishes the row's real `seq`), and `EventFollower` (`EventBus::follow(store, after)` → an async `next()` that yields the DB snapshot then live events, gap-free and dup-free). Wrap the inner store once and **both** emitters — the sync supervisor (`supervisor::emit`) and the async hub (`Hub::emit`) — publish for free; neither loop is touched. `fleetor run` now wraps its store and prints events live via a follower task (replacing the post-hoc `print_event_tail` dump). Capacity is `BUS_CAPACITY = 1024`.
- **Why:** Every event already funnels through the one chokepoint `Store::append_event`; a decorator there captures all of them with zero change to the proven Phase 1–4b code (KISS + reversible — unwrap and you have a plain store, BUILDING §8). The bus lives in `fleetor-server`, not `fleetor-core`, because it needs `tokio` and core must stay tokio-free (D-012). **Persist-then-publish** keeps the DB the single source of truth (matching the 4b "shared, persisted log" bridge, D-019): publish is best-effort (no subscribers = no-op; the event is already durable), and a follower that joins late or lags the bounded ring recovers by re-reading `events_since(cursor)` — the channel only *accelerates* delivery, it never becomes a second source of truth. `broadcast::Sender::send` is sync and runtime-free, so the sync supervisor thread publishes without a handle to the runtime. This is the substrate 4d (orchestrator feed) and 4e (Tauri event pump) consume.
- **Verified:** `event_bus.rs` (4 tests) — a subscriber live for a whole `run_fleet` receives *exactly* the persisted log (same seqs, strictly increasing, no gaps/dupes); a late subscriber gets the full DB history then live events seamlessly across the snapshot boundary; a follower flooded past `BUS_CAPACITY` without reading recovers **every** event from the DB, contiguous and in order; and a bare `EventBus` fans one publish to all subscribers. Full suite 48 tests, 0 warnings. No live-CC spend (deterministic at the store/bus layer).
- **Reverses if:** a second transport for the feed never appears and `broadcast` proves heavier than needed — collapse to a plain `Vec<Sender>` or a single mpsc; or if per-event fan-out is too coarse for the UI, batch in the follower. If the Tauri app (4e) would rather subscribe from inside the app process than through the CLI, `BroadcastStore::bus()`/`follow()` are already the public handles it consumes.

## D-021 — Phase 4d: orchestrator-as-lead drives a *dynamic* fleet over the lead MCP face; the lead seat becomes external; `run_fleet` stays for the static path

- **What:** The scripted `LeadPolicy` stand-in is replaced by a real lead seat that drives the fleet through MCP tools. (a) New lead-facing wire ops `Op::Assign { ticket }` and `Op::FleetStatus`, plus `OpResult::Status { board }`; `Ticket`/`Budget` gain `PartialEq/Eq` so `Op` keeps its derives (as `Op::Report` already required of `Report`). (b) The hub gains an optional dispatcher (`mpsc::UnboundedSender<AssignCommand>`, via `Hub::with_dispatcher`): `assign` validates the slot, persists the ticket so `fleet_status` reflects it immediately, and forwards the command; a **static** hub (no dispatcher) answers a clean error rather than dropping it. `fleet_status` returns the board from `store.tickets()`. (c) New `run_dynamic_fleet` (runner): workers are spawned **on demand** as the lead calls `assign`, not from a fixed list up front (`run_fleet` is untouched). The lead seat is *external* — a `driver` future runs the session; when it returns, the runner stops accepting work, joins the spawned workers (the hub stays up so they can still report over the socket), and returns per-slot outcomes. The hub→runner bridge is a plain mpsc channel; each assign becomes a supervised worker on `spawn_blocking` — the same sync↔async seam as 4a (D-018), now fed dynamically. (d) The shim gains a **lead role** (`FLEETOR_ROLE=lead` → `Party::Lead`), a lead tool face (`assign`/`await_events`/`inbox`/`fleet_status`/`reply`/`send`), and renders `Events`/`Status` for the orchestrator to read. One binary, role via env — mirroring worker-slot-via-env.
- **Why:** This is the first time a real model (not a Rust script) can drive the fleet, and the point of "orchestrator-as-lead" is **dynamic assign** — the orchestrator *decides* to dispatch and it happens, which needs the hub→runner command seam a static fleet never had. Keeping `run_fleet` byte-for-byte preserves every 4a/4b/4c test (reversible; BUILDING §8). A `driver` future for the lead session covers both faces: a Rust test lead connects a `Client`; the future `fleetor run --real` path (deferred) spawns the real orchestrator process and awaits it — the process connects independently through the lead shim, so the runner code is identical either way. `fleet_status` + `await_events` give the orchestrator a supervise loop without reading transcripts.

## D-025 — Phase 4f: the lead can interrupt / restart a worker; the async→sync yank is a kill-by-pid over one `RunnerCommand` channel; a deliberate kill is `Interrupted`, not `Crashed`

- **What:** Two new lead ops, `Op::Interrupt { slot }` and `Op::WorkerRestart { slot }` (with matching shim lead tools `interrupt` / `worker_restart`), let the orchestrator yank a busy worker. The hub's single dispatcher channel is generalized from `AssignCommand` to a `RunnerCommand` enum (`Assign(AssignCommand)` / `Interrupt { slot }` / `Restart { slot }`); the hub routes control ops through the same slot-validated, dynamic-only path as `assign` (a static fleet answers a clean error). In the dynamic runner, each spawned worker now carries an `Arc<WorkerControl>` — a shared handle holding the worker's **pid** (published by `run_ticket` the instant `Session::spawn` returns) and an `interrupted` flag. `WorkerControl::kill()` sends `SIGKILL` to that pid (via `libc`, already in-tree); the worker's stdout stream then closes, the *sync* supervisor loop sees `Recv::Closed` and unwinds normally, and the runner **relabels** that worker's `Crashed` outcome to the new `Outcome::Interrupted` (only when it initiated the kill). `Restart` kills the live worker and re-dispatches its ticket through the same factory, producing a fresh worker in the slot. The command loop keeps a per-slot `HashMap<u8, (Arc<WorkerControl>, Ticket)>` (touched only by the one loop, so no lock).
- **Why:** This is the async↔sync interrupt D-021 explicitly deferred as "a real feature, not a stub" — the hard part is signalling a worker whose supervisor runs on a `spawn_blocking` thread with no async cancellation point. Killing by pid is the clean, reversible seam: it reuses the stream-close the supervisor *already* handles (no new state machine, no restructuring of `Session` ownership), and `libc::kill` needs no cross-runtime channel. Generalizing the existing dispatcher channel (rather than adding a second) keeps one ordered command stream lead→runner, so an `interrupt` can't overtake an in-flight `assign` for the same slot. Relabelling `Crashed`→`Interrupted` at the runner (not in the supervisor) keeps the sync loop untouched and honest: a stream-close the operator *caused* is not a crash, and the flag lives on each worker's own control so a later real crash on a reused slot is never mislabelled.
- **Deferred / not silent (BUILDING §9):** `worker_restart` is proven at the mapping + routing level (shim tool → `Op` → `RunnerCommand`, shared with the interrupt seam) but its full kill-then-respawn is not yet an end-to-end integration test (the two-worker timing is fiddly against fake-claude; the kill mechanism it depends on *is* proven end-to-end by the interrupt test). SIGKILL is a hard kill (no graceful drain / SIGTERM-then-wait); a worker mid-write leaves a partial worktree, which the git-branch isolation already contains. Windows is unaddressed (unix `kill(2)`), consistent with the rest of the unix-socket stack. `interrupt` cannot yet target the lead's own turn (it is the operator's TTY).
- **Verified:** `orchestrator::lead_interrupt_yanks_a_busy_worker` — a `hang` worker (consumes its assignment, never reports) is assigned, driven to in-progress, then `interrupt`ed; the run ends `Outcome::Interrupted` (not `TimedOut`/`Crashed`), proving the pid-kill reached the sync supervisor before the idle watchdog and that the deliberate close is relabelled. The shim lead-tool mapping tests gain `interrupt`/`worker_restart` (drift guard + "every listed lead tool is translatable"), and the cross-process bridge test is updated for the `RunnerCommand` channel. Full workspace suite green; `cargo check` on the shell (separate workspace, path dep on the changed server) passes. No live-CC spend — deterministic against fake-claude.
- **Reverses if:** a graceful interrupt is wanted (SIGTERM + grace window before SIGKILL, or a cooperative cancel token the supervisor polls) — `WorkerControl::kill` is the one place to change; or if the fleet ever needs Windows workers (swap `libc::kill` for a portable process-kill handle); or if per-slot ordering guarantees are relaxed and control commands want their own priority channel.

## D-026 — Phase 4g (D-015 reversal): the last two mail-delivery paths land — idle→stdin (supervisor) and opportunistic piggyback (shim); mail framing single-sourced in `fleetor-core`

- **What:** The two delivery paths deferred since D-015 (again at D-019, D-021) are now wired, closing the messaging model. **(a) Idle→stdin** — at a report-less turn boundary, `supervisor::drive_to_report` runs a bounded `idle_drain_step`: it flips the worker `Working→Idle`, briefly polls `store.take_mail(&Party::Worker(slot))` (10×50ms, honoring the wall-clock `deadline`, mirroring `grace_poll_mcp_report`), and if mail is queued writes it straight to stdin as a **fresh turn** via the existing `Session::send_user` — *not* counted against the no-report reprompt cap (a mail-driven turn is real work, bounded by `deadline`), then `Idle→Working`. Empty window → falls through to the unchanged reprompt/finish path. **(b) Opportunistic piggyback** — in the shim's `call_tool`, after any *worker* tool call, one `Op::DrainMail` folds pending mail into the rendered MCP result as an extra content block (`protocol::append_piggyback`); skips the `report` op (mail-after-report can prompt a redundant report — D-018 followup a) and the lead face (no mailbox). **(c) Framing single-sourced** — `frame_mail_for_injection` + `sender_label` moved from the shim's `protocol.rs` to `fleetor_core::mail`, so all three paths (Stop-hook drain, idle→stdin, piggyback) inject byte-identical D-014 coordination framing.
- **Why:** These paths finally have a live consumer — Phase 4d's `run_dynamic_fleet` + external lead can `send` steering at arbitrary times (D-019/D-021 deferred them precisely for want of that). **Idle→stdin is supervisor-side, not a new channel:** the supervisor already holds `Arc<dyn Store>` and reads it for `ReportFiled` (D-019's shared-log bridge), so it drains the same store directly — no cross-runtime plumbing. **Piggyback is shim-side, not hub-side:** `Client::call` returns only `OpResult` (a Response-level piggyback field would force Client + every-caller plumbing), and fake-claude speaks the raw socket *bypassing the shim*, so enriching the **MCP** result a real worker sees is inherently the shim's job. **Exactly-once holds across all three drains** because `Store::take_mail` is an atomic destructive SQLite drain: concurrent drainers serialize, each message goes out exactly one path, and the orderings are naturally disjoint (mid-turn → Stop hook / piggyback; after the turn's `result` — emitted only once the Stop hook declines to block — → the supervisor's idle drain, which therefore never races the hook for the same message).

- **Deferred (stated):** the worker-spawn crash **fix** (this makes the reason *visible*; the fix follows once we read it); full delivered-mail **body** in the transcript (the event log carries mail metadata, not the body — the marker has no text yet); tool-call **inputs/results** (v1 shows tool names via the existing `tool-activity`); tmux-TUI workers (rejected).

## D-029 — Phase 4i: a persistent worker pool — 4 headless workers spawned idle at startup, messaged/broadcast by the orch; `session = ticket` relaxed to `session = worker`

- **What:** The shell now runs a **standing pool** instead of the dynamic assign-to-spawn fleet. A new `supervisor::run_standby_worker` spawns a worker session once and keeps it alive idle: it polls its mailbox, delivers each queued message to stdin (the D-015 idle→stdin path) and drives the resulting turn via `read_until_result` (so words + tools stream to the transcript, D-028), then returns to idle — it **never reports-and-dies**. A new `runner::run_pool_fleet` spawns N such standby workers up front on `spawn_blocking` (the D-018 sync↔async seam), wires the hub with a dispatcher so `interrupt`/`worker_restart` still act on a slot (assign-to-spawn is a no-op — the pool takes work as messages), runs the lead `driver`, then signals all workers to stop and drains. The Tauri app's `spawn_pool_fleet` builds 4 real workers from the existing `build_factory` and runs the pool, so `fleet_bootstrap` brings up **1 orch + 4 idle workers** with no assign. Added a **lead `broadcast`** (`Op::LeadBroadcast` → hub fans `enqueue_mail` from the lead to every slot → shim lead tool `broadcast`) so the orch messages all four at once.
- **Why:** The operator wants an interactive fleet — 4 available workers to message and watch — not a one-shot ticket runner. The key economy: the messaging + observability substrate already existed. D-015's idle→stdin *is* the delivery mechanism for a standing worker, and D-028's transcript events *are* how you watch it; so the only genuinely new code is the standby loop that keeps a worker alive (spawn once, idle-wait-for-mail) instead of `run_ticket`'s spawn→report→die. `run_ticket`/`run_fleet`/`run_dynamic_fleet` are **untouched**, so the quality loop and every existing test still pass; the pool is additive. An idle standby worker spends **no tokens**; each message is one turn. This relaxes `session = ticket` to `session = worker` for the pool only.
- **Verified (no real spend):** new fake-claude `standby` scenario (echoes each delivered message, stays alive) + `pool::pool_spawns_four_standby_workers_and_broadcast_reaches_all` — four standby workers spawn, a lead `broadcast` produces four `mail` events and lands in **all four** workers' transcripts (`worker-said` per slot), then drains. Lead-broadcast shim mapping added to the drift guards. Full crates suite green (23 test binaries, 0 warnings); `src-tauri` `cargo check` + `tsc/vite` clean. Live: real backend brings up 4 idle workers in the band; the orch `broadcast`s → all four receive → replies type back into the orch TUI (D-027).
- **Deferred (stated):** formal ticket/board dispatch to pool workers (pool is message-driven; the assign→spawn path stays for dynamic mode); auto-respawn of a crashed standby worker (stays dead, surfaced via `WorkerExited` in the Workers tab, until `worker_restart`); Claude-TUI-per-worker (a separate, larger pivot — this delivers "message & watch 4 workers" with headless workers + the transcript view).

## D-030 — The 5-TUI messaging pivot: MCP and the headless supervision model are deleted; all five agents become live `claude` TUIs

- **What:** A ground-up narrowing of the product to *messaging + visibility*. The MCP shim (`fleetor-shim`), the headless stream-json supervision model (`supervisor`/`quality`/`gate`/`runner`, `fleetor-cc`), and the whole ticket/board/report/review apparatus are deleted. In their place: **1 orchestrator + 4 worker `claude` TUIs**, each in its own pty owned by the Tauri app, each viewable in the shell (orch fixed left, workers tabbed right). Agents address each other through a small **`fleet` CLI invoked via Claude Code's built-in Bash tool** (`fleet send 2 "…"`), a plain socket client — no MCP, no JSON-RPC. The hub survives as a pure router; `fleetor-ipc` and the `BroadcastStore` event bus survive untouched. Plan: `docs/tui-pivot-plan.md`. Phase 0 findings: `docs/tui-spawn-notes.md`. Branch `feat/tui-fleet`.
- **Why:** Mapping the as-built system (`docs/fleet-comms-map.md`) showed two things. First, **messaging is the only part that works** — the shipped app runs `run_pool_fleet`, where `RunnerCommand::Assign(_) => {}`, so a lead's `assign` returns `Ack`, lands the ticket on the board as `Backlog`, and nothing ever runs or moves it; gate/review/report are unreachable from the app entirely. Second, and decisively, **the headless model is what forces the complexity**: mail has to be queued and drained at turn boundaries (three delivery paths, a Stop hook, an atomic `take_mail`) *only* because a `-p` process has no writable stdin between turns. Turn detection, report ingestion, transcript reconstruction and pid-interrupt all exist to compensate for not having a terminal. A live TUI has an always-writable stdin, so all of it becomes **unnecessary rather than merely unused** — delivery is just "write bytes to the target pty." Net ~3,500 lines out. This also reverses D-028's "tmux-TUI workers rejected" and D-029's deferred "Claude-TUI-per-worker" — that pivot is now the product, because the operator wants to *watch and steer* four agents, not run a one-shot ticket pipeline.
- **Consequences accepted:** No queue — a send to a dead pane fails loudly (nonzero exit + stderr) rather than buffering; the model self-corrects from its own Bash result. No blocking — `ask_lead`, the waiters, the ask timeout and `WorkerState::Blocked` all die. Message **bodies** move into the event log (`FleetEvent::Mail` carried metadata only, which is useless for a product about watching messages). `session = worker` (D-029) becomes permanent. Delivery is honest best-effort: the event field is `accepted`, never `delivered` — we queued bytes to a live pty and cannot know the model read them. Worker transcript reconstruction is abandoned outright (the TUI *is* the view); parsing redrawn ANSI to rebuild it is explicitly rejected.
- **Verified (Phase 0, real CC 2.1.220, no app code changed):** The onboarding wedge is **absolute, not intermittent** — a virgin `CLAUDE_CONFIG_DIR` never reaches a prompt, and the four worker config dirs on disk are in exactly that state. Bisected to a **two-key** minimum seed (`hasCompletedOnboarding` + `projects[cwd].hasTrustDialogAccepted`; `theme` unnecessary), with the sharp edge that **`hasTrustDialogAccepted` is keyed by absolute path**, so the target picker must re-seed every pane cwd. `ANTHROPIC_API_KEY` blocks the interactive TUI on api-key approval — only `ANTHROPIC_AUTH_TOKEN` may be set, though `apply_env` currently sets both. Bracketed paste + `\r` submits at 0/10/30 ms, multi-line included. `--permission-mode auto` is prompt-free for Bash/Read (ran the testbed suite, returned the right count) where the default `manual` would wedge. `tauri::ipc::Channel` was **rejected** for now: under its 1 KB threshold raw payloads serialize to a JSON integer array (~4× base64), so Phase 3 ships per-pane event names + base64 + 16 ms/64 KB coalescing instead. New finding: `CLAUDE_CODE_CHILD_SESSION` leaks through env inherit and silently disables transcript saving — add to `env_remove`.
- **Deferred (stated):** Phases 1–6 unstarted. `tauri::ipc::Channel` revisited in Phase 6 behind a measurement. Broadcast amplification is the highest-consequence *new* failure mode (five peers that can all broadcast and are all instructed to be helpful — the old system was immune only because headless workers had no volition between turns); three mitigations are required together, none yet built: a hub-side per-pane token bucket, an explicit "never reply to a broadcast unless it names you" brief clause, and a visible per-pane messages/min rate. An instant write into the orch pane can land mid-line if the operator is typing; accepted, with a "hold" toggle as the fix if it bites.

## D-031 — Phase 1: the pane contract lands additively alongside the headless one; delivery becomes request/response so the log can never claim a send that didn't happen

- **What:** The D-030 contract, built **beside** the old surface rather than on top of it, so the workspace stays green and all 85 pre-existing tests pass untouched. New in `fleetor-core`: `pane.rs` (`PaneId`/`PaneState`/`PaneEntry`, serialized as bare strings — `"orch"`, `"worker-2"` — so the CLI arg, DB payload, event field and TS type are one thing; `FromStr` accepts `orch`/`lead`/`2`/`w2`/`worker-2`), `message.rs` (`Message` carrying the **body**, plus the single-sourced `frame_for_pane` / `frame_broadcast_for_pane` injection framings), and `brief.rs` (`orch_brief`/`worker_brief` for `--append-system-prompt`). `event.rs` gains `Message { id, from, to, body, group, accepted, detail }` and `PaneState { pane, from, to }`. `wire.rs` gains `Hello.pane`, four pane ops and `OpResult::{Delivered, Roster}`. `hub.rs` gains `AppCommand`/`DeliveryResult`, `Hub::with_app`, the four handler arms, `last_inbound_from` and a per-pane token bucket. New `crates/fleetor-server/tests/pane_messaging.rs` (14 tests) drives the whole surface in-process against a fake app.
- **Why request/response at the app seam:** `RunnerCommand` is fire-and-forget because a runner's job is asynchronous. `fleet send 3` is not — it needs a real yes/no, and only the pty registry knows whether pane 3 is alive. So `AppCommand::Deliver` carries a `oneshot` ack, and the hub **awaits it before appending the event**. That ordering is the whole point: the feed records what happened, never an intention. Keeping the seam in the hub (rather than collapsing routing into `src-tauri`) is what preserves in-process, zero-spend testing — a test can answer a delivery exactly as a live pane, a dead pane, a missing app or a wedged app would, and then assert on the log. The 2s ack ceiling exists only so a wedged app cannot park the CLI forever; the round-trip is a HashMap lookup and a pty write, and nothing in the path sleeps.
- **Naming deviation from the plan (deliberate):** the plan says "add `Op::{Send, Broadcast, Reply}`", but `wire.rs` already has all three with different shapes (`Send { to: u8 }`, `Reply { event_id, .. }`), so adding them under those names is impossible while the old surface lives. They land as `PaneSend`/`PaneBroadcast`/`PaneReply`; **Phase 5 deletes the originals and renames these to the bare verbs.** Likewise `PaneConfig` is a separate struct rather than fields on `HubConfig`, because six existing test files construct `HubConfig` by literal and a new field would break every one; Phase 5 folds them together.
- **Bug the tests caught, at the contract layer:** `Response` `#[serde(flatten)]`s `OpResult` into the same JSON object as its own `id`, so `OpResult::Delivered { id, .. }` produced a **duplicate `id` key** and failed to deserialize — every delivery would have come back as a client error. Field renamed to `msg_id`, and `wire.rs` now has a round-trip test over every pane frame so the next variant cannot reintroduce it.
- **L5, and why the rate limiter was pulled back out:** a per-pane token bucket was built and then **removed on operator direction** — nothing may sit in the delivery path that can stop a message from landing while messaging itself is still unproven. It was a guard against a hypothesis (a broadcast fountain) whose only power is to refuse sends, with hand-picked defaults nobody had measured; the failure mode it prevents costs tokens, the failure mode it introduces is *the product not working*. Mitigation 2 — the "never reply to a broadcast unless it names you" brief clause — stays, and is the right layer for this: it is prompt text with zero code in the send path, so it cannot cause a message to be dropped. Mitigation 3 (a visible per-pane messages/min figure) is Phase 4 and is likewise observation, not enforcement. The direct and broadcast framings differ (`[fleet · worker-1]` vs `[fleet · worker-1 → all]`) precisely so a worker *can* obey clause 2. If amplification turns out to be real, it comes back in Phase 6 behind a measurement — and behind a demonstrated fountain, not a predicted one.
- **Other decisions made here:** `reply` resolves against `last_inbound_from`, updated **only on accepted deliveries** — you cannot reply to a pane that never heard you (tested). Pane identity comes from `Hello.pane` and a connection that never declared one is refused rather than guessed at; a misattributed message is unrecoverable. `PaneId::from_str` is permissive and does **not** validate slot existence — the hub holds the roster, so it is the hub that rejects `worker-9`. `roster` is answered by the app, not the config: "this pane should exist" and "this pane is alive" are different questions with different owners.
- **Verified (zero spend):** `cargo test --workspace` — 99 tests across 24 binaries, 0 failures, 0 warnings; `cargo check` clean in `src-tauri`. Nothing is wired: `src-tauri` still runs the old pool fleet, and no pane op is reachable from the app until Phase 2 unwires it and Phase 3 builds the registry.
- **Deferred (stated):** everything Phase 1 deliberately does not do — no pty registry, no `fleet` binary, no UI, and the briefs are unvalidated against a real Flash worker (Phase 6). Rate limiting entirely (see above). The one thing left in the delivery path that can refuse a send is the 2s ack ceiling, kept because it protects the caller rather than policing it: without it a wedged app parks the `fleet` CLI — and therefore the agent's Bash call — forever.

## D-032 — Delivery-path audit: only a dead pane may refuse a message, and membership has exactly one source of truth

- **What:** Two guards removed from the send path, both introduced in Phase 1 and both capable of silently refusing a healthy pane. (1) `PaneState` no longer gates delivery on `Live`. `is_live()` stays as a *display* predicate for the roster and band; the delivery path uses the new `accepts_input()` — `!Dead`. (2) `pane_send` no longer validates its target against `HubConfig.slots`, and `pane_broadcast` takes its targets from the app's roster rather than config. `roster_ids()` is gone; `app_roster()` is the single read of fleet membership.
- **Why (1):** nothing tells us when `claude` reaches its prompt. `Spawning` is a *guess about a running process*, so gating sends on `Live` means a perfectly healthy pane refuses every message until the guess flips — and if the flip is never implemented, or is implemented against a banner string that changes next `claude` release, the fleet goes mute while reporting exactly the error it was designed to report. That is L1's shape: it looks like it works and it doesn't. Writing into a still-booting pty is buffered by the kernel and read when the TUI starts reading; that is a failure we can live with, whereas refusing a live pane is not. The asymmetry decides it — a delivery gate should only fire on a fact (the process is gone), never on an inference.
- **Why (2):** `HubConfig.slots` and the pty registry were two answers to "who is in this fleet", and they can disagree — a pane the app is running would have been rejected as `unknown pane worker-4` with no way for the model to correct it, and a config entry never spawned would have looked reachable. The machine holding the ptys is the only one that knows, so it is now the only one asked. Config is not allowed to veto it (tested: a pane outside `SLOTS` is reachable if the app runs it). The self-send check stays, because it compares the sender to itself and cannot be wrong.
- **Verified:** `cargo test --workspace` — 98 tests, 24 binaries, 0 failures, 0 warnings; `cargo check` clean in `src-tauri`. New/changed tests: a spawning pane accepts while a dead one is rejected and logged; membership is the app's answer; a pane outside the hub config is still reachable.
- **Standing rule this establishes:** nothing may sit between `fleet send` and the pty that can refuse on an inference, a prediction, or a second copy of state. The remaining refusals in the path are the app saying a process is gone, the app being absent, and the 2s ack ceiling — which protects the caller (a wedged app would otherwise park the agent's Bash call forever) rather than policing it.

## D-033 — A message body can escape the bracketed paste that carries it; framing now sanitizes at the pty boundary

- **What:** `frame()` passes every body through `sanitize()` before it becomes bytes for a pty. CRLF and lone CR collapse to newlines; tabs and newlines survive; every other control character is dropped. `Message::body` keeps the raw text — sanitizing is a property of the pty boundary, not of the message, and the log should record what was actually sent.
- **Why:** delivery wraps the framed text in `\x1b[200~ … \x1b[201~` then `\r`, which makes the body *data* only for as long as it contains no escape of its own. A body carrying `\x1b[201~` ends the paste early and every byte after it arrives as **live keystrokes** at a `claude` prompt — where `\x1b` cancels and `/` opens a menu. That is L3 ("delivery is remote control of a text field, not messaging") in its sharpest form, and it is reachable by any pane that can compose a message, including a worker quoting terminal output it just read. A lone `\r` is the same bug in miniature: it submits the turn, splitting one message into two.
- **Why strip rather than reject:** consistent with D-032 — a mangled message that lands beats a clean one that doesn't. No legitimate body contains ESC, and the Phase-0-verified multi-line case (`\n`, tabs) is preserved exactly.
- **Verified:** `cargo test --workspace` — 102 tests, 24 binaries, 0 failures, 0 warnings. Tests: a hostile body cannot escape its paste through either framing; CR becomes a newline rather than submitting; newlines and tabs survive; the record keeps the raw body.
- **Two findings from the same audit left as Phase 3 requirements, not built:** (1) the `fleet` CLI has **no client-side timeout** — `fleetor_ipc::Client::call` waits forever, so a wedged hub parks the calling agent's Bash tool indefinitely; the hub's ack ceiling does not protect the caller. (2) Broadcast legs are awaited **sequentially**, so a receiver that blocks multiplies the ack ceiling by the number of targets. Both are recorded against `deliver.rs` in the plan. Neither is fixed here, because both fixes add concurrency to the delivery path and the path's simplicity is currently worth more than its worst case.

## D-034 - Delivery is unbounded: every timeout, ceiling and success-heuristic removed from the message path

- **What:** Operator direction after a two-agent audit of `crates/`, `src-tauri/` and `ui/`. The 2s ack ceiling is gone, and with it `PaneConfig` entirely - `Hub::with_app(store, config, app)` is back to three arguments, and `ask_app`/`app_roster` simply `rx.await`. Three live bugs the audit surfaced are fixed in the same pass. No timeout, rate limit, retry, backoff, queue, batch, idle guard or delay constant now exists anywhere between `fleet send` and the pty.
- **Why remove the ceiling:** it could not do the job it was there for. The `AppCommand` is already in an unbounded channel when the timer fires, so a timeout cannot *cancel* the delivery - it can only cause the hub to report failure for a message that then arrives. The `fleet` CLI exits non-zero, the model reads its own Bash stderr exactly as the brief teaches it to, and resends. Net effect of the guard: duplicate messages plus a log that says "rejected" about a message sitting in the recipient's terminal. Waiting forever is the honest failure mode, and it is diagnosable - a hung `fleet` is visible; a phantom rejection is not.
- **Live bugs fixed in the same pass:**
  - **A broadcast leg hijacked the recipient's reply target.** `log_message` set `last_inbound_from[to] = from` on every accepted delivery including fan-out legs, so a worker mid-conversation with the orch had its reply target silently repointed by whoever broadcast last - and `fleet reply` is what the worker brief calls its usual move. This was the only path where a message could arrive somewhere it was never meant to go. Broadcast legs no longer register a reply target; a fan-out is not a conversation.
  - **A broadcast reported success if *any* leg landed.** `accepted` drove the CLI's exit code, and the brief has taught the model that a zero exit means the bytes reached a terminal - so a fan-out that missed three of four panes read as a complete one, with the failures buried in a `detail` that a zero-exit path never prints. `accepted` now means every leg landed.
  - **A poisoned mutex ended messaging for the process.** One panic while holding `last_inbound_from`, `waiters`, `lead_events` or the SQLite connection would make every subsequent delivery panic its connection task forever, surfacing only as "server closed the connection". All `.lock().unwrap()` in `hub.rs` and `fleetor-db` are now `.unwrap_or_else(|e| e.into_inner())`.
- **Audited and found clean (stated so it is not re-audited):** no rate limits, token buckets, quotas or caps remain on the pane path; no retries, backoff or circuit breakers; no sleeps, intervals, debounce, coalescing, idle guards or parking; no size limits or clipping of bodies; no bounded channels on the delivery path; no locks held across an await. Everything the sweep found in `supervisor.rs`/`quality.rs`/`runner.rs`/`gate.rs`/the shim belongs to the headless surface deleted in Phase 5 and is unreachable from any `Pane*` op.
- **Kept, with reasons:** `sanitize()` (D-033 - it stops a body escaping its own bracketed paste and becoming keystrokes, and it alters rather than refuses); the self-send guard (compares the sender to itself, cannot be wrong); the `Hello.pane` requirement (there is no other identity source, and it fails loudly per call); `emit` swallowing a store error (a log failure must never fail a delivery).
- **Known and accepted, not fixed:** the SQLite `append_event` is a blocking write on the response path behind one global connection mutex - consistent with the now-unbounded posture, and moving it off-path risks reordering the message log. Broadcast legs are still awaited sequentially. `last_inbound_from` is in-memory, so a hub restart silently breaks `fleet reply` until each pane is addressed again. A malformed frame tears down the connection rather than being answered - loud to the sender, so not silent. Each is recorded rather than pre-emptively engineered: the priority is proving the mechanism works end to end.
- **Verified:** `cargo test --workspace` - 104 tests, 24 binaries, 0 failures, 0 warnings; `cargo check` clean in `src-tauri`. New regression tests: a broadcast does not hijack a reply target; a broadcast alone gives its recipients nobody to reply to; a partial fan-out is not accepted.
