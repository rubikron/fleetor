title: "WP-15: the evaluator is a `PaneId` in no enumeration, its wake is a bus subscriber, and it reads the live run in place"
phase: "WP-15"
status: superseded
---

- **What changed.** `orch` calling `fleet handoff` now wakes a real interactive `claude` in a second Tauri window: `PaneId` gains a sixth variant `Evaluator`, the app lays the *live* run out for reading at `~/.fleetor/dev/retro/<run-id>/`, fetches the answer key, and spawns the pane there. The brief is compiled in from `~/harness/fleetor-eval/evaluator/brief.md` behind a new **`devmode` cargo feature** (`src-tauri/build.rs` → `OUT_DIR`); a default build carries none of it and has no reachable spawn path. Three conditions gate it and each fails with its own sentence: the feature, `dev::is_enabled()`, and the target being a prepared rewind-mission workspace.
- **Why a `PaneId` variant, and why the default lost.** The obvious reading of the veil is that a name `orch` has never heard of should not be in `orch`'s own contract at all. It has to be: the retro is a two-way logged conversation, and every name in this system's record *is* a `PaneId` — the CLI parses one before the socket, `Hello` declares one, `FleetEvent::Message` carries one from and to, and `fleet reply` resolves through a `HashMap<PaneId, PaneId>`. The alternatives were a spelling chosen to dodge a grep (the workaround `building.md` §6 bans by name) or reusing `operator`, which would put a lie in the log about who spoke. So the veil moved from *the name does not exist* to **the name is in no enumeration**, expressed once as `PaneId::is_fleet_member()` and filtered once in `PaneRegistry::roster()` — the single answer that feeds both `fleet roster`'s listing and a broadcast's legs.
- **The shape, stated as the inverse of D-051, because that is what makes both legible.** The operator is **in the roster listing and has no terminal**; the evaluator **has a terminal and is in no listing**. `has_pty()` and `is_fleet_member()` disagree in both directions, which is exactly why neither is derived from the other. A message to the evaluator is `accepted` — there is a real pty and bytes reached it — and Tier 1.5 needs no stretching.
- **The wake is off the message path, and the proof is a count that did not move.** It is a second `EventFollower` in `src-tauri`, downstream of D-020's persist-then-publish bus: `Hub::handoff` is byte-identical, no `AppCommand` is sent, and `tests/handoff.rs::a_handoff_asks_the_app_for_nothing_and_changes_no_later_send` is untouched and green. **One doc sentence was wrong and was corrected rather than left:** `Hub::handoff` claimed *nothing anywhere* read a handoff back. It now says *nothing on the message path*. What `task.rs`'s tripwire bars is a read that goes on to permit, order or refuse something; this permits, orders and refuses nothing — it changes what *exists*, the shape WP-16 named as allowed and WP-19 is held to.
- **An existing test's letter changed, and the replacement is stricter.** `no_pane_is_briefed_about_the_evaluator` grepped seven files for `evaluat`, one of them `pane.rs`, which the variant fails on day one. `pane.rs` came off **that one test's** list (it stays on the dev-mode one) and `nothing_a_pane_can_read_ever_names_the_evaluator` replaced it: the *rendered* orch brief, the *rendered* worker brief, `PaneId::roster()`, and the parse error a mistyped name produces. That asserts the property the grep was a proxy for — not "the source lacks the word" but "no pane is ever shown it" — and `pane.rs` could always have rendered a name it never spelled. The prose list also gained `prompts/scaffolding.md`, a fragment composed into both briefs that nobody had been checking. Net: seven greps became seven greps plus four behavioural assertions.
- **The live run is read in place, read-only, by the function that already existed** (`docs/notes/live-run-snapshot-notes.md`, measured). Rotation archives the *previous* run at bootstrap, so the run the evaluator wants is `_shell/state.db` with this process's writer holding it open. A read-only connection sees every committed row through an uncheckpointed WAL and does not disturb the writer; copying `state.db` alone provably does not (4 KB with no schema — D-058's finding, confirmed for a live run). So `archive::to_json` is called on the live file, `archive::freeze` is never called on it, transcripts are **copied** rather than moved, and no `Store` method and no third seam were added. `events.json` mid-run and `events.json` in `runs/` come from one function and cannot drift.
- **Two placements are load-bearing and neither is obvious.** The retro directory is under `~/.fleetor/dev/`, a **sibling** of `_shell/` — every pane's write guardrail has `_shell` as a root (D-065), so a snapshot inside it would be writable by the fleet being judged. And the evaluator's `CLAUDE_CONFIG_DIR` is outside `_shell/pane-config/`, because `harvest_transcripts` walks that directory and would file the evaluator's own reasoning into `runs/<id>/transcripts/` — handing the *next* generation's fleet the past retros WP-12 requires to be absent, by a code path nobody wrote.
- **Two live bugs the second window exposed, both pre-existing.** `pty::channel_key` matched on `slot()`, so `PaneId::Operator` already resolved to `orch`'s channel — harmless only because nothing spawns the operator, and a silent cross-render for any second slotless name. And `on_window_event` tore the **whole fleet** down on any `CloseRequested`, which with two windows is a six-pty kill on closing the wrong one. Separately, `capabilities/default.json` scopes permissions by window label, and a window missing from it gets no `invoke` and no `listen` with no error at all.
- **Tier 1.7 is narrowed here, not widened, and it is the one call worth re-reading.** The evaluator spawns `--permission-mode auto`, which `orch` does not get; its guardrail roots are its own working directory alone — not `_shell`, not `[fence] allow` — so what auto-approve can change is a strict subset of what any worker's already could. §9.2's trigger is *widening*. `manual` was the alternative and would park the pane on its first `Read` of a run archive while looking exactly like a healthy pane.
- **What would reverse it.** A first retro that produces nothing `orch` has to argue with — at which point the fault is the brief's prose or the mission's usefulness, and the fix is text or mission selection, not more machinery (D-060 already says so). Evidence that `auto` lets the evaluator change something it should not, which is one word in `spawn::evaluator_command`. Or the retro directory's transcript copies growing enough to matter, whose answer is a size column and an operator-driven delete, as D-058 reserved for `runs/`.
- **Verified:** **213** workspace tests green, up from 210 — the only `crates/` diff outside `pane.rs`'s three new tests is one corrected doc comment in `hub.rs` — and **165** shell tests green, up from 143: 134 lib (including 2 new in `pty` and 3 in `runs`), 4 dev-mode, **8 new in `tests/evaluator.rs`**, 11 real-pty, 8 write-guardrail. `cargo test --features devmode` green at 165 too (the `evaluator.rs` suite swaps its default-build assertion for the compiled-in-brief one). `cargo build --features devmode` succeeds against the real brief; with `FLEETOR_EVAL_HARNESS` pointed at nothing it fails at `build.rs:68` naming the absolute path. `strings` finds the brief's version stamp **0 times** in a default binary and 2 times in a `devmode` one. `npx tsc --noEmit` and `npx vite build` clean. **Not verified:** no fleet has been started, so the window has never been on screen, no evaluator has reached a prompt, and no retro has happened — the same gap D-062 and D-065 record, one package larger. No live spend.
