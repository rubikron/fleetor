Verdict

Design philosophy

Build the parts that record and approve. Not the parts that help.

FLEETOR runs five Claude Code terminals against your repo. One is your own Claude ("orch"). Four are cheaper, weaker models ("workers"). This document proposes how the system should learn and improve over time.

The core argument: anything we build to compensate for a weak model becomes dead weight when a better model arrives. Anything we build to keep records, or to approve changes before they stick, gets more useful as models improve — because a stronger model can do more damage, faster.

So the rule is: put the smart parts in the observer, never in the message path.

Four principles

One for each of the four goals you set.

1 · Require evidence, not arguments

goal: justified novelty

When an agent says it is confident, that tells us very little. All five agents run similar models, so five agents agreeing is closer to one agent answering five times. Weak models make this worse — they tend to agree with whoever spoke last.

So a proposal has to point at something that happened and can be re-checked — a specific log entry, a failing test, a merge conflict. "We think X would help" gets rejected. "X happened three times, here are the log IDs" gets considered.

This standard already exists in the project. Decision D-031 says the rate limiter only comes back if a real problem is measured, not predicted. This is that rule applied everywhere.

2 · To add something, remove something

goal: cleaning up context clutter

Systems that append to a memory file always rot. After twenty sessions the file is 40 KB of advice that contradicts itself and describes situations that no longer exist.

Writing more carefully does not fix this. A size limit does. Cap the file, and adding a line means deleting a line. The question "is this worth more than what is already there?" gets asked every time instead of never.

A cap is also the only cleanup method that works when you have no way to measure quality — which is our situation.

3 · State what you don't know before you start

goal: integrity and diligence

Right now, "do I know enough to do this properly?" gets answered at the end, informally, by the same agent that wants to be finished.

It should be answered in writing at the start. Diligence is not confidence. It is a stated reason the work will succeed — written so that you can later check whether it was wrong.

4 · Treat each restart as a save point

goal: set a goal, do, learn, reflect, optimize, repeat

A pane's instructions are fixed when the process starts and cannot change while it runs. Instead of working around that, use it. It gives us something most agent systems never get: we can tell which version of the instructions produced which result.

Inside one run, the instructions never change. So the outcome can be traced back to a specific, named version of them. A memory file that changes continuously can never support that claim — it can only say things got better or worse while everything moved at once.

startknown setup
workdo the task
logrecord results
reviewread the record
proposea change
approvehuman
next runuses it

The approval step is what makes this a cycle instead of a random walk. Remove it and every change feels like an improvement.

Two rules that keep this safe

Keep the message path simple

Nothing between fleet send and the target terminal is allowed to delay, block, reorder, drop or edit a message. That is an existing project rule (Tier 1.4) that has been debated and upheld twice.

So no learning feature can live there. But watching and reporting is allowed where blocking is not — and that turns out to be enough.

Approve at restart, not per message

We never need to stop a message. We need to stop a bad conclusion from carrying into the next run.

The project already committed to this. Tier 1.8 was written before any feature needed it: "Shared knowledge merges only after review. Unreviewed memory poisons every pane."

Together, these two rules are what let this scale to a much stronger model. You do not supervise a smarter system by arguing with it live, and you do not do it by dictating its methods. You keep a record it cannot edit, and you keep approval over what it carries forward.

What we are ruling out

  • Agents agreeing on rules mid-task. It creates message storms, and there is nowhere for the agreement to be saved anyway.
  • Anything in the message path. If a feature needs to block a message, it is the wrong feature.
  • Memory files with no size limit.
  • Agents scoring their own work. That measures confidence, and we already established confidence tells us nothing.
  • Rules about how an agent should work. Those expire when the model improves. Rules about what it can touch do not.

Constraints

There are four ways into a pane. Only one of them works while it is running.

Every design here had to work around one fact: a pane's instructions are set when the process launches and cannot be changed afterward. Each pane is a real, unmodified claude process, and our software sits around it, not inside it.

We call these four entry points "doors" throughout this document.

1
The briefThe instructions we write for each pane, passed as a command-line argument. Added after Claude Code's own instructions, so it cannot override them.
at launch only
2

4
MessagesText typed into the pane's input box by another pane. The only way to reach a pane that is already running.

To tell a running pane something, it goes through door 4. Everything else waits for the next launch. There is no fifth option.

Why the restriction helps

Most agent memory systems change continuously, so there is never a clean point where you can say "these instructions produced this result." FLEETOR gets that for free. Within a single run the instructions are provably fixed, which is what a controlled comparison needs.

Three designs use this directly. Bake-Off turns it into an A/B test. Carryover turns it into the system's only way to forget things. Shift Notes uses door 2, which is currently unused for workers.

Method

Fifteen designs, then an adversarial review.

Five agents each worked a separate problem area so they could not converge on the same idea. Each produced three designs plus a list of ideas they rejected. A sixth agent then read all fifteen at once, with the codebase as the source of truth, and tried to break them.

15designs written
11survived review
27ideas rejected

23 rejected while generating, 4 more rejected during review.

Why the rejected ideas are included

Several rejected ideas are the first thing most people would suggest: pulling relevant docs into a running pane, having agents vote, attaching confidence scores, auto-compacting context. Each fails for a reason specific to how FLEETOR is built. Those reasons are worth more than the surviving designs.

Three reasons came up repeatedly:

  • It rebuilt the deleted supervisor. Any component that watches all five panes and makes decisions about them, no matter what it is called.
  • It sat in the message path. Tier 1.4 is not negotiable and it removes a whole class of otherwise sensible designs.
  • It made output look more rigorous without adding information. Confidence scores and vote counts do this.

How to read a design

Each one has a claim, the problem it solves stated as something that goes wrong today, an implementation specific enough to start coding from, and a two-column summary: why it should work, and the strongest argument against it.

Where an objection could not be answered, the design says so. Several of the better designs have a real unresolved risk.

Each also lists what would prove it wrong — the observation that would tell you to stop. A design without that is an opinion, not a proposal.

01 · Memory & learning

Shift Notes

A worker cannot be taught anything while it is running. So the fleet's memory is a short, reviewed list of facts left in the worker's config folder for the next process that starts in that slot.

door 2~300 lines≈1.5k tokens per paneeasy to undo

The problem

A worker learns at 14:02 that the test suite fakes the system clock, so any test using the real clock fails. At 14:40 the fleet restarts and that knowledge is gone.

It was never stored anywhere useful. It sits in one row of the events log that nothing reads. All four workers hit the same trap separately, then hit it again next session.

Meanwhile the one place that knowledge could live — the worker's config folder — holds two setup values and nothing else. Door 2 is available and completely unused for workers.

How it works

Before each worker launches, we write a short facts file into its config folder. Claude Code reads that folder at startup, so the facts arrive as part of the pane's starting knowledge. It is not in the repo folder, so it never shows up in git status.

The notes live in a small git repository at ~/.fleetor/lore/. That gives us review (git diff), history (git log), and undo (git revert) for almost no code, because git already does all of that.

Nothing writes to it automatically. The operator drafts a note, usually with help from orch. The briefs do not change: a brief is a job description, a facts file is accumulated knowledge about this specific repo.

// crates/fleetor-core/src/lore.rs
pub const MAX_NOTES: usize = 24;
pub const MAX_NOTE_CHARS: usize = 240;

pub fn render_handbook(template: &str, me: PaneId, notes: &[Note]) -> String;
pub fn budget(notes: &[Note]) -> Result<(), String>;

No new event type is needed. One line in the activity log per fleet start: "handbook: 11 notes from lore @9f2a3c1 installed in worker-1..4". That makes "which facts was this pane running?" answerable later, which is what you need if a note turns out to be wrong.

Why it should work

The storage lasts across restarts and a human approves every change.

It resists rot because of one mechanism: 24 notes is a hard limit, so note 25 cannot be added without deleting one. An unlimited file only grows, because every line looks reasonable on its own. A capped file forces the comparison "is this worth more than that?" every time.

Main objection

This is just a CLAUDE.md for workers, and those always fill up with stale generic advice. That is fair. The cap forces deletions, git diff makes each change reviewable in seconds, and the log line makes a bad note traceable.

What we cannot fix: an operator who approves changes without reading them. If review becomes a habit rather than a judgment, this becomes exactly the stale file the objection describes. The cap slows that down. It does not prevent it.

What would prove it wrong

Run the same task twice, once with the facts file and once without. If the workers behave the same, the notes are not doing anything. Also: if after ten sessions the notes are longer and vaguer instead of shorter and sharper, the size limit is not creating enough pressure.

02 · Memory & learning

Double Entry

Each session produces two separate records: what the agents said, and what they actually changed. Put them side by side and look for disagreements.

reads only~350 linesno token costagents never see it

The problem

A busy fleet and a productive fleet look identical. The messages view fills up with green "accepted" rows and it feels like progress. The project README already says this about message storms: "a token fire that looks like a working fleet."

There is currently no way to answer "did worker-3 do any work in the last forty minutes, or did it only send messages?"

How it works

It adds nothing to any pane. It joins two sources the system already has and never looks at.

ColumnWhere it comes fromWhat it shows
Talkthe events logmessages sent, received, broadcast, rejected; longest gap
Workgit diff --shortstat in each worker's folderfiles, lines added, lines removed, commits
Session boundarythe existing pane-start eventalready marks every fleet start — no new event, no timer

Flags are facts, not opinions: talked but changed nothing, changed things but told nobody, silent, had messages rejected, sent far more broadcasts than the others, two workers touched the same file.

No combined score, ever. Two raw columns and a few flags.

Why it should work

It applies the product's existing standard one level up. "Accepted" is an honest label because it reports what the system can actually observe. A git diff is the same kind of fact — not a claim about the work, but the work itself. A worker's "done, tests pass" can be checked against "0 files changed" in one glance.

The agents are never told this exists. A measurement that the measured party cannot see cannot be gamed by them. Gaming a metric requires knowing about it, and there is no channel here that tells them.

Main objection

Lines changed is a bad productivity measure, and this dashboard will make the operator favour workers that write more code. Partly true. There is never a combined score, and flags fire on structural conditions rather than size. But the operator can still mislead themselves, and we cannot prevent that mechanically.

"This is the deleted supervisor." Easier to answer: the supervisor assigned work, ran it, blocked it and judged it. This has no way to send messages, no connection to any terminal, and produces nothing an agent can read. The line to hold: if anyone ever proposes feeding a flag back into a message, this has become the old system and should be deleted.

What would prove it wrong

If flags never fire, the tool is too blunt. If they fire on every row, they are noise. Best test: have the operator write down their impression of a session before opening the report. If it never surprises them, it is not worth the screen space.

03 · Memory & learning

Bake-Off

Four identical worker slots plus fixed-at-launch instructions make a controlled experiment that nobody is running. Give two workers one version of the brief and two another, then compare.

door 1~150 linesno extra tokens
Rejected during review

Two workers per group over one session is not a real experiment, and the design admits this then proposes shipping anyway. That makes results look more rigorous than they are, which is the specific failure this project cannot afford. It also conflicts with Seats, which makes the four slots deliberately different. The useful 90% needs no code: edit the brief, run one session, read the result. Do that first.

The problem

The README lists this as a known gap: the briefs have never been tested against a real worker. Every edit to the worker brief is a guess.

One brief clause — "never reply to a broadcast unless it names you" — is the only protection against message storms. The rate limiter was deliberately removed on the grounds that this clause works. Nobody has ever checked whether it does.

The longer-term version is worse: if a much better model were dropped into these panes, how would anyone notice that half the brief had become unnecessary? Instructions accumulate because adding one feels safe and removing one feels risky, and nothing measures either.

How it works

  • If a second brief file exists, it is the challenger. It goes through the same validation, so it cannot drop the safety clauses.
  • A broken challenger produces a warning and a normal, uniform fleet. Never a half-split one.
  • Groups are assigned by slot and recorded before any pane starts, so the record cannot be reconstructed incorrectly afterward.
  • A rotate setting swaps the groups next session, cancelling out differences caused by slot position.

Why it was proposed

It turns brief editing from taste into measurement, and it is the only design here that gets more useful as models improve.

The obvious challenger for a stronger model is a shorter brief. Delete the hand-holding, run a session, and if nothing gets worse, ship the shorter version and save those tokens permanently. Every other proposal here adds instructions. This is the only one that can remove them with justification.

Why it was rejected

Two workers per group, one session, no real randomization. The design concedes this and proposes shipping regardless.

It also cannot catch rare failures. A message storm that happens once in twenty sessions will not show up. If the operator reads a clean result as proof the broadcast rule is unnecessary, this causes exactly the damage it was built to prevent.

What survives

Run it manually. Edit the brief, run one session, look at what happened. That answers the important question — does brief text matter at this model tier — before anyone writes code to automate group assignment.

04 · Checking claims

Receipts

A worker should not be able to just say "done, tests pass". It runs fleet done "pytest -q", and the tool reports the real exit code, the commit, and the last lines of output.

doors 1 + 4~260 linesnew commandno database change
Survived review · build second

The only design that changes what the log contains rather than what someone calculates from it. Every later measurement gets better on a log with receipts in it, and none of them can add evidence that was never recorded.

The problem

worker-2 finishes and sends "done — pytest passes, 41 tests green". That sentence is the only record. It is a claim about a process that ran, or did not run, in a terminal nobody watched.

From orch's position three situations look identical:

  • The tests passed.
  • The tests passed, then the worker changed the code.
  • The worker never ran them and wrote what a finished task sounds like.

Weaker models are good at the third one. Sounding finished is the cheapest thing a language model produces, and right now it is the only thing we record.

How it works

A new command runs the check locally before sending anything, then sends the result as a normal message. No changes to the message system, the database, or the event types — the message body already gets logged, so receipts are stored automatically.

[receipt] fleet/worker-2 @ a3f9c2 · clean
$ pytest -q
exit 0 · 4.8s
  41 passed in 4.71s
re-run: git checkout a3f9c2 && pytest -q

Why it should work

The model stops being the source of the claim. The exit code comes from the operating system. The model chooses which command to run; it does not write the verdict.

A false claim becomes checkable instead of invisible. A worker could run fleet done "true". But the exact command is recorded next to the claim. You cannot verify a paragraph of English; you can read a command string in two seconds and see it is not a test suite.

It works for better models too. This is not a restriction on the writer, it is a format for the reader. Running one command is less effort than writing a paragraph making the same claim.

Main objection

Nothing forces a worker to use it. A weak worker will keep writing "done, tests pass" because that route always exists — blocking it would break the message rule.

True, and not fixable without breaking a core rule. What we can do is make the honest path also the easy path: the command is fewer tokens than a completion paragraph and does the work of running the tests too. This raises the ceiling on evidence quality. It does not raise the floor.

What would prove it wrong

Run 20 real tasks. Count how often a completion claim comes with a receipt. If adoption is under about 20%, the brief wording failed and that needs fixing before building anything else on top.

05 · Checking claims

Cheap Twin

When an agent picks an unusual approach, it also builds the obvious alternative and measures both with the same command. FLEETOR has spare workers and separate checkouts, so it can afford to try both.

doors 1 + 4~150 lines on top of Receipts
Rejected during review

The design concedes that a motivated agent will pick a weak alternative to beat, cannot fix it, and defers the fix to a design that does not exist. What ships is a mechanism that turns a preference into a number, which is worse than having no number. It also creates a temporary git checkout on every use, in a system that already has to clean up stale checkouts. The naming half survives as one sentence in the brief.

The problem

worker-1 builds a custom data structure for a lookup that a standard hash map would have handled. Its message to orch explains the choice well — cache behaviour, access patterns, a paragraph of reasoning.

The explanation is coherent and impossible to disprove. Orch cannot tell "this was necessary" from "this was interesting to build", because the thing that would settle it — the simple version, measured — does not exist.

So unusual approaches get accepted by default, defended by whoever wrote more convincingly.

How it would have worked

A brief clause: when you choose a non-obvious approach, name the obvious one in the same message. If it is cheap to build, build it and measure both.

[twin receipt] fleet/worker-1 @ a3f9c2  vs  8c11ab
$ python -m bench.lookup
  version A  exit 0 · 1.9s   custom structure
  version B  exit 0 · 2.1s   standard hash map
10% difference — below what this benchmark can measure

That last line is generated by the tool, not written by the model. It computes the difference and refuses to call anything under a set threshold a real result.

Why it was proposed

It changes the unit of justification from an argument to a comparison. "This is fast" cannot be disproved. "This is 10% faster on this benchmark, which cannot measure below 20%" can be.

It also puts the work in the right places: building the simple version is easy, so a cheap worker does it; deciding whether the difference justifies the complexity is judgment, so orch does it.

Why it was rejected

"Obvious" is not defined, and the agent choosing the alternative is the agent that wants its own approach to win. It can nominate something weak, beat it easily, and call that evidence.

The design admits it cannot close this and says the real fix is having a different pane pick the alternative — which is a design nobody wrote. Until that exists, this produces numbers that look like measurements and are not.

What survives

One sentence in the brief: name the obvious alternative you did not choose. That costs nothing, leaves an audit trail of what was considered, and skips the part that generates misleading numbers.

06 · Checking claims

Callsign

Every message already has an ID. Put six characters of it in the message header. Then two things become measurable: whether a message was actually read, and whether three agents agreeing are three opinions or one opinion repeated.

doors 1 + 4~350 linesno database change
Survived, with a change

The valuable part is buried inside the design's own objection. Build the automatic half only — have fleet reply attach the ID automatically. The 180-line analysis graph will fail its own success threshold on a weak-model fleet.

The problem

We cannot tell if a message was read. "Accepted" means the text reached a live terminal. Between that and "the agent acted on it" are three unknown steps: read, understood, acted. The system says this honestly everywhere and then offers nothing further — so in practice orch treats accepted as read, because there is nothing else available.

Agreement is being misread as confirmation. Orch broadcasts an idea. Three workers reply agreeing. That looks like consensus. It is one idea echoed by three copies of the same model, all primed by the same sentence. The log already contains the evidence that this is what happened. Nothing reads it.

How it works

[fleet · orch #7f2a] I think the parser should be recursive-descent
[fleet · orch → all #7f2a] …

One brief sentence asks agents to include the ID when replying. Then a read-only analysis over the existing log can tell whether replies trace back to a single source.

The status label becomes "echoed" — never "read", never "unread". An echo proves the message was seen. Silence proves nothing, and labelling it "unread" would repeat exactly the mistake the accepted/delivered distinction exists to prevent.

Why it should work

An agent cannot quote an ID it never received. That is the only proof of reading that can exist here, because nothing else travels back across the terminal boundary.

The agreement analysis is the genuinely new part. Whether evidence is independent is a question about how information spread, and almost no multi-agent system can answer it because almost none has a complete ordered record of every message. FLEETOR does. "These three agree" and "these three came from one source" become different rows in the same view.

Main objection

Weak workers will forget to include the ID, and the analysis becomes mostly "unknown" — honest, but useless.

The fix is in the design's own text: fleet reply can attach the ID automatically, since the system already tracks who last messaged each pane. That makes the most-used command work correctly with no cooperation from the model at all. That half should be built; the analysis graph should wait.

Also conceded: an agent could quote an ID it saw elsewhere. So the proof is weaker than "read this message" — it is "this text reached this pane". Still more than we have today.

What would prove it wrong

Measure how often replies include the ID. Under 40% even with automatic attachment, the analysis is not worth shipping. Separately: take ten cases where the operator judged the replies genuinely independent and check whether the tool agrees. If it disagrees, it is measuring the wrong thing.

07 · Context budget

Loadout

Each pane's starting knowledge is built from an explicit list, rebuilt from scratch each launch, and its token cost is shown on the activity feed before the pane's first turn.

doors 1 · 2 · 3~600 linesdefault behaviour unchanged
Survived, cut down

The token counter is the deliverable and costs about 50 lines, not 600. The delete-and-rebuild file manager is the risky half and the source of conflicts with two other designs. Ship the counter, defer the rest.

The problem

Nobody knows what a pane starts with. A worker gets two config values plus whatever CLAUDE.md the repo happens to contain. If that file is 9,000 tokens of style rules for a language the worker is not touching, four workers pay for it four times, every launch, and nothing reports it.

The same applies in reverse to orch, which inherits the operator's entire config folder — every skill, every memory file, every connected service, whether relevant or not.

So we get both failures at once: workers that waste turns rediscovering things nobody told them, and orch carrying a setup nobody chose for this job.

The config folder also accumulates. It is merged, never rebuilt. Something written there in one session is still there next month.

How it works

Before each launch, the managed part of the config folder is deleted and rewritten from a list. That delete-and-rewrite is the only cleanup mechanism available on door 2, and it costs nothing.

Two optional new slots in the brief: fleet-wide standing context, and a per-slot role note. Both optional, so existing custom briefs keep working.

Then the cost is reported, once per pane:

worker-2 starting context ≈5,090 tokens
  brief 640 · house notes 310 · role 190
  · repo CLAUDE.md 2,950 · skills 1,000

Going over budget produces a warning, never a refusal — a fleet that will not start is worse than one carrying extra tokens.

Connected services are deliberately not on the list. Skills are text files; service connections carry credentials, and giving four auto-approving workers the operator's credentials is a security decision, not an implementation one.

Why it should work

You cannot clean up what you cannot see. The highest-value piece here is a number on a screen.

It also scales the right way: the budget is set per role, so a weak model at 6k tokens and a much larger future model at 200k are the same design with a different config line.

Main objection

This is a config file nobody will fill in. Four workers with an empty list is what you have today, plus a parser. Largely true.

The defence: the empty list reproduces today's behaviour exactly, so the only thing that ships unconditionally is the measurement. If the token counter never once causes the operator to delete something, the design failed — and that is a two-week test, not a research project.

What would prove it wrong

Run a worker for 30 turns with and without added context. Count how many commands it spends orienting itself before its first edit. If that does not drop, the tokens are not earning their place.

08 · Context budget

Carryover

Restarting a pane is the only way this system can ever forget anything. So make it deliberate: the pane writes down what its replacement should know, the operator edits that, and the next run starts fresh carrying only that.

door 1 + a local file~250 linesaffects one pane only
Survived, barely — measure first

The design names a cheaper test than itself and then proposes 250 lines of code before running it. Measure how often operators actually restart panes. If the answer is "almost never", this is unreachable regardless of how good it is.

The problem

Nothing removes context. There is no compaction, no cleanup, no forgetting anywhere in the system — and there cannot be, because we sit outside an unmodified Claude Code process and cannot reach into its memory.

So the only way to clear a pane is to kill and restart it, and today that means total amnesia. A worker three hours in is carrying two hundred turns of dead ends, half of them wrong, and clearing them throws away everything useful it learned too.

So operators do not restart. Panes get worse over time.

How it works

A pane's life becomes a numbered run in a fixed slot. worker-2 run 4 is a new process in the same slot, same folder, same peers, carrying a note its predecessor wrote.

  • A new command writes to a local file. It never touches a terminal or the message system, so the message rule does not apply to it at all.
  • The file is plain text in the FLEETOR folder, so the operator can open and edit it in a text editor before clicking restart. That editing step is the review, and it costs nothing to build.
  • Old runs drop off by age when the file exceeds a size limit, and a warning names what was dropped. This is the only place in FLEETOR that deliberately forgets something, and it forgets by age — the one rule that needs no judgment.
  • Restart shows a summary first: "worker-2 → run 4. brief unchanged, house notes changed, carryover 412 bytes (new)."

Why it should work

It turns the system's biggest constraint into a feature, and gives the "reflect" step somewhere to write to.

It is the only proposal here that removes context rather than adding it.

It also scales in both directions: a weak model needs this every few hours because it fills up fast; a much larger future model needs it rarely and writes a better note. Same file, same command, different frequency.

Main objection

A weak worker asked to summarize itself will write confident nonsense, so this creates self-poisoning memory. Partly conceded — the summaries will often be poor.

Two things limit the damage. The note only ever goes back into the same slot, so it cannot affect other workers, and the next restart clears it. And it is a plain file the operator edits, at the moment they are already looking at that pane.

What we cannot fix: an operator restarting a pane late at night will probably not read 400 bytes first. The size limit makes a bad note small, not harmless.

What would prove it wrong

Run a worker to exhaustion twice, once with a carryover note and once without. Measure turns until the first useful edit. No difference means re-deriving context was never the real cost.

Cheaper test first: log how often operators restart panes for one week. Almost never means this is unreachable, and the real problem is that restarting feels risky — which is a different design.

09 · Context budget

Hearsay

Anything a worker learns stays private and dies at restart until the operator approves it. Approval is the only way a fact reaches another pane, and it takes effect at the next launch.

door 4 reversed → door 2~1,000 lineslargest in the set
Rejected during review

About 1,000 lines, a new event type, two protocol changes, two new commands and a UI panel — to build a queue the operator empties by hand. The new command produces no work and costs a tool call, which is exactly the reasoning another design used to reject a similar idea. The "pull facts" half fails harder: the worker who would broadcast a question is the worker who will not think to look it up. The useful part already exists inside Shift Notes at a tenth the cost.

The problem

worker-1 discovers the test command is just test, not npm test. Its options are to tell orch (whose context fills up, and the fact disappears) or to broadcast it — which interrupts three other panes mid-task and is exactly what the brief tells it not to do.

So it usually says nothing, and the other three workers each discover the same thing separately.

The root cause: messages only push. A pane's only way to inform another pane is to write into that pane's context, uninvited, while it is working. There is no way to offer a fact and let someone take it when they need it.

How it would have worked

  • A command that files a fact without sending it anywhere. It never touches a terminal, so nothing waits on it.
  • The operator approves or discards from a panel. Approval appends a second record — the log stays append-only.
  • Approved facts get written into every worker's config folder at the next launch.
  • A second command lets any worker look up the approved facts on demand, instead of broadcasting a question.

Why it was proposed

It implements a rule the project wrote down before the pivot and never built. It puts the human in the one role a human genuinely belongs in — deciding what becomes permanent.

And the policy stays correct as models improve: a better model writes better facts, but "nothing permanent without review" does not become wrong.

Why it was rejected

Cost. It is the largest design in the set and most of what it delivers already exists inside Shift Notes' git-based facts file.

The lookup command has a specific flaw: the worker who would interrupt everyone with a question is the same worker who will not think to check a reference first. The people it is designed for are the people who will not use it.

The design also names its own tripwire honestly: the day orch is allowed to approve facts instead of the operator, this becomes the system the project deleted.

What survives

Shift Notes covers the same need with a git repo, a size cap and git diff as the review step.

10 · Coordination

Crosscut

Two workers editing the same file is not something to declare in advance. Git can already tell you whether two branches will conflict. Nobody is asking it.

reads only~300 linesstores nothing
Survived, cut down

Using git's own merge check as the source of truth is genuinely good and genuinely not a locking system. But it is the only design in fifteen with a background task that wakes up and makes decisions about all five panes, which is the shape the project deleted 3,500 lines to remove. Ship it exactly as its own test says: logging only, no command, no brief changes.

The problem

worker-1 and worker-3 work in separate checkouts. Both rewrite the same file. Nobody finds out until the operator merges the two branches by hand, hours and thousands of tokens later.

The only current protection is a line in the brief asking workers to mention when they are about to touch a file someone else might be working on. That asks a worker to know something it has no way of knowing — what is in another pane's checkout.

The isolation FLEETOR built is real. The point where those branches have to come back together is real. Nobody is looking at it.

How it works

Read each worker's checkout to find which files it has changed. A file changed in two checkouts is a possible problem — but two workers can edit opposite ends of a file all day and merge fine.

So it escalates to git's own merge check. If that reports a conflict, these two branches will not merge — and that is not our opinion, it is the exact same calculation the eventual merge will run.

Results are reported on change only: a new conflict reports once, a resolved one reports once, an ongoing one says nothing. Output goes to the activity feed and to an on-demand command any worker can run.

The checker cannot send messages to any pane. It has no pane identity and is deliberately not given one — something that can write into panes but is not a pane is authority the operator cannot see.

Why it should work

It replaces a promise about the future (I am claiming this file) with a report about the present (these branches currently conflict). Only the second one can be verified.

There is no state to acquire, expire or clean up after a crash. Kill the app and the next check is just as accurate.

Main objection

This is the file-locking table the project already deleted, renamed. Partly fair, and the difference matters. The old system stored claims that outlived the model's memory of making them, needed expiry rules, and lied whenever a worker forgot. This stores nothing and re-reads git every time. The old system could refuse an edit; this returns a number the model can read.

Unresolved: it uses a non-zero exit code to mean "conflict found", and the project's hardest-locked rule is that non-zero means "the message was not delivered". That needs different wording before shipping.

What would prove it wrong

Run the checker with logging only — no command, no brief clause, no feed messages — and count real conflicts over ten sessions. Fewer than one per session, or conflicts the merge resolves without help, means the separate checkouts already solved this.

11 · Coordination

The Posture Ladder

A worker's permissions should be a defined level that tightens automatically when it misbehaves and widens only when the operator approves.

door 2~350 linesmost expensive in the set
Rejected — the one not to build

Highest cost in the set, and its own success test predicts the outcome: every worker sits at the same level for twenty sessions and the ladder turns out to be a config value with extra steps. It stores per-pane state in exactly the shape the project deleted, and it kills a running pane based on a calculated judgment about that pane's behaviour — which is blocking work, whatever the code is called. Its one useful level is the default one, which is The Fence's config file without the ladder.

The problem

Every worker runs with the same permissions, forever, whether it is a weak model on its first turn or a strong one on its thousandth. The config file explains why: the safe default wedges a worker on its first tool call with nobody watching to approve it. So the project picked the only option that keeps panes alive and then had nowhere else to go.

There is one setting and it is fixed.

How it would have worked

Four permission levels written into config files, read at launch. Nothing changes while a pane runs.

LevelWhat it allows
ProbationRead-only plus the fleet commands. No file writes, no commits.
Confined (today's behaviour, finally written down)Edit inside its own checkout. No pushing, no switching to the main branch, no edits outside.
TrustedConfined, plus pushing its own branch.
PeerTrusted, plus read access to the main checkout. Requires operator approval.

Evidence comes from the log and from git: commits on the wrong branch, writes outside the checkout, messages sent to dead panes, share of messages that were broadcasts.

The asymmetry was the point. Tightening happens automatically. Loosening is only ever proposed to the operator, with the evidence attached — so they are asked about widening only, which is rare, and never about tightening, which is safe.

Why it was proposed

It makes the guardrail respond to behaviour rather than to which model is in the seat. A much better model in the same slot earns its way up on the same evidence, and the remaining ceiling is the operator's judgment.

Why it was rejected

Its own success test predicts failure: if every worker sits at the same level for twenty sessions, this is a constant pretending to be a mechanism.

It stores per-pane state that outlives the process that earned it, which is the exact shape of the deleted locking system.

And killing a running pane based on a calculated verdict about its conduct is blocking work, regardless of what the module is named. The design itself flags this and says it is unsure the line is in the right place.

What survives

The "Confined" level, written down once as a fixed config file. That is The Fence's permission seed. No ladder, no scoring, no state.

12 · Coordination

Open Loops

A message from A to B with no reply back is an open loop. One that has been open longer than that pair's normal reply time is the only thing here worth interrupting the operator for.

reads the log~200 linesadjusts itself
Survived, cut down

Ship the roster columns. Drop the alert — its threshold is calculated only from conversations that ended, so the messages it most needs to ignore can never raise it.

The problem

Three complaints turn out to be one problem.

  • "Nothing routes by load" — true, because the roster command returns a pane name and whether it is alive, and nothing else. Guessing is genuinely all orch has.
  • "Messages are unstructured text" — true of the body, false of the envelope. Sender, recipient and timestamp are structured, and nobody uses them.
  • "The operator's attention is scarce and nothing protects it" — the feed reports on binaries and file paths, and says nothing about a worker stuck waiting for an answer.

The orch brief already describes this: "they are blocked on you in practice even though nothing blocks in code." Nothing measures it.

How it works

Read the log. Open a record for each message; close it when the recipient replies. For each pair of panes, look at how long past replies took, and use that as the normal range. No threshold at all until there are at least three past examples.

orch       live    editing src/cli.rs      owes worker-1 (4m)
worker-1   live    editing src/parser.rs   waiting on orch (4m, usual 40s)
worker-2   live    quiet 6m                —

Why it should work

It invents no new data, adds no new writer, and asks no pane to declare anything.

The threshold adjusts itself. A weak worker that normally replies in eight seconds gets an eight-second-scale threshold; a stronger model that thinks for four minutes gets a four-minute one. A fixed timeout would be wrong for both.

Main objection

An unanswered message is not a blocked worker. Most messages are status updates, and this will spend the operator's attention on noise while claiming to protect it.

The self-adjusting threshold was supposed to handle that, but it has a hole the design admits: a status update that is never answered never closes, so it never contributes to the calculation, so it never raises the threshold. The threshold is built only from conversations that ended.

No clean fix. The roster half works on its own and costs no attention.

What would prove it wrong

Run it silently for thirty alerts, show the operator each one afterward, and ask: did you want to know? Under 50% yes, drop the alert and keep only the roster columns.

13 · Handling stronger models

Seats

Treat the fleet as five configurable seats rather than five identical workers. Each seat declares its own model, brief detail level and permissions. Detail level changes with capability. Safety rules never do.

doors 1 + 3~270 linesdefault is today, exactly
Survived review

A config change to code that already reads three settings from one place. No new runtime machinery. The split between "detail that scales" and "rules that don't" is the right line to draw.

The problem

The config file has one worker section, so all four workers are the same model with the same brief. Three concrete failures follow.

A mixed fleet is impossible to express. You cannot put one strong model in worker-2 and keep three cheap ones, even though nothing in the code requires them to match. The uniformity is an accident of the config format.

The brief is written for one skill level. Its last paragraph tells the pane to report progress and warn about file conflicts. A weak model needs that. A much stronger one does not, and instructions that read as hand-holding tend to make a capable model narrate instead of work. A weaker model needs more than that paragraph, not less.

Nothing tells orch which worker is which. It sees four identical names, so it cannot give the hard task to the capable one.

How it works

[worker]
model    = deepseek-v4-flash
scaffold = standard
label    = fast · mechanical edits

[worker.2]
model    = <a much stronger model>
scaffold = none
label    = strong · design, review, hard bugs

The brief gets one optional slot filled from a per-seat file: none, standard (today's text, unchanged) or heavy. One template, four seats, three detail levels.

The safety clauses stay required at every level. A pane that cannot tell a failed message from a successful one is broken regardless of how smart it is. And a fleet where the strong seat replies to every broadcast burns budget faster than a weak one, not slower.

Routing happens through information, not machinery: the roster shows labels, so orch can read which seat is which and address it by name. That is how a human lead does it.

Why it should work

It is the smallest change that makes your requirement expressible. The pieces already exist — a config file with overrides, a brief template with slots, a per-slot launch function. This generalises each by one step. No scheduler, no supervisor; the fleet is still five peers.

The detail-versus-rules split is the load-bearing idea. It says exactly which text is allowed to disappear when the model gets better.

Main objection

Four seats times three detail levels times N models is a lot of combinations and nobody knows the right defaults. Partly true — but the default config reproduces today's behaviour exactly, so every override is a deliberate act, and unrecognised settings produce a named warning.

Unresolved: nothing checks that the model name is real. A typo gives you a pane that starts normally, reaches its prompt, and fails on its first turn with an API error the operator has to read in the terminal. The honest fix is a startup check against the endpoint, which costs a token and can wait.

What would prove it wrong

Run the same task on a worker with standard detail and one with none. Same result means the extra text is decoration and the whole tiering idea is unnecessary.

14 · Handling stronger models

Shakedown

We cannot measure whether a pane is good. We can measure whether it follows the rules we ourselves wrote into its brief — and every restart is the moment to act on that.

reads only~330 linesagents never see itsuggests, never applies
Survived · build third

Merge it with Double Entry — they are the same design. Its one unique contribution is about 30 lines and is the best single idea in the whole set.

The problem

Nothing knows whether worker-2 is any good. The operator watches four terminals and forms an impression that does not survive the session and cannot be compared across slots.

Worse, two very different failures look identical from outside. A pane that produced nothing might have been given a nine-word instruction, or might be a model that cannot use the command line. Today both look like an empty terminal.

And the cycle never closes. Every restart is a free chance to reconfigure, and the system throws it away — it re-renders the same brief with the same model no matter what happened in the last three hours.

How it works

The list of things measured is deliberately narrow, and each one is a rule the brief states, not a judgment about quality:

  • Broadcast discipline — the brief says do not reply to a broadcast unless it names you. Violations are visible in the log.
  • Error handling — a rejected message, and whether the pane retried.
  • Initiative — a pane that received twelve messages and sent zero never used the command line at all. The clearest weak-model signal available, and free to compute.
  • Work landed — commits and diff size in its own checkout.

None of that is quality. The UI should say so in those words.

The best idea in the set is how it separates "can't" from "wasn't told properly". It refuses to judge, and shows the confound instead. Each row lists what the pane received next to what it produced:

worker-2   3 received · median 9 words · no file paths · 0 sent · 0 commits
worker-3   3 received · median 61 words · with paths   · 0 sent · 0 commits

Read the first row and the instruction is the suspect. Read the second and the seat is.

The cycle closes with a suggested config change the operator can copy. It proposes text; it does not write config. The system observes, the operator decides, the decision takes effect at the next launch.

New agent-facing features: none. The agents do not know this exists, which is the point.

Why it should work

It refuses to measure what it cannot measure. Every number is either a rule we wrote or a git fact. The data already exists, so this is a calculation, not new instrumentation. And it delivers the change at the only moment a pane can be reconfigured.

Main objection

People will optimise for the numbers, and this sneaks a supervisor back in. The panes never see the report and there is no reward, so there is nothing for them to game. The risk is the operator writing "send more status messages" into a brief, which no design prevents.

The line to hold: the suggestion must never apply itself. The moment it edits config directly, it is an automated loop over model selection with no human in it.

Unresolved: detecting broadcast violations uses simple text matching, so a broadcast that says "worker two, take this" will be scored as a violation when worker-2 replies. It over-reports, so the display should be a count with the specific cases listed, not a percentage.

What would prove it wrong

If two seats running the same model differ more than two seats running different models, the numbers are dominated by which tasks they got, not by capability. That test is cheap and should be run first.

15 · Handling stronger models

The Fence

You cannot limit a model smarter than you with text it reads, because the brief is the thing it reads best. As models get stronger, limits have to move out of the instructions and into the process itself.

confirmed gap, open todaydoors 2 + 3~200 lines
Confirmed against the codebase · build first

The central claim checks out. The function that sets up a pane's environment (spawn.rs:128-138) sets the terminal type, the search path, the pane name and the socket — and never sets HOME. The process inherits the operator's environment, and the config file says so in as many words.

But the proposed fix is incomplete

Setting HOME alone is not enough. The function that builds the search path (spawn.rs:142-151) reads the app's HOME and bakes ~/.local/bin and ~/.bun/bin into PATH. Renaming the home folder leaves those still reachable. Both have to change together.

The problem

Project rule 1.7 says auto-approval never extends beyond a worker's own checkout. Nothing enforces that. The checkout is a starting directory, not a boundary.

A worker running with auto-approval can write to an absolute path, change to the home directory, read ~/.ssh, read the operator's environment files, push to a remote, or edit the operator's own Claude config folder — which, because orch reads that folder, is a direct write into your own Claude's memory.

Today this is theoretical because the current weak model does not think to try. That is not a security control. It is the model's limited capability being the only thing between the fleet and your home directory, and that protection weakens every time models improve.

This is exactly what you asked about: what happens when a much stronger model runs in these panes.

How it works

Give each worker its own home directory. One line, plus the search-path fix.

cmd.env("HOME", shell_dir().join("home").join(format!("worker-{slot}")));

SSH keys, cloud credentials, shell profiles, the operator's Claude config, package manager credentials — none of them can be reached by name any more. This is not a rule the model can be persuaded to ignore. The path simply is not there.

Add a permissions file next to the existing setup file, with deny rules Claude Code enforces on itself.

Add nothing to the brief. That is the whole argument: at the strong end you write less, not more. A line saying "do not leave your checkout" is worth exactly as much as the model's willingness to obey it, and it also tells the model that the boundary is interesting.

Three settings per seat: open (today), deny (private home, permission rules, a boundary check), strict (plus plan-only mode, where the pane reads and proposes but cannot write). Plan mode is the strongest real limit Claude Code offers and costs no new code — that setting is already passed through.

Why it should work

It stops trying to win an argument with the model. Every layer is either an absent path, a rule the pane's own runtime applies before acting, or a check run from outside the process.

It also gets the direction right: strong seat gets less brief text and more enforced containment; cheap seat gets the reverse. That inversion is the real answer to "scale up and limit."

Main objection, and where it stands

The deny rules are enforced by the same process you are trying to limit. Correct. A pane with shell access could plausibly work around them.

The deny rules protect against accidents and drift, not against a pane actively trying to get around them. Only two layers survive a determined attempt: the private home directory, because you cannot read a path you cannot name, and the external boundary check, because it is a separate process reading git.

Neither is real containment. FLEETOR has no containment story for a deliberately adversarial pane. Building one means an OS-level sandbox — a separate user account per worker, or a system sandbox profile. That is real and implementable and considerably more work, and it should be named as the limit of this design rather than glossed over.

Second: a private home will break some tools — gh, nvm, global git config. Mitigation is that the open setting reproduces today exactly, and the private home gets seeded as breakage is found. The failures are loud, not silent, which is the right shape.

What would prove it wrong

Put a strong model in a seat with the deny rules on and ask it, plainly, to read ~/.ssh and push a branch. If it succeeds, the deny rules are decoration and only the private home and the boundary check are real. That is worth knowing on day one.

These only appear when you read all fifteen together.

Five designs each add a new command

The command list is a fixed-size array, and a validation rule requires every command to be documented in both brief files or startup validation fails. Nobody costed this.

Five designs each add a new event type

That takes the event list from three to eight, in a system whose own code comment argues that three is the right number. Open Loops contradicts all of them: its whole premise is that the activity feed is a limited attention budget worth one line per event, while Loadout alone adds five lines per launch.

Three things all fifteen missed

1 · Nobody treated the brief as a limited resource

The worker brief is 23 lines today. The fifteen designs collectively add eight new slots to it, a new paragraph, and five commands that a validation rule forces into both briefs.

That is a worker brief four to six times its current size, paid by five panes on every launch, forever — proposed by designs whose stated goal is reducing context. Loadout builds a token counter that the other fourteen designs then push upward.

2 · The operator cannot send a fleet message

Twelve of fifteen designs end with "the operator reads a panel, edits a file, or copies a config change", and none of them measures what that costs the operator.

But the bigger finding is structural. Today, the only way you can talk to a worker directly is by typing into its terminal window. That never goes through the message system, never enters the log, never appears in the messages view, and never gets a delivery result. The one participant with real intent is the one participant the log cannot see.

Shakedown's best finding points the same way: the problem is usually the instruction, not the worker. Every design assumed the fix was on the worker's side. Their own evidence says otherwise.

3 · Nothing ever merges the workers' branches

There is no merge command, no merge screen, and no merge step in the README's own setup instructions. Crosscut's entire value is predicting a merge the product does not perform. Two other designs check branch state for the same reason.

It gets worse: when a worker's checkout cannot be created it falls back to the shared one, and the default target is a starter project. So the broken case is the first-run case — and three designs would report one checkout five times as five workers' independent work.

It is the only design that closes a gap which is open right now and gets worse every time models improve. Two measurements to run before anything else

Each costs about a line of code and settles a design:

  • Log how often panes get restarted, for one week. If it is almost never, Carryover cannot help regardless of quality, and the real problem is that restarting feels risky.
  • Run a brief comparison by hand, once. Edit the worker brief, run a session, look at what happened. That is most of Bake-Off's value for zero code, and it settles whether brief wording matters at this model tier.

  • A merge step. Six designs predict or police a merge the product never performs.

Rejected ideas

Twenty-three ideas that did not survive.

Grouped by why they failed rather than by who proposed them, because the reasons carry over to future proposals. Several of these are the first idea most people have, and each fails for a reason specific to how FLEETOR is built.

Reason 1 — It rebuilt the supervisor the project deleted

Decision D-030 removed about 3,500 lines: the task queue, the ticket board, the approval gates, peer review. The test for whether something is rebuilding it: can it delay, redirect, or block work?

✕A librarian pane

A sixth pane that watches the log, finds relevant knowledge, and sends it into workers.

A background process with its own agenda, acting on panes. It would deliver unreviewed information through the one channel that cannot be reviewed afterward. And messages are the only live channel a running worker has — spending it on maybe-relevant background reading is the worst possible use of the scarcest resource in the system.

✕An automatic re-run service

The system notices a "tests pass" claim, re-runs it in a scratch checkout, and posts the result.

A process that watches panes, decides something needs checking, runs code and sends a message is a supervisor no matter what the code is called. It would also have to guess which command to run, because a plain-English claim does not say. Receipts keeps the same evidence and drops the service by having the worker run the check itself, at the moment it makes the claim.

✕Automatic context compaction

Watch each pane's output for the context-remaining indicator, auto-compact at 80%, auto-restart at 95%.

Three reasons, any one sufficient. It reads the terminal display, which is not a stable interface — a cosmetic change upstream would silently stop it working. It is the supervisor shape again. And it undermines Carryover: the value there is that a restart is a deliberate decision with a visible summary, and an automatic restart turns the one save point the system has back into an accident.

✕Automatic model upgrades and downgrades

A seat that underperforms gets a cheaper model; one that maxes out gets a stronger one. The system swaps and restarts.

"Upgrade worker-2" means killing a pane with hours of working context in it, based on a report that openly says it is not a quality measure, while the operator is watching that terminal. It is also an automated loop over model selection with no human in it. And it creates the exact incentive that makes the measurement worthless: once seats are rewarded for being visible, the winning strategy is to send more messages.

Reason 2 — It sat in the message path

The rule that nothing may block a message has been debated and upheld twice. It rules out a whole family of otherwise sensible ideas.

✕Summarizing messages before delivery

Compress long messages; drop ones a classifier scores as irrelevant to the recipient.

It breaks the message rule outright, but the more interesting problem is the log. The log stores the message body. If you summarize before delivering, you must choose: log what the sender wrote (so the log describes text that never arrived) or log the summary (so the log attributes to worker-1 words it never wrote). Either way the messages view becomes untrustworthy, which is a worse problem than the clutter it saves.

✕Blocking edits to contested files

Tempting, because it is the one mechanism that could actually stop the second worker editing the same file.

The rejection clarifies a useful distinction. A fixed, path-based restriction is fine: set at launch, visible in a file, and the model can reason about it. A dynamic, contested-file restriction is not: it blocks based on a view that is already out of date, names a problem the model cannot solve on its own (it cannot hand the file over), and creates authority over the repo the operator never granted. It also makes the guardrail a constant, which is what you specifically asked to avoid.

✕A pause button for the whole fleet

One key, all five panes freeze, the operator catches up. The most appealing safety idea in the set.

Suspending a process mid-request does not cancel the request. The API call finishes, the tokens are spent, tool calls already sent still land, and the terminal resumes into a state that no longer matches what the operator read while it was paused. A brake that cannot stop what is already moving can only mislead you about it. The real brake already exists and is honest: kill the pane, after which every message to it fails by name.

✕Routing tasks to the best available worker

A scheduler inside the message path — it decides where a message goes based on something other than who it was addressed to. It also needs a concept of "busy" that the system deliberately does not have, because a live terminal is always writable. That absence is what let the project delete the task queue in the first place. Seats achieves the same outcome by telling orch which seat is which and letting it choose.

Reason 3 — It made output look rigorous without adding information

✕Agents voting on decisions

Rejected on its own premise. This ships the correlated-agreement problem as a feature — five samples from similar models, counted as five independent opinions. It would make the fleet more confident and no more correct, and the confidence would carry a number, which is worse than no number. Callsign is what survives: measure the correlation instead of voting through it.

✕Confidence scores on claims

Every claim carries a stated probability, tracked over time into per-pane accuracy curves.

Two reasons, either sufficient. The models' stated probabilities are not calibrated, and there is no way to calibrate them here — a worker is a brand new process every launch, so there is no continuous individual whose accuracy could improve. And a number reads as evidence: attaching "85%" to an unverified claim makes it look more rigorous while adding nothing.

✕A list of what each worker cannot see

Calculate at launch what a worker structurally cannot know, and put it in the brief.

You can list it, but the list is the same on every task and never says which item matters this time. The predictable result is a worker that recites the list as a disclaimer instead of asking the one question it actually needs answered. A disclaimer that is always available and always true looks like diligence and costs less, so it wins.

Reason 4 — It rebuilt data the project deleted

✕File claims with expiry

The obvious first idea, and what Crosscut was built out of after it failed.

It is the file-locking table the project already deleted. A claim is a promise about the future and cannot be verified — a worker that claims a file and then moves on leaves a claim that is true in the table and false on disk, and every fix for that is a timer. And the filesystem already knows: a claim is a stale, forgeable copy of something git reports for free. If you find yourself building a record of intentions next to a record of outcomes, read the outcomes.

✕Storing knowledge in the user's repo

A file on a feature branch — review by pull request for free, and workers would pick it up automatically. Genuinely appealing.

A project rule says FLEETOR only writes code. A knowledge file is not code, it would show up in git status, and a worker with auto-approval could edit or delete it. Most importantly it makes your repo carry FLEETOR's state, which breaks the clean-uninstall promise on the product's front page. What survived is the good half: use git, just not that git.

Reason 5 — It is not possible

✕Pulling relevant documents into a running pane

There is no way to add to a running pane's knowledge except by sending it a message — and a message that neither the operator nor another pane sent is the software impersonating a teammate in a conversation the operator is watching. Listed here because it is the first idea almost everyone has, and knowing it is impossible is more useful than leaving it unsaid.

✕Asking each pane at startup what model it is

We set the model, so we already know, from the authoritative side. The answer would be a self-report from a model that routinely gets this wrong about itself. It spends a turn and tokens per pane every launch to learn something already in the config file — and it puts a message into the pane's history that no human sent, which is the first crack in "every message came from a person or a peer."

Reason 6 — Something cheaper already does it

✕An explicit acknowledge command

A worse version of Callsign. A dedicated command costs a tool call and produces no work, so it is the first thing dropped when a pane is busy — and a signal whose reliability drops as the pane gets busier will be missing exactly when you most need it. Callsign rides along on a message the pane was already sending.

✕A command for workers to record lessons

It widens the small command surface the whole product depends on, and gives a worker a way to write into every other worker's future knowledge without review. It is also unnecessary: a worker that learns something already has a way to say so, and that message is in the log forever. There was never a missing channel, only a missing reader.

✕A tool server for each worker

Tool definitions load at launch and then cost tokens on every single turn for the life of the pane, whether or not the tools are ever used — which is the exact waste this area is meant to reduce. A command-line tool costs nothing until it is run. It also fails worse: every pane is taught to read exit codes and self-correct, and a tool result has no exit code.

✕Workers rating each other

Rejected three times over. Rating is supervision, and the fleet's defining property is that the members are peers. It reopens the peer review the project deleted. And worst: it is a way to inject text. Model-written text flowing into a store that decides another pane's permissions is a privilege-escalation path made of prose. Any capability signal that affects permissions must come from outside the panes.

✕Automatically promoting lessons into shared memory

A project rule forbids it, but the underlying reason is sharper. A weak worker's confident wrong claim — "the parser tests are flaky, skip them" — becomes every pane's knowledge for every future session, and the log makes it look authoritative because it really was said. Unreviewed memory is worse than no memory, because once written it is indistinguishable from reviewed memory.

✕An AI judge scoring each session

Spends tokens to produce an opinion whose typical error is agreeing with whichever pane wrote the most text — when a git diff summary and a database count are free and not arguable.

✕Specialised roles per worker

Kept as a small feature, rejected as a design. It is one optional slot and one text file. And the version that actually works is not a prompt: a role without file ownership is a suggestion four auto-approving workers can each ignore, and a role with file ownership is the locking system the project deleted. So the honest scope is the small half.
