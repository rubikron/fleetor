id: D-031
title: "Phase 1: the pane contract lands additively alongside the headless one; delivery becomes request/response so the log can never claim a send that didn't happen"
phase: "1"
status: alive
---

- **What:** The D-030 contract, built **beside** the old surface rather than on top of it, so the workspace stays green and all 85 pre-existing tests pass untouched. New in `fleetor-core`: `pane.rs` (`PaneId`/`PaneState`/`PaneEntry`, serialized as bare strings — `"orch"`, `"worker-2"` — so the CLI arg, DB payload, event field and TS type are one thing; `FromStr` accepts `orch`/`lead`/`2`/`w2`/`worker-2`), `message.rs` (`Message` carrying the **body**, plus the single-sourced `frame_for_pane` / `frame_broadcast_for_pane` injection framings), and `brief.rs` (`orch_brief`/`worker_brief` for `--append-system-prompt`). `event.rs` gains `Message { id, from, to, body, group, accepted, detail }` and `PaneState { pane, from, to }`. `wire.rs` gains `Hello.pane`, four pane ops and `OpResult::{Delivered, Roster}`. `hub.rs` gains `AppCommand`/`DeliveryResult`, `Hub::with_app`, the four handler arms, `last_inbound_from` and a per-pane token bucket. New `crates/fleetor-server/tests/pane_messaging.rs` (14 tests) drives the whole surface in-process against a fake app.
- **Why request/response at the app seam:** `RunnerCommand` is fire-and-forget because a runner's job is asynchronous. `fleet send 3` is not — it needs a real yes/no, and only the pty registry knows whether pane 3 is alive. So `AppCommand::Deliver` carries a `oneshot` ack, and the hub **awaits it before appending the event**. That ordering is the whole point: the feed records what happened, never an intention. Keeping the seam in the hub (rather than collapsing routing into `src-tauri`) is what preserves in-process, zero-spend testing — a test can answer a delivery exactly as a live pane, a dead pane, a missing app or a wedged app would, and then assert on the log. The 2s ack ceiling exists only so a wedged app cannot park the CLI forever; the round-trip is a HashMap lookup and a pty write, and nothing in the path sleeps.
- **Naming deviation from the plan (deliberate):** the plan says "add `Op::{Send, Broadcast, Reply}`", but `wire.rs` already has all three with different shapes (`Send { to: u8 }`, `Reply { event_id, .. }`), so adding them under those names is impossible while the old surface lives. They land as `PaneSend`/`PaneBroadcast`/`PaneReply`; **Phase 5 deletes the originals and renames these to the bare verbs.** Likewise `PaneConfig` is a separate struct rather than fields on `HubConfig`, because six existing test files construct `HubConfig` by literal and a new field would break every one; Phase 5 folds them together.
- **Bug the tests caught, at the contract layer:** `Response` `#[serde(flatten)]`s `OpResult` into the same JSON object as its own `id`, so `OpResult::Delivered { id, .. }` produced a **duplicate `id` key** and failed to deserialize — every delivery would have come back as a client error. Field renamed to `msg_id`, and `wire.rs` now has a round-trip test over every pane frame so the next variant cannot reintroduce it.
- **L5, and why the rate limiter was pulled back out:** a per-pane token bucket was built and then **removed on operator direction** — nothing may sit in the delivery path that can stop a message from landing while messaging itself is still unproven. It was a guard against a hypothesis (a broadcast fountain) whose only power is to refuse sends, with hand-picked defaults nobody had measured; the failure mode it prevents costs tokens, the failure mode it introduces is *the product not working*. Mitigation 2 — the "never reply to a broadcast unless it names you" brief clause — stays, and is the right layer for this: it is prompt text with zero code in the send path, so it cannot cause a message to be dropped. Mitigation 3 (a visible per-pane messages/min figure) is Phase 4 and is likewise observation, not enforcement. The direct and broadcast framings differ (`[fleet · worker-1]` vs `[fleet · worker-1 → all]`) precisely so a worker *can* obey clause 2. If amplification turns out to be real, it comes back in Phase 6 behind a measurement — and behind a demonstrated fountain, not a predicted one.
- **Other decisions made here:** `reply` resolves against `last_inbound_from`, updated **only on accepted deliveries** — you cannot reply to a pane that never heard you (tested). Pane identity comes from `Hello.pane` and a connection that never declared one is refused rather than guessed at; a misattributed message is unrecoverable. `PaneId::from_str` is permissive and does **not** validate slot existence — the hub holds the roster, so it is the hub that rejects `worker-9`. `roster` is answered by the app, not the config: "this pane should exist" and "this pane is alive" are different questions with different owners.
- **Verified (zero spend):** `cargo test --workspace` — 99 tests across 24 binaries, 0 failures, 0 warnings; `cargo check` clean in `src-tauri`. Nothing is wired: `src-tauri` still runs the old pool fleet, and no pane op is reachable from the app until Phase 2 unwires it and Phase 3 builds the registry.
- **Deferred (stated):** everything Phase 1 deliberately does not do — no pty registry, no `fleet` binary, no UI, and the briefs are unvalidated against a real Flash worker (Phase 6). Rate limiting entirely (see above). The one thing left in the delivery path that can refuse a send is the 2s ack ceiling, kept because it protects the caller rather than policing it: without it a wedged app parks the `fleet` CLI — and therefore the agent's Bash call — forever.
