---
id: D-096
title: "panes wake at once: `pty_spawn` leaves the main thread, and placement alone is one at a time"
phase: meta
status: alive
---

- **What.** `pty_spawn` is an async command that runs `spawn_pane` on a blocking thread. `spawn_pane` holds a `PLACING` lock while it places a pane and drops it before `registry.spawn`, so placement stays serial and the wake runs for every pane concurrently. A pane that is already up returns before placement, so React StrictMode's second mount no longer re-seeds a live pane or logs a second spawn event. The wake itself (#42, #47) is unchanged.
- **Why.** Measured in the live log of a five-seat codex reopen on 2026-10-02: spawn events at +0.0, +3.1, +6.2, +9.3 and +13.4 s — each pane's wake waited for the one before, about 16 s before the last pane was usable. The command was synchronous, and a synchronous Tauri command runs on the main thread, so the window was held for the same 16 s. A new codex fleet takes the same path and had the same queue; Claude Code panes are `AtOnce` and never waited.
- **Why placement keeps a lock.** It writes files the panes share — `run.json` is a read-modify-write, and worktrees are added to one repository — and it costs about 60 ms a pane, measured in the same log.
- **Not verified.** The new timing has not been measured in the running app; expected is one wake's length for the whole fleet. That a synchronous command runs on the main thread is from Tauri's documentation, consistent with the serial timings, not instrumented here.
- **Reverses if.** Concurrent wakes turn out to interfere — five codex processes starting together against one login, say — in which case the wake goes back to serial but stays off the main thread.
