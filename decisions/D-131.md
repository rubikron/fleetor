---
id: D-131
title: "a worker never inherits a variable whose name looks like a secret, whatever its harness"
phase: "WP-24"
status: alive
---

- **What.** `Host::discover` collects the inherited names that `spawn::looks_like_a_secret` matches. That means any `_`-separated segment equal to `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `CREDENTIAL(S)`, `APIKEY`, `AUTH` or `KEY`, with `SSH_AUTH_SOCK` kept. `worker_command_with` removes those names before it sets anything of its own, and the placement adds an Info notice listing the names withheld. Values are never logged. Each harness's `scrubbed_env` still applies on top. The orchestrator is the operator's own attended seat and keeps its whole environment.
- **Why.** The live baseline's check 8 found `CMUX_CUA_AUTH_TOKEN_FILE` in a cursor worker's pane. A worker inherits the whole app environment, and `scrubbed_env` names only its own vendor's keys. Reads are open (WP-17), so any token the operator's shell exports was reachable by every worker on every harness. A pattern was chosen over an allowlist because it is cheap and cannot break a toolchain that needs an ordinary variable. Its cost is that it only catches names that look like secrets.
- **Reverses if.** A worker needs a matching variable to do its job (`GH_TOKEN` for `gh`, for example). The fix then is an operator-set exemption, not dropping the rule. Or an allowlist package replaces it.
