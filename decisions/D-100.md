---
id: D-100
title: "tasks live in a per-target store as chain entries; the run log's task event is read-only"
phase: S1
status: alive
---

- **What.** A goal or task is a fold over `FleetEvent::Chain { task, from, at, run, lineage, entry }` rows in the target's `tasks.db`, written through the unchanged store interface. `entry` is `opened`, `taken-up` or `status` so far. Numbers are per target: highest opened + 1, taken under a hub lock held across the read and the append. Every entry carries both the run id and the lineage id. Statuses are `planned`, `in-progress`, `done`, `dropped`; `claimed` is gone. The old `FleetEvent::Task` (kind `task`) and its types move to `legacy_task` unchanged: nothing writes it, and archived `state.db` files still digest and replay byte for byte.
- **Why.** Tasks vanished when the run database rotated. A new variant name rather than a reshaped `task` keeps every archived run decodable, and a reopen replays those rows to the UI. Lineage on every entry makes "owner from an earlier run" a string comparison instead of a walk over run manifests.
- **Rules, checked against creator and owner, never task state.** Goals are opened by orch and the operator. Orch's tasks must name a goal; a worker's task starts unowned. Anyone takes a task up and becomes its owner. Only the owner, in the same lineage, marks it done. Dropping and reopening follow edit authority: the creator, orch on a worker's task, the operator on any. A goal is not taken up or marked done.
- **Amends.** D-047: owner optional, status words, identity rules, tasks out of the run log. "A record, not a dispatcher" stands and is still pinned by the send-is-byte-identical test.
- **For the wiring half.** History reads a run's task count from `tasks.json` when present and falls back to the run-log digest for older runs, which is why the digest still counts old `task` events.
- **Reverses if.** Two apps must write one target's store at once (the number lock is per hub), or folding the whole store per operation becomes measurable.
