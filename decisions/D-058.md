title: "WP-11: a run is a database, rotated at start, and history is a directory of frozen files"
phase: "WP-11"
status: alive
---

- **What changed.** The event log stops being one file that every fleet start appends to. `~/.fleetor/_shell/state.db` is now always and only the **live** run; at each `fleet_bootstrap`, before the store is opened, the previous run is archived to `~/.fleetor/runs/<timestamp>/state.db` and a fresh database is opened. Archiving checkpoints the old WAL and moves a single self-contained file (strategy B in `docs/notes/run-rotation-notes.md`), falling back to moving `state.db`+`-wal`+`-shm` together, and finally to leaving them alone with a `Warn` — rotation may never fail a boot. `runs/index.json` holds each run's editable label, target and derived counts, and is a **cache**: reads scan `runs/*/` for existence and merge, so losing it costs labels only. A new History view lists past runs and opens one read-only into the existing Messages, Tasks and Activity components. The run id is the timestamp directory; the label is a separate mutable string, auto-suggested at archive time, so renaming never moves a file.
- **Why the default lost.** The single shared log was about to become actively wrong: the evaluation loop this unblocks compares one cycle against another, and cannot while cycle 4's read returns cycle 1's messages. Physical isolation beat the cheaper `run_id`-column design because run separation behind a `WHERE` clause on the one table that is this app's whole persistence story is the corruption being prevented, reimplemented as a predicate — and migrations here are appended, never edited, so a wrong schema would be permanent. The boundary is cut at **start** rather than at teardown because teardown is the thing that fails; `orphans.rs` exists for exactly that reason, and a crash under rotate-on-stop silently reopens the previous run.
- **What would reverse it.** Runs accumulating to the point that the directory needs a retention policy — at which point the answer is a size column and an operator-driven delete before it is automatic expiry. Or a measured need for cross-run queries frequent enough that opening N files hurts, which would argue for `ATTACH` over a schema change, not for the `run_id` column.
