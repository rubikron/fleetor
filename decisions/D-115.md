---
id: D-115
title: "a codex worker in a linked worktree gets four git writable roots, never the whole `.git`"
phase: meta
status: alive
---

- **What.** The codex seeder appends four paths to `sandbox_workspace_write.writable_roots` when the seat is not the operator's own and its cwd is inside a linked worktree: the worktree's gitdir (`<common>/worktrees/<name>`), `<common>/objects`, `<common>/refs`, `<common>/logs`. Both directories are asked of git (`Seed::worktree_git`). The operator's own entries are kept and nothing is announced. A main checkout, a non-repo cwd and the orchestrator seat get none; the orchestrator's commit block is not covered here.
- **Why.** A codex worker could not `git commit` (issue 10): the gitdir and object store live in the target repo's `.git`, outside the sandbox. Measured on codex-cli 0.161.0, the whole `.git` as one root does not work alone (the cwd's own gitdir stays read-only) and was rejected anyway for opening `hooks/` and `config`. With the four, commit, amend, `switch -c` and stash pass, and hooks, config and the main checkout stay refused; removing any one fails the commit. `git gc` fails under this set and that is accepted. This is a Tier 1.7 widening, approved by the operator on 2026-10-10.
- **Reverses if.** A worker needs a git operation these four do not allow, or a codex version changes what a root grants; then re-measure with `examples/codex-commit-spike/commit.sh` and get the operator's approval before adding a path.
