id: D-082
title: "a fenced worker is handed `DISABLE_AUTOUPDATER=1`, because its private HOME had become four Claude Code installations nobody runs"
phase: "meta"
status: alive
---

- **What.** `ConfigAndCredentialIsolation` gains `fenced_env`, variables a pane given a private `HOME` is also handed; spawn sets them alongside that `HOME`. Claude Code's is `DISABLE_AUTOUPDATER=1`; codex's is empty (not measured). Orch is untouched — its updater is the operator's own install (D-030).
- **Why, measured 2026-09-10.** `~/.fleetor/_shell/home/worker-{1..4}` each held `.local/share/claude/versions/{2.1.261,2.1.263,2.1.265}` at ~190 MB apiece, ~2.2 GB total, each version landing shortly after the operator's own install got it. Probe: the operator's 2.1.266 binary under a scratch private `HOME` (trust pre-seeded, no credential) downloaded 2.1.267 (200 MB) into it within 90 s and printed "Update installed · Restart to update"; the same run with `DISABLE_AUTOUPDATER=1` wrote nothing. The binary's own sandbox runner sets the same variable for its children.
- **The copies were never run, which corrects an earlier belief in this session.** A worker's PATH (`worker_augmented_path_from`) has no private-`HOME` rung, so a worker keeps resolving whatever `claude` the inherited PATH tail finds — the operator's. "Pin workers to the operator's binary by absolute path" was therefore rejected as moot for this problem: workers already run the device's version.
- **Not done here.** The existing copies are not deleted by code (a one-off manual cleanup), and a GUI-launched app whose inherited PATH lacks `~/.local/bin` still leaves a worker with no `claude` to find — a separate, unmeasured question.
