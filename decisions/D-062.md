id: D-062
title: "WP-14: `orch` gets a config dir of its own, and D-059's named gap closes"
phase: "WP-14"
status: alive
---

- **What changed.** `orch` stops running on the operator's own `CLAUDE_CONFIG_DIR`. It now spawns with `CLAUDE_CONFIG_DIR=~/.fleetor/_shell/pane-config/orch`, seeded at the spawn site with the same two onboarding keys a worker's dir gets — because once it is a fleet-owned directory, L1 applies to `orch` exactly as it applies to a worker. Its session transcript therefore lands under `~/.fleetor`, and `runs::harvest_transcripts` archives it into `runs/<id>/transcripts/orch/` with **no code change**: it already walked `_shell/pane-config/*`. Nothing is read, copied or linked out of the operator's directory; `orch` starts a new one and goes forward from there. `worker_config_dir(slot)` became `pane_config_dir(PaneId)`, one root for every pane. This also gives WP-17's deny rules and hooks the home they need — the second job WP-12 filed this package for.
- **The load-bearing detail, and it is not obvious.** `CLAUDE_CONFIG_DIR` alone **logs `orch` out**, invisibly. Claude Code namespaces its macOS Keychain service name by `sha256(config dir)[..8]` whenever that variable is set, so a fleet-owned directory is a fresh, empty login. The pane still reaches its input box, so every `fleet send` into it reports `accepted` and only its turns fail — the risk-register failure that looks exactly like a healthy pane. `orch_command` therefore also sets `CLAUDE_SECURESTORAGE_CONFIG_DIR` to the **empty string**, which selects the unsuffixed service name: the entry the operator's own `/login` already wrote. That moves the credential *lookup* and nothing else — `claude` performs the identical keychain read it performs today, so this does not touch the operator's auth, it preserves it. `worker_command` `env_remove`s the same variable so a worker can never inherit the key to that entry. Measured against CC 2.1.224 in `docs/notes/orch-config-dir-notes.md`, four arms of a real interactive pane plus the derivation read out of the binary.
- **Why the default lost.** D-059 left this gap open and said closing it needed an operator decision, because reaching into the operator's personal Claude history to move it would cross Tier 1.1. The operator made the call: the pane that makes every decision cannot be the one pane an evaluator cannot read, and the event log alone gives it `orch`'s messages with none of its reasoning. The refusal that produced the gap is intact — nothing reaches into their directory. What changed is that `orch` gets a directory of its own going forward, which is a different move from the one D-059 refused.
- **What it costs, stated plainly.** `orch` no longer inherits the operator's user `CLAUDE.md`, skills, subagents, MCP servers, settings or hooks — all of which are read from `CLAUDE_CONFIG_DIR` (`docs/notes/system-prompt-notes.md` §3 measured that they load today). D-030's "orch is untouched" is narrowed here for the first time, and narrowed to exactly one thing: the config dir. The Fence stays worker-only, `HOME` is still the operator's, `augmented_path()` still reads it, and `orch` still spawns with no `--permission-mode` and no `ANTHROPIC_*` override. Three tests assert that, because the cheap way to break this package is to make `orch` slightly more like a worker.
- **What would reverse it.** An operator noticing that `orch` stopped being *their* Claude — no skills, no MCP servers, no memory. The fix is not to undo this: it is to let the operator populate `~/.fleetor/_shell/pane-config/orch/` themselves, which is a directory they own and this app only seeds two keys into. Or Claude Code dropping `CLAUDE_SECURESTORAGE_CONFIG_DIR`, which is an internal and not in `claude --help`. That failure is bounded and self-healing — `orch` shows `Not logged in · Run /login`, one `/login` inside the pane writes the credential into the fleet dir's own namespace, it persists, and it cannot disturb the operator's own entry. `spawn_pane` puts that sentence on the Activity feed at every `orch` launch rather than leaving the operator to diagnose a pane that looks fine.
- **Not verified:** `orch` reaching a prompt *inside the running app*. The exact environment was spawned by hand in a pty and reached `Claude Max` with an input box; no fleet has been started since the change landed.
