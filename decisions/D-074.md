---
id: D-074
title: "the evaluator is placed, dev mode is read through the layout, and the target is one cell"
phase: "meta"
status: alive
---

- **What changed.** `PaneSpec::Evaluator` joins `Orch` and `Worker(slot)`, so every pane kind that can exist now comes up through `placement::place`. The evaluator arm re-checks dev mode itself, lays the live run out under `~/.fleetor/dev/retro/<run-id>/`, renders the brief against that directory, seeds the config dir, installs the guardrail and builds the command — in that order, in one function. `fleet::spawn_pane`'s tail match is gone with it, and so are the two helpers only that arm used, `install_guardrail` and `evaluator_brief`. Separately, `Fleet.target` became a `Target` — one `Arc<Mutex<PathBuf>>` that the spawn path and the handoff watch both hold, rather than a field and a bootstrap-time copy of it.
- **Dev mode is read through the layout, not through the process (D11).** `Layout::dev_enabled()` is `dev::read_at(self.config_file())` — the same parse `dev::is_enabled` performs, against the config file inside the layout placement was handed. This is the one file read `place` performs that is neither an argument nor a write, and it is the rule applied rather than a hole in it: pointing the layout at a scratch directory points the mode at a scratch directory. It buys three properties at once that no other shape buys together. The spawn site genuinely re-checks, so `wake_evaluator` cannot lie to it — the existing code argued for that explicitly and had no way to test it. The mode stays read fresh at every placement, which is what D-061 promised. And a test can flip the flag without touching `~/.fleetor`. **Passing the mode in as a `bool` was rejected** for losing the first of those; it is what the code effectively did before, and it is why "unreachable outside dev mode" was a property of one caller rather than of the spawn site.
- **`evaluator::readiness` stopped reading the environment.** It resolved the harness, workspace and answer-key roots itself, from `FLEETOR_EVAL_*` or the operator's home — which is precisely what made it uncallable from placement. It takes a `&MissionRoots` now, which `Host::discover` already carried (D12). One consequence worth naming: the same target is `Ready` under one machine's roots and `NoMission` under another's, and that is a case a test can now write.
- **Laying the run out is part of placing, not a step before it (D2).** The evaluator's working directory *is* a snapshot of the run, so there is no order in which a caller could usefully do this first — the brief cites the directory, and a brief citing a directory nobody wrote costs the pane its first turn asking about it. The alternative on the table (the caller lays it out and hands a rendered brief in) reintroduces exactly what this module removes: a piece of the sequence living in the caller, plus a parameter the other arms discard.
- **The wake and the spawn path read one target (D14), and the doc comment that said so is true for the first time.** `wake_evaluator`'s comment claimed its target was "the same one `spawn_pane` renders the brief against". It was not: the watch was handed a `PathBuf` at bootstrap and kept it, while the spawn path read a field `apply_target` rewrites. Both now read one cell. **This changes no behaviour, and there is a reason to expect none rather than a hope:** D-071 fixed the target the moment a pane exists, and a handoff cannot happen before `orch` exists to send one, so the value the watch used to snapshot and the value it now reads can only differ in a fleet that never reaches a handoff. The behaviour-change half of D14 was that freeze, and it landed as D-071.
- **The write-guardrail test has no copy of the sequence left, which is the point of the ticket.** It used to invent a `_shell` and a worktree, call `guardrail::roots_for` and `guardrail::install` itself, and read the settings file it had just written. That copy had already drifted: `roots_for` is unconditional, so the hand-built version could never have produced the evaluator's narrower pair — the one pane whose roots matter most was the one pane the file could not test. Every `settings.json` it now runs is written by the same `place` call the application makes, against a scratch layout. **The seam it exists for is untouched:** the hook still goes through `sh -c`, still reads a genuine `PreToolUse` payload on stdin, and is still believed only when it answers. This is not a unit test of a Rust function and must not become one. `placement::guardrail_notices` is private again as a result — it had exactly one caller outside the module and one hand-typed impostor, and both are gone.
- **The evaluator's roots are now a checked property rather than a comment.** Its guardrail gets its own working directory and nothing else: not `_shell`, which holds the live event log it is reading, and not the operator's `[fence] allow` extras, which exist for the panes doing the work. Two tests hold it from different sides. `tests/placement.rs` reads the policy file placement wrote and compares it against `orch`'s three roots placed from the same layout and the same context, so "narrower" is a comparison and not a remembered number. `tests/write_guardrail.rs` runs the installed hook and watches the evaluator be refused all three directories `orch` is allowed on the same bench. This is the filesystem half of the veil; `PaneId`'s enumeration half is unchanged and its tripwires are untouched and green.
- **One shared test fixture was added rather than a second copy.** `src-tauri/tests/common/mod.rs` builds a whole scratch installation — layout, host, a prepared mission workspace, a real repository, a live SQLite run — because placing an evaluator has four preconditions and two test binaries assert different things about the same placement. A module for one thing, not a helpers grab-bag; retyping it in both files is the move this ticket exists to stop making.
- **What would reverse it.** A relocatable state root, which the arc puts out of scope: `Layout` is the shape that change needs, and `dev_enabled` would follow it for free. Or the Critic turning out to need a mode of its own, at which point "read the flag through the layout" becomes "read *which* flag through the layout" and the accessor takes an argument. Neither is evidence anyone has.
- **Verified:** **200** shell tests green under `cargo test --features devmode`, up from **195** at `edecac8` — 151 lib (was 150; one new, `evaluator::tests::readiness_judges_the_target_against_the_roots_it_was_handed`), 4 dev-mode, 8 evaluator, 11 real-pty, **14** placement (was 11), 3 views, **9** write-guardrail (was 8). **195** green under plain `cargo test` as well, where the four `devmode`-gated additions compile out. **213** workspace tests green, unchanged; no file under `crates/` was touched. `cargo build` and `cargo build --features devmode` produce no warnings; `npm run build` clean. `cargo clippy --all-targets --features devmode` reports the same three pre-existing warnings and no new one. Both new veil assertions were mutation-checked rather than only asserted: replacing the evaluator's roots branch with the worker's fails `the_evaluators_write_roots_are_its_own_directory_alone_and_no_pane_is_narrower` and `the_evaluator_may_write_in_the_run_it_was_given_and_in_nothing_else`, and replacing `layout.dev_enabled()` with `dev::is_enabled()` fails `placing_an_evaluator_reads_the_mode_from_the_layouts_own_config` on this machine, whose real config has the mode on. No test was deleted, weakened or marked ignored; six in `tests/write_guardrail.rs` changed their setup and kept every assertion.
- **Not verified:** **no fleet has been started since this landed**, so no evaluator has woken through `place`, no handoff has fired, and no retro has happened — the same honest gap D-062, D-065, D-066, D-069, D-071, D-072 and D-073 each record. The claim that the evaluator's command is unchanged rests on reading: `spawn::evaluator_command` now delegates to `evaluator_command_with`, and the two values placement hands it — `host.pane_program` and `host.orch_path()` — are what `pane_program()` and `augmented_path()` would have read. Nothing asserts the two commands are byte-identical. The mutation check on the mode is only meaningful on a machine whose real `config.json` has dev mode **on**; on a machine with it off, that test would pass even if placement read the process, and nothing detects that. `rustfmt` is not installed on this machine, so formatting was not checked. No live spend.
