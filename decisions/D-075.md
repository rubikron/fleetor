---
id: D-075
title: "the process-shaping module becomes an internal of placement, and the layout goes on the fleet"
phase: "meta"
status: alive
---

- **What changed.** `src-tauri/src/spawn.rs` is now `src-tauri/src/placement/spawn.rs`, a **child module of `placement`** rather than its sibling, and every seeding and command-building function in it is `pub(super)`. Nothing outside `placement/mod.rs` can call them at all — not `fleet`, not a test binary — so they cannot be called in the wrong order by anything that is not the module that owns the order. `lib.rs` no longer exports `spawn`. Alongside it: `Layout` is held on `Fleet`, resolved once at bootstrap; `fleet.rs`'s five remaining location helpers (`fleetor_dir`, `shell_dir`, `testbed_dir`, `config_path`, `socket_path`) are gone with the sequence that needed them, leaving `layout()` alone; the two machine-level warnings moved into `placement::machine_notices`; and `"pane-config"` is spelled once, in `placement::pane_config_root`.
- **Why this is logged at all.** `building.md` puts internal module structure in Tier 3 and a refactor needs no entry. Two things here are not internal structure. `Layout` landing on the fleet's live state is the answer to "where does a pane's layout come from" that WP-22 and WP-23 will both ask, and D-072 logged the value for exactly that reason. And the visibility rule is a claim about what a future ticket *cannot* do, which is worth more written down than discovered.
- **The seam `spawn.rs` presented was hypothetical, and the test for that is who calls it.** Every seeding and command-building function in it had exactly one production caller after ticket 04, and that caller was `placement`. A public function with one caller is not an interface, it is an invitation: the next agent needing a seeded config dir calls `seed_config_dir` and skips the guardrail install that has to follow it, and nothing fails until an operator's pane can rewrite its own hook policy. `pub(super)` inside a child module is what makes that a compile error rather than a code review. Verified as a compile error, not asserted: adding `placement::spawn::seed_config_dir(...)` to `fleet::spawn_pane` fails with `function seed_config_dir is private`.
- **The reading wrappers are deleted, and the tests that wanted them keep every assertion.** `orch_command`, `evaluator_command`, `worker_command`, `augmented_path` and `worker_augmented_path` were each one line: the `*_with` implementation plus the process reads `Host::discover` now performs. `evaluator_command` had no caller at all. The other four had none in production and sixteen in `spawn.rs`'s own unit tests, so what was left was scaffolding — and **scaffolding belongs in the test module**, which is where those four now are, `#[cfg(test)]`, unchanged in body. Every test in that file keeps its letter, including the one that sets `HOME=/Users/operator` and reads the rungs back: what moved is *where* the environment is read, and it is read in the test rather than in the shipped module. **This loses no coverage of production**, because production stopped calling those wrappers in ticket 02 — `place` has gone through `Host` since then. The alternative on the table (have each test call `augmented_path_from` with literals) would have dropped the `$HOME` read from the test's letter, which is a weakening, so it was refused.
- **`tests/panes.rs` drives `placement::place` now, and that is stricter rather than merely different.** It was the last thing outside `placement` that knew how a pane is shaped: it built five commands by hand and spawned them on real ptys. It builds them by placing them, against a scratch layout and a `Host` that carries the stand-in program as a field — the same override, handed in instead of read out of `FLEETOR_PANE_CMD`, so the file no longer sets a process-global at all. The seeding and the guardrail install now happen on the way to every pty this file opens, which they did not before. Its target is deliberately **not** a git repository: a worker placed against it takes the announced shared-checkout fallback, so running the test suite branches nothing and creates no worktree of the repository it is running inside.
- **`Layout` is on `Fleet`; `Host` is deliberately not, and getting that backwards is a bug no test would catch.** The state root cannot move under a running fleet, so resolving it once and holding it is both cheaper and more honest than six accessors re-deriving it from `$HOME`. What the machine *has* is the opposite: a rustup installed mid-session, an `.env` saved, a `fleet` binary built. Caching those at bootstrap makes them invisible until relaunch — the exact staleness D13 exists to avoid — and it fails silently, because a stale `Host` produces a perfectly well-formed command. So `spawn_pane` discovers one per spawn, and now discovers it **once** per spawn: `warn_about_the_machine` used to call `fleet_bin_path` and `operator_toolchain` itself, a second independent read of the same machine that could in principle disagree with the one the pane was placed against.
- **`machine_notices` is the one part of bringing a pane up that the caller performs, and the reason is ordering.** Those two lines have to reach the operator even when the placement that follows returns `Err` — a machine with no worker key would otherwise be told only about the key. What moved into `placement` is the decision: which sentences, under which conditions, off which `Host`. `fleet.rs` holds neither. `orch` is excluded there because `place_orch` emits the `fleet`-binary line from the same constant, and saying it twice is how an operator learns to stop reading the feed.
- **Four spellings of `"pane-config"` became one, and they were never four independent facts.** `Layout::pane_config`, `guardrail::policy_dir` and the two transcript scans in `runs` each wrote `shell.join("pane-config")` out again. The guardrail refuses writes to exactly the directory the layout puts configs in, and rotation archives a transcript by walking exactly that directory — so a rename reaching three of them leaves either a fleet whose panes can rewrite their own hook policy or one whose orchestrator's transcript stops being archived, and no test would say which. `placement::pane_config_root(shell)` takes the `_shell` path rather than the whole `Layout` because the two callers outside `placement` hold one and not the other; converging their signatures onto `Layout` would have meant changing `runs::rotate` and `runs::snapshot_live_run` and the twenty-five test call sites under them, which is a wider ticket than this one.
- **The missing-key refusal names the directory again (the deferred cleanup this ticket owed).** `MISSING_API_KEY` was a constant, and a constant cannot say where it looked; the sentence the old sequence emitted did. It is `missing_api_key(searched_from)` now, fed by a new `Host::api_key_searched_from` and by `fleet::api_key_search_start`, which is also what `load_api_key`'s own walk starts from — one spelling, so the message names the directory that was actually searched. This is the operator-actionable half: under `tauri dev` the working directory is `src-tauri/`, so a key at the repo root *is* found by the walk, and an operator whose key is elsewhere can only tell which case they are in if the message says where it looked.
- **What would reverse it.** A second consumer of the process-shaping functions that is genuinely not a placement — a `fleet doctor` that wants to print the PATH a worker would get, say. That is a reason to make `placement` answer the question, not a reason to re-export the internals. Or a relocatable state root, which the arc puts out of scope and which `Layout` is already the shape of.
- **Verified:** **202** shell tests green under `cargo test --features devmode`, up from **200** at `1f69427` — 151 lib (unchanged), 4 dev-mode, 8 evaluator, 11 real-pty, **16** placement (was 14), 3 views, 9 write-guardrail. **197** green under plain `cargo test`, up from 195, where the three `devmode`-gated placement tests compile out. **213** workspace tests green, unchanged; no file under `crates/` was touched. `cargo build` and `cargo build --features devmode` produce no warnings; `npm run build` clean. `cargo clippy --all-targets --features devmode` reports **two** warnings, down from three: the third was `this function has too many arguments (8/7)` on `spawn::worker_command`, which this ticket deletes. **No test was deleted, weakened or marked ignored.** Both new tests were mutation-checked rather than only asserted: dropping the path from `missing_api_key` fails `a_worker_with_no_key_is_told_where_the_key_was_looked_for`, and removing the `orch` early return from `machine_notices` fails `a_bare_machine_warns_about_the_fleet_binary_and_the_toolchain_but_never_for_orch`. The visibility claim was checked by making the compiler enforce it (above). No source-reading tripwire names `src/spawn.rs` or `src/placement.rs` by path, so none of them silently stopped reading a file when the two moved — checked by grep over `tests/` before the move and after.
- **Not verified:** **no fleet has been started since this landed**, so no pane of any kind has come up through the moved module — the same honest gap D-062, D-065, D-066, D-069, D-071, D-072, D-073 and D-074 each record. The claim of no behaviour change rests on reading and on the suite: nothing asserts that the five commands are byte-identical to the ones the deleted wrappers built, and `tests/panes.rs` now proves the panes spawn and talk rather than proving their commands are unchanged. **`fleet.rs` did not get materially smaller**, which is one of this ticket's stated goals: 844 code lines to 831, and 1474 total lines to 1482 because the doc comments grew. Ticket 04 had already taken the bulk — the bring-up match and the two helpers only its evaluator arm used — and what was left for this ticket was five one-line location helpers and two process reads. The *composition* claim holds and the line count does not, and it is recorded here rather than rounded up. `rustfmt` is not installed on this machine, so formatting was not checked. No prompt template changed, so `brief-cost` is 0. No live spend.
