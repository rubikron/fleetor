- **What changed.** The evaluation sandbox abandoned on 2026-08-06 is re-opened with a different shape, filed as the WP-12 arc. Settled this session: (1) **dev mode** is a real, operator-triggered product mode, not a test rig bolted on the side — the last attempt died pretending to be a rig while doing ~10 files of core surgery; (2) **the evaluator** is a real `claude` in its own Tauri window, wakes on a new done verb, coaches and never edits; (3) **the veil** — `orch` is not told the evaluator exists and cannot address it until it declares done; (4) **rewind missions** — a real repo pinned to an old tag, judged against the feature upstream actually shipped, so the retro rests on an information asymmetry rather than on two Claude instances agreeing; (5) **the operator is the only writer** in the loop, which is Tier 1.8 applied to the platform itself.
- **Why the default lost.** "Evaluate the fleet" with no answer key converges on congratulation. Upstream's real commit is the only cheap source of ground truth that is not itself a model's opinion. And the abandoned attempt's failure was scoping, not concept: gating this behind a visible mode makes it product from the first line, and putting the largest chunk (the rewind harness) in a separate repo that imports nothing makes core churn structurally impossible for that part.
- **The hiding model, stated once.** A Claude Code process running as the operator can read any file the operator can read; deny rules are friction, not enforcement. So only three things are made **absent** rather than fenced — the answer key (not cloned until after the done verb), the evaluator's brief (separate private repo, `include_str!` behind a `devmode` cargo feature, so nothing on disk holds it), and the ledger. Dev-mode code, the second window and the done verb are deliberately *not* hidden: they do not contaminate, and `orch` learns the evaluator exists at first contact anyway.
- **The grader is frozen across generations.** Compiling the evaluator's brief in from a repo the fleet cannot reach is not only about `orch` reading its rubric — if an improve run ever softened the evaluator, "did the fleet improve or did the grader get soft" becomes unanswerable. Changing the evaluator deliberately resets the comparison baseline and must be version-stamped on every retro.
- **Tier 1.4 held, not bent.** The operator asked for an orch-to-orch cutoff the CLI honours too. Built as a mute it would be exactly the refusal-in-the-message-path §9.3 records as argued and lost twice, and it would make the log lie (L3). The allowed shape is **addressing, not delivery**: link off means the other fleet's panes are not addresses, so `fleet send other:orch` fails at *resolution* like `fleet send worker-9` does today. Nothing enters the delivery path to be refused. WP-19 is built this way or filed as a Tier-1 question.
- **The fleet is a contributor, not a hot-patcher.** An improve run works in its own worktree with its own `target/`, never writes into the running install, and takes effect only at an operator-triggered rebuild-and-relaunch — that relaunch *is* the generation boundary. Five cases catalogued in WP-12; the one live today is that `npm run tauri dev` runs Vite, so HMR would hot-swap the running UI. **Standing rule: run a built binary during a cycle, never `tauri dev`.**
- **What would reverse it.** A first retro (WP-15) that produces nothing `orch` has to argue with — at which point the fault is the evaluator's brief or the answer key's usefulness, and the fix is prose or mission selection, not more machinery. Or the arc reaching ~10 files of core churn again, which is the original verdict repeating and should stop the arc rather than be worked around.
- **Not verified:** managed-settings precedence and `PreToolUse` interception of `Bash` for the installed CC version — deny layers 2 and 3 in WP-12 are written as unconfirmed on purpose.
