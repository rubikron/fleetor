Running the launch PRD and the task PRD in parallel

How the system works today, where the two plans collide, what the resolutions fix, and the rules each Claude Code session follows. Sources: .scratch/one-fleet-launch/PRD.md, .scratch/task-system/PRD.md.

1Before: two start paths, one run log holding everything

New fleet and reopen are separate commands. Only reopen tears the running fleet down. Tasks are events inside the run's own database, so they are archived with the session.

UIthe reported bug

2The conflict: both plans rebuild the same middle

The launch PRD replaces the start path and the archive. The task PRD moves tasks out of the run log into a per-target store wired into that same start path. Written separately, they contradict each other in four places and collide on setup in three.

ATasks reset on launch

Launch PRD
Clear feed, messages and tasks on every launch.
Task PRD
Tasks outlive sessions.
Breaks
The Tasks view empties on every launch.
Fix. Launch calls a resetTasks() hook. The task PRD fills it with clear + replay of the store.

BWhich target is "current"

Launch PRD
The gate's target can differ from the live fleet's.
Task PRD
One store per "current target".
Breaks
Tasks written to the wrong repo's store.
Fix. The store follows the target fixed on the fleet. Opened in Build, closed by Teardown.

Ctasks.json and the split archive

Launch PRD
Archive = fast stage + background finish.
Task PRD
Write tasks.json "when archiving".
Breaks
Finish runs after the next fleet is up, maybe on another target.
Fix. Written at stage through a hook, filtered by run id. History reads its task count from that file.

DReopen and "earlier run" owners

Launch PRD
A reopen resumes each pane's conversation under a new run id.
Task PRD
An owner from an earlier run is available.
Breaks
A worker mid-task looks free and its task is re-handed.
Fix. Ownership follows the lineage (sessions id). Startup triage applies to fresh launches only.

SSetup collisions

Base
The plans assumed different branches; remove/critic-evaluator rewrites the same files.
D-099
Claimed by both.
Machine
Both run the real app on one ~/.fleetor/_shell.
Fix. One shared base, separate worktrees, task PRD starts at D-100, live demos take turns.

3After: one launch, two stores

Every fleet comes up through one launch with a fixed order. The run log keeps events; goals and tasks live in a store that belongs to the target repo and survives sessions.

6Standing rules

  1. Decision numbers. The launch PRD owns D-099. The task PRD records D-100 onward.
  2. Live demos take turns. One real app instance at a time; both sessions share ~/.fleetor/_shell.
  3. Hooks are the contract. The launch session ships resetTasks() and the stage hook as no-ops and keeps Build and Teardown as single functions. The task session only fills them in.
  4. No fleet: Tasks view is read-only. It shows the gate target's tasks with a "Carried over" banner; controls are disabled until a fleet is live.
  5. Reopen. The Activity feed filters task entries by lineage, and a resumed worker re-checks its task with fleet task show before continuing.
  6. History counts. Running now counts from the live store; Archiving and Archived rows count from tasks.json.
  7. Cleanup is neither session's job. Deleting old tasks and worktrees from previous projects is approved, but it is a separate cutover step.
