status: alive

- **What:** The two delivery paths deferred since D-015 (again at D-019, D-021) are now wired, closing the messaging model. **(a) Idle→stdin** — at a report-less turn boundary, `supervisor::drive_to_report` runs a bounded `idle_drain_step`: it flips the worker `Working→Idle`, briefly polls `store.take_mail(&Party::Worker(slot))` (10×50ms, honoring the wall-clock `deadline`, mirroring `grace_poll_mcp_report`), and if mail is queued writes it straight to stdin as a **fresh turn** via the existing `Session::send_user` — *not* counted against the no-report reprompt cap (a mail-driven turn is real work, bounded by `deadline`), then `Idle→Working`. Empty window → falls through to the unchanged reprompt/finish path. **(b) Opportunistic piggyback** — in the shim's `call_tool`, after any *worker* tool call, one `Op::DrainMail` folds pending mail into the rendered MCP result as an extra content block (`protocol::append_piggyback`); skips the `report` op (mail-after-report can prompt a redundant report — D-018 followup a) and the lead face (no mailbox). **(c) Framing single-sourced** — `frame_mail_for_injection` + `sender_label` moved from the shim's `protocol.rs` to `fleetor_core::mail`, so all three paths (Stop-hook drain, idle→stdin, piggyback) inject byte-identical D-014 coordination framing.
- **Why:** These paths finally have a live consumer — Phase 4d's `run_dynamic_fleet` + external lead can `send` steering at arbitrary times (D-019/D-021 deferred them precisely for want of that). **Idle→stdin is supervisor-side, not a new channel:** the supervisor already holds `Arc<dyn Store>` and reads it for `ReportFiled` (D-019's shared-log bridge), so it drains the same store directly — no cross-runtime plumbing. **Piggyback is shim-side, not hub-side:** `Client::call` returns only `OpResult` (a Response-level piggyback field would force Client + every-caller plumbing), and fake-claude speaks the raw socket *bypassing the shim*, so enriching the **MCP** result a real worker sees is inherently the shim's job. **Exactly-once holds across all three drains** because `Store::take_mail` is an atomic destructive SQLite drain: concurrent drainers serialize, each message goes out exactly one path, and the orderings are naturally disjoint (mid-turn → Stop hook / piggyback; after the turn's `result` — emitted only once the Stop hook declines to block — → the supervisor's idle drain, which therefore never races the hook for the same message).
- **Verified (no live-CC spend):** `bridge::tool_result_piggybacks_pending_mail` — the real shim binary folds queued mail into a `whos_working_on` result (with framing), a second call after the queue empties carries none, and a `report` call does **not** piggyback (the mail stays queued). `idle_mail::idle_mail_is_injected_over_stdin_as_a_fresh_turn` — a fake worker ends turn 1 with no report; the supervisor injects pre-queued mail over stdin (transcript shows the framed mail), the worker files `done` on turn 2, and a `Working→Idle` beat is in the event log. New `idle-mail` fake scenario. Full workspace suite green (57 crate tests). The live `--real` run (a lead `send`ing steering after a worker's first turn, confirming both paths against real Flash) stays an operator-triggered gate, per every prior phase.
- **Reverses if:** the idle window proves too coarse under a busy multi-worker log (promote to a per-slot notify channel from the hub — the alternative D-019 already named); or piggyback wants to ride *every* client including the raw-socket fake (then it moves hub-side onto a `Response` field with the Client plumbing that entails); or a `report`-result *should* carry mail once the redundant-report concern is otherwise solved (drop the skip).
