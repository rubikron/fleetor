- **Startup setting.** "Finish remaining tasks upon startup" is `startup_tasks` in `~/.fleetor/config.json`, written through `write_config_key` like the target and read at each launch, as D-061's `dev_mode` was. Only a JSON `true` is on. The Settings switch shows what the write returned. No new file.
- **`{startup_tasks}`.** An optional orch placeholder with three renderings: ask the operator first (fresh launch, the default), resume in-progress tasks and announce them (fresh launch, setting on), or nothing to triage (a reopen, whatever the setting says). `render_orch` keeps its signature and renders "ask"; the app calls `render_orch_at`.
- **Earlier run.** An owner whose lineage is not the answering session's reads as `worker-3, earlier run` in the CLI and the Tasks view, and is not `--mine`. The `Board` reply carries the answering lineage so the CLI can tell. With no fleet running every owner is from an earlier run.
- **Carried over.** The Tasks view banner counts open tasks owned from another lineage, with or without a fleet.
- **Operator release.** The Tasks view offers Release on an open, owned task; its form requires all four fields, and "where" is typed because the operator stands in no checkout.
- **Briefs.** orch learns release, the earlier-run reading and resuming from `fleet task show`; a worker learns release, never to take up an in-progress task orch did not hand it, and to re-check its task after a resume.
- **Measured, in rendered characters (D-103's unit).** orch 17,112 → 18,236 with the longest startup text (+6.6%); worker 8,835 → 9,409 (+6.5%). Both pass D-103's tripwire (17,700 and 9,150). Restated with the same ~3.6% headroom: **orch 18,900, worker 9,750**.
- **Reverses if.** Live runs show orch skipping the triage because it sits in a subsection, in which case it moves to the top of the brief.
