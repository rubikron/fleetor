- **What changed.** `PaneId::Critic` joins `Orch`, `Worker(n)`, `Operator` and `Evaluator`, and `PaneSpec::Critic { run: RunSource }` joins the three placement variants. A new `src-tauri/src/critic.rs` says what it is told and where it works; `prompts/critic.md` is its brief, baked in with `include_str!` and overridable from `~/.fleetor/prompts/critic.md` like every other brief; `PaneContext` carries a third template. In the interface it is a rail row and an always-mounted stage view with one Start button. Neither `prompts/orch.md` nor `prompts/worker.md` changed by a byte, and `crates/fleetor-core/src/brief.rs` — where `VERBS` lives — was not touched at all, so `brief-cost` for this ticket is **0**.
- **The one fact every asymmetry falls out of: the Critic is a reader, not a participant.** `Operator` has no pty; `Evaluator` has a pty and is hidden; this has a pty and is simply not *in* the fleet. From that one fact: nothing enumerates a non-participant, so `is_fleet_member()` is false and it is therefore in no `fleet roster` listing, is no leg of a `fleet broadcast`, and is in no brief's peer list — all three through the single filter in `PaneRegistry::roster`, which is what `Hub::roster` and `Hub::broadcast` both read. And it is given **no `FLEET_SOCKET` and no `FLEETOR_PANE`**, which is what "it cannot message the fleet" means in code rather than in prose: the `fleet` CLI resolves that variable before it does anything else, so a `fleet send` typed inside the Critic exits non-zero with the sentence naming the variable and no pty is written to. `spawn::apply_pane_env` split into `apply_terminal_env` (what makes a process one of this app's terminals) plus the two fleet variables, so the Critic can have the first and not the second.
- **It is openly named, and that is the load-bearing difference from the evaluator (D5, D7).** The evaluator is hidden because WP-12's veil is what makes a handoff evidence rather than performance. Nothing about the Critic depends on the fleet not knowing it exists, so its brief is a file the operator can read and rewrite, it exists whether or not the mode is on, and no tripwire greps the fleet's prose for the word `critic`. **The veil tripwires were not weakened to make room for it**, and one of them caught this change while it was being written: `no_pane_is_briefed_about_dev_mode` failed on doc comments in `pane.rs` that named the mode and its test file while explaining the Critic. The prose was rewritten; the grep was not.
- **`prompts/critic.md` joined `WHAT_A_PANE_IS_TOLD` and deliberately did not join `WHAT_A_PANE_IS_TOLD_IN_PROSE`, and the reason is one phrase.** It is on the mode list because it is prose a terminal is handed and it has no business naming the mode — adding it cost nothing, since it names no spelling of it. It is off the evaluator-vocabulary list because six of that list's seven needles never appear in it and the seventh, `answer key`, appears in *"You have no answer key"* — D10's own phrase for why this pane judges the run and never the work. Putting the file on that list leaves exactly two moves, editing the prompt the spike converged on or widening a needle so it stops catching what it was written for, and **neither is worth a grep on a file no fleet pane reads.** What replaced it is `the_critics_brief_is_openly_named_and_names_no_evaluator_vocabulary`, which asserts the other six on that file, plus `the_evaluators_needles_still_mean_the_evaluator_and_never_the_critic`, which pins the six needles as literals and checks that none of them overlaps this pane's name — the collision D7 renamed it to avoid.
- **The brief is the spike's v3 prompt, and it ships with six categories rather than D10's five — a deliberate departure, on the spike's evidence.** `docs/notes/critic-spike-notes.md` measured two runs under three prompts. D10's categories 3 (blocks with no criteria) and 4 (two workers editing one file) produced **nothing on either run**, and the sixth category the spike added — *"Anything else the fleet did that cost the operator"* — produced the largest finding on **both**: run A's reviewed work never integrated because the integration worktree belonged to a different repository, and run B's `orch` abandoning its own workers to edit the target in place, uncommitted, until the operator interrupted it. Without a sixth slot the Critic reports a tidy run and misses what actually cost the money. The operator approved the addition. **It is a bounded slot, not an opinion slot**, and the spike is explicit that this is why it did not reopen the mush door: it carries the same citation rule, bans inference and prescription by name, and sends any moment that cannot be cited to UNCITED. That wording is not to be loosened.
- **The failure mode the brief is shaped against is not the one the arc predicted.** The spike's control — the same archive, an unconstrained prompt — did not produce "solid work, maybe more tests". It produced fluent, substantive, largely **true** prose with not one citation in it, judgements of the *work* ("wasn't a rubber stamp"), and prescriptions ("should be namespaced per-target"). Mush would be obvious and harmless; this is neither, because an operator cannot separate its true claims from its unfalsifiable ones. The two clauses doing the work are the **citation rule** and the **ban on prescription**, and `prompts/README.md` now says so with the measurement behind it, because story 35 makes the brief the operator's to edit and nothing defends against them being trimmed.
- **Its write-guardrail roots are its own working directory alone, like the evaluator's.** `placement::guardrail_notices` branched on `pane.is_evaluator()`; it is `pane.is_evaluator() || pane.is_critic()` now — **two names on one branch rather than a shared `PaneId::reads_a_run()` predicate**, because D5 refused one identity with a mode flag and a shared predicate would read as one. Not `_shell`, which holds the live event log it is reading, and not the operator's `[fence] allow` extras, which exist for the panes doing the work. Asserted the way ticket 04 asserted the evaluator's: `orch` is placed from the same layout with the same context in the same test, so "narrower" is a comparison and not a remembered number. Its config dir is `~/.fleetor/critic/config`, outside `_shell/pane-config/` — otherwise `runs::copy_transcripts` would copy the Critic's own transcript into the directory it is reading, as it works, and `harvest_transcripts` would file it into the run archive where the next run's Critic would read it as if it were the fleet's.
- **`RunSource` is declared in full and only `Live` is built, which bends this module's own rule on purpose.** `placement`'s doc says every variant that exists, works — a variant that errored is the `building.md` §6 trap, because the obvious next move on finding one is to point it at something live. `RunSource::Archived(id)` is declared because the design prototype's shape is what a Critic *is* and the type should say so, it is **constructed nowhere in the application**, and `place_critic` answers it with `ARCHIVED_NOT_BUILT` naming ticket 09. The §6 trap does not apply because there is no other live path to re-point it at: reading a past run does not exist anywhere yet. The alternative — falling through to the live run — was refused as the worst of the three, since the operator would get a pane that looked right and was reading a different run than the one they asked for.
- **Two match arms answer questions rather than filling holes, and both follow from the identity.** `machine_notices` now returns nothing for the Critic, for the opposite reason it returns nothing for `orch`: `orch` emits the `fleet`-binary line itself, and for the Critic that line would be **false** — it has no socket, so building a `fleet` binary would change nothing about it, and "panes cannot message each other" would send the operator to fix something irrelevant. And `place_critic` takes no `target`: the Critic reads a run, the repository the fleet was pointed at is named inside `manifest.json` where it reads it like every other fact, and a pane that reads a run has no business holding the live checkout. Every other arm — `slot()`, `Display`, `FromStr`, `channel_key`, `spawn_pane`'s spec match — is a one-liner that follows directly.
- **`FromStr` accepts `critic` for exactly one reason, and it is not that a model types it.** `pty_spawn` takes a `PaneId` and Tauri deserializes it out of the webview's JSON, so the name has to parse. No pane can learn it: it is in no brief, no roster and not in `ParsePaneIdError`'s list, which `pane.rs` still documents as the fleet's own names and nothing else.
- **What would reverse it.** A measurement showing the brief produces the control's failure mode under a cheaper model — the spike ran on Sonnet and explicitly does not establish that a smaller model holds the discipline, so putting one behind this pane means repeating that measurement first. Or a third run-reading pane, at which point two names on the guardrail branch becomes three and a predicate on `PaneId` starts being cheaper than the ambiguity it costs. Or `fleet task post` changing so criteria become optional, which is the one change that would make D10's category 3 start earning its keep and would weaken the case for category 6 carrying the run.
- **Verified:** **219** shell tests green under `cargo test --features devmode`, up from **202** at `bf52164` — 157 lib (was 151; six new, in `critic::tests` and `prompts::tests`), **7** dev-mode (was 4), 8 evaluator, 11 real-pty, **22** placement (was 16), **5** views (was 3), 9 write-guardrail. **214** green under plain `cargo test`, up from **197**: every one of the six Critic placement tests runs without the `devmode` feature, which is the assertion that it is a product feature. **215** workspace tests green from the repo root, up from **213** — two new `PaneId` tests in `crates/fleetor-core`. `cargo build`, `cargo build --features devmode` and `npm run build` all clean. `cargo clippy --all-targets --features devmode` reports the same **two** pre-existing warnings and no new one. A diff of `prompts/orch.md` and `prompts/worker.md` against `bf52164` is empty, and `crates/fleetor-core/src/brief.rs` is untouched, so the verb list is unchanged by construction. **No test was deleted, weakened or marked ignored**; one existing test (`pty.rs`'s roster test) gained the Critic beside the evaluator, and `tests/placement.rs`'s `mod common` lost its `devmode` gate so a default build can use the fixture. Four claims were mutation-checked rather than only asserted: giving the Critic `apply_pane_env` fails `the_critic_is_given_no_socket_so_fleet_send_inside_it_reaches_nothing`; narrowing the guardrail branch back to `is_evaluator()` alone fails `the_critics_write_roots_are_its_own_directory_alone_and_orch_is_wider`; dropping `Critic` from `is_fleet_member` fails `a_running_evaluator_is_not_on_the_fleets_roster`, which is the one filter `fleet roster` and `fleet broadcast` both read; and adding `prompts/critic.md` to `WHAT_A_PANE_IS_TOLD_IN_PROSE` fails `no_pane_is_briefed_about_the_evaluator` on `prompts/critic.md:14` alone, which is the evidence for the paragraph above rather than an inference.
- **Not verified:** **no fleet has been started since this landed, and no Critic has ever run** — the same honest gap D-062, D-065, D-066, D-069, D-071, D-072, D-073, D-074 and D-075 each record. Nothing here measures what a Critic pointed at a live snapshot actually produces; the spike measured *archived* runs read by an ordinary session with the prompt pasted in, never this pane, never this placement, never `snapshot_live_run`'s output. **One wrinkle in the shipped brief is known and was left verbatim:** its archive listing names `state.db`, which a live snapshot does not contain — `runs::snapshot_live_run` writes `events.json`, `manifest.json` and `transcripts/` only, and that manifest says "There is no state.db here" in so many words. The brief was shipped as the spike wrote it because the ticket asks for the prompt the spike converged on, and ticket 09's archived runs *do* have a `state.db`; whether a Critic burns a turn on the missing file is unmeasured. **The one-directional claim is the one that is tested.** `fleet send` from inside the Critic reaches nothing, structurally. The reverse — a pane sending *to* `critic` — is not blocked in the hub, and would write into the Critic's terminal if a pane ever typed that string; it is protected the way the evaluator's is, by the name being absent from every brief, every roster and the parse error, and nothing more. Closing it would mean a branch in the delivery path, which Tier 1.4 forbids. The Critic's cwd is a snapshot of the live run, so in a session where the evaluator has already messaged `orch`, the word `evaluator` is in the `events.json` the Critic reads — that is run data rather than prose and nothing in this ticket changes it, but it is the one place the two panes can meet. `rustfmt` is not installed on this machine, so formatting was not checked. No live spend.
