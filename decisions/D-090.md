---
id: D-090
title: "harness.rs becomes interface-only, and machine-probing joins the trait"
phase: "WP-30"
status: alive
---

- **The seam stays compile-time; what changes is where the implementations live.** Operator's call, 2026-09-11. `HarnessSpec` + the `Harness` trait remain the template a TUI must satisfy, and a registration remains a Rust file rather than a manifest FLEETOR reads at startup. Rejected: data-driven registration from TOML/JSON — nine of the trait's methods are behaviour that no manifest can carry (`read_usage` parses a vendor transcript format, `read_operator_login` narrows a macOS keychain item, `install_guardrail` writes JSON for one vendor and TOML for the other, `Transport::SqliteBackup` runs `VACUUM INTO`), so a manifest would cover the `'static` fields only and leave two registration mechanisms and a harness that can be half-declared — the exact failure the missing `Default` exists to prevent. Rejected also: a narrow manifest for pure argv+config harnesses, for the same reason at smaller scale.
- **`harness.rs` holds the interface and nothing else.** The checkpoint types, the `Harness` trait, the registry and the shared helpers stay; `CLAUDE_CODE_SPEC`, `impl Harness for ClaudeCode`, `claude_code_diagnose` and their unit tests move to `placement/claude_code.rs`, beside the `placement/codex.rs` that already exists. Reading `harness.rs` is then reading what a TUI must answer, with no vendor's answers mixed into it.
- **`diagnose` becomes a trait method, superseding the argument recorded at `placement/mod.rs`'s `discover_for_the_gate` that it "would have made it a fifteenth checkpoint, which is the wrong shape".** That argument rested on vendor-facts-versus-machine-facts, and the distinction is already broken: `read_operator_login` is on the trait today and reads the macOS keychain. The invariant that actually holds is **a harness is handed its facts, never discovers them** — which Claude Code's probe already obeys (it takes `home` and `path` as arguments) and codex's does not: `codex::diagnose(&Installation::default())` inherits the application's environment behind a `Default`, a process read hiding inside `placement`. Folding the probe onto the trait with an explicit facts argument closes that hole and deletes the gate's hand-written two-vendor vector in one move. Rejected: a second `HarnessProbe` trait (same end-state at the cost of a second registry and a new way for a harness to be half-registered); leaving the vector (adding a TUI would still mean editing `mod.rs`).
- **The literals tripwire becomes per-harness too, moving with the implementation it guards.** Operator's call, 2026-09-11. `harness_literals.rs` resolves every needle against `claude_code().spec()` (verified, line 248) and hand-lists twelve scanned files, so a third harness's vendor strings get no coverage at all today; it iterates `registered()` instead, and each harness carries its own needles beside its own spec. Rejected: a free ride on conformance alone (leaves the re-hardcoding tripwire guarding one vendor forever); requiring a named vendor suite per harness on top of conformance (ceremony conformance already performs — the four vendor-named suites exist because codex needed *measurements* conformance structurally cannot express, and mandating such a file up front produces a stub that passes and proves nothing).
- **Extraction is tripwire-neutral, checked before committing to it.** `placement/codex.rs` is absent from `MIGRATED`, so vendor implementation files are unscanned; creating `placement/claude_code.rs` therefore trips nothing.
- **A vendor file owns anything that knows the vendor's format; `harness.rs` owns anything driven purely by spec fields.** Operator's call, 2026-09-11 — the line the extraction is drawn on, after measuring that both vendors' bodies currently live in shared modules under generic names and delegate *backwards* into them from the trait impl. Moving: `spawn::project_key` (its own doc already says "this is Claude Code's own answer to checkpoint 14, not the fleet's") and `context_gauge::transcript_usage` (called "the default reader"; it is Claude Code's JSONL `usage`-object parser) into `claude_code.rs`; `context_gauge::codex_vendor_usage` (called only from `codex.rs:1007`) into `codex.rs`. Staying: the JSON read-modify-write inside `spawn::seed_config_dir`, which is genuinely spec-driven — it reads `seed_keys` and `trust_keys` off the spec and would serve any harness keeping one JSON document — so it moves to a neutral support seam rather than into a vendor file. Its `debug_assert` that `seed_file == trust_file` is Claude Code's and goes with the vendor. Rejected: a thin extraction leaving the four bodies in place (`claude_code.rs` would be a spec plus three one-line delegations pointing back into shared files — the present situation with added indirection); a hard extraction burying the JSON seeder in `claude_code.rs` (a third JSON-config harness would have to copy it or import from a vendor file).
- **The moved readers are renamed to their vendor, noted rather than asked:** once private to their own file, `transcript_usage` and `codex_vendor_usage` mislead in opposite directions — one claims to be general and is not, the other carries a vendor prefix it no longer needs.
- **The three remaining vendor-named production sites stay.** Operator's call, 2026-09-11. `mod.rs:802` (the two judges answer Claude Code, C15), `fleet.rs:164` (`FleetSeats::unpicked`, the fleet nobody has picked yet) and `REGISTERED` itself each *name* a harness through the registry's public API without knowing anything about it — unlike the four bodies this ticket moves, which knew Claude Code's JSON shape, its canonicalization rule and its JSONL format. A third TUI registering changes none of the three. Rejected: making the two defaults configurable (they are product choices, and C15's is deliberately "the absence of a place to put one"); replacing `REGISTERED` with auto-registration (the array *is* the registration gesture — "a gesture an operator makes, not a side effect" — and discovery would let a harness register without anyone deciding it should).
- **The frontend needs no work, verified rather than assumed.** `PaneHead.tsx` knows no vendor name; the harness name, mark and model arrive on the wire as one `PaneIdentity`, and `tests/gate_pickers.rs` fails the build if a branch on harness name appears.
- **It lands as three commits, in order: the file move, the probe onto the trait, the needles onto the vendor files.** Operator's call, 2026-09-11. Only the first is mechanical, and its entire review is "check that nothing changed" — a check that becomes impossible the moment behaviour rides along in the same diff. The probe change is the only step that can regress the gate, so it gets its own bisect point. The needles go last because they may surface genuine hard-coding, which is a finding rather than a blocker for the two steps before it; checked at spec time, no codex spec literal sits in the twelve scanned files outside tests, so it should land green. Rejected: one commit; the probe change first.
- **Parked for a future session, specified rather than started.** Operator's call, 2026-09-11. Written up as WP-30 (`docs/roadmap/30-harness-interface.md`, spec in [issue #52](https://github.com/rubikron/fleetor/issues/52)) and not implemented in the session that designed it. It blocks WP-24: registering cursor through a layout that is about to move would pay C57's cost twice.
