---
id: D-077
title: "`fleet reply` refuses a recipient at parse, and the discriminator is the argv element rather than the first word"
phase: "meta"
status: alive
---

- **What changed.** One match arm in `crates/fleetor-cli/src/main.rs` — `Command::Reply { text } => Op::Reply { text: reply_text(text)? }` — and the `reply_text` function it calls, which refuses when `text.first()` parses as a `PaneId` and otherwise returns `join(text)` exactly as before. **No verb was added, renamed or removed.** `crates/fleetor-core/src/brief.rs` (where `VERBS` lives), `crates/fleetor-core/src/wire.rs` (where `Op` lives), the clap `Command` enum, `prompts/orch.md` and `prompts/worker.md` are all byte-unchanged — `git diff` on the four files is empty and the only hunks in `main.rs` are at the match arm, at the new function, and in `mod tests`. `brief-cost` is **0**.
- **The defect is measured, and its shape is the reason it went unnoticed.** `Op::Reply { text }` has no recipient field, unlike `Op::Send { to, text }`, and `Command::Reply`'s `text` is `trailing_var_arg`. So `fleet reply worker-3 "Agreed — Rooftop Garden"` parses cleanly, prepends `worker-3` to the *message body*, and delivers the whole thing to whoever messaged the sender last. Nothing failed, so nothing was corrected. A 5m 40s run produced **nine** misdeliveries; two panes spent turns diagnosing "tangled cross-replies" and one re-sent three confirmations it had already sent. The panes were not being careless: `prompts/worker.md:23` teaches ``fleet reply "<text>"`` on the line *below* ``fleet send orch "<text>"``, and a name argument pattern-matched across. **The brief is correct and was not changed** — a verb whose only safe use requires the reader not to generalise from the line above it is the thing to fix, not the line.
- **The discriminator is the first argv element, not the first word of the joined string, and that is the whole of the care this needed.** `fleet reply worker-3 "Agreed"` arrives as `["worker-3", "Agreed"]` and is refused; `fleet reply "worker-3 said the annex is out"` arrives as one element that is not a pane name and goes through untouched. A pane must be able to open a message with a peer's name — quoting one, reporting on one, arguing with one — and **replacing a silent misroute with a silent refusal would be the worse trade of the two.** The first-word reading was mutation-checked, not merely avoided: swapping `text.first()` for `join(text).split_whitespace().next()` fails two tests.
- **It asks `PaneId::from_str` rather than matching spellings of its own**, so it is exactly as wide as `fleet send`'s recipient and cannot drift from it: `orch`, `orchestrator`, `lead`, `o`, `operator`, `critic`, the out-of-fleet grader's own name, and every worker as `3` / `w3` / `worker3` / `worker-3`, all case-insensitive and trimmed. `self` is deliberately *not* caught, because `fleet send self` is not a thing — only `fleet cmd` resolves that word, in `target()` — so a reply may start with it. A first token beginning with `-` never reaches the check at all; clap rejects it first, `-1` included.
- **Tier 1.4 holds because it refuses at parse, and that is not a matter of degree.** `reply_text` runs inside `run()`'s `let op = match cli.command`, in the same position as `Command::Send`'s `pane.parse::<PaneId>()` — **before** the tokio runtime is built, before `UnixTransport::new(socket()?)`, before `Client::connect`, before an `Op` exists. Nothing between a `fleet send` and a pty gained the ability to delay, refuse, reorder, drop or alter anything; this is the same shape of failure `fleet send worker-9` produces today. A check downstream of the socket would have been the wrong implementation of the same sentence.
- **WP-15's Tier 1.4 grep caught this ticket while it was being written**, which is worth recording because it is the second time (D-076 records the first): `the_delivery_path_cannot_see_the_evaluator` failed on two test-data literals in `main.rs`. The literals moved to `crates/fleetor-cli/tests/reply_recipient.rs`, which is not a file a message passes through; the grep was not touched. **The refusal message echoes back only the word the pane itself typed**, so it teaches no name to a pane that did not already have one — the same property `ParsePaneIdError` keeps by listing the fleet's names and nothing else.
- **What would reverse it.** A measured case of a pane wanting to send a one-token message that is exactly a pane name (`fleet reply orch`, `fleet reply 3`) — those are refused today and the refusal is the cost of the rule, unmeasured. Or a recipient field arriving on `Op::Reply`, at which point the refusal becomes a redirect and this entry is superseded rather than amended.
- **Verified:** **222** workspace tests green from the repo root, up from **215** at `bc9ef09` — four new unit tests in `crates/fleetor-cli/src/main.rs` beside the existing parse tests, three new integration tests in `crates/fleetor-cli/tests/reply_recipient.rs`. **219** shell tests green under `cargo test --features devmode` and **214** under plain `cargo test`, both unchanged: the shell does not test the CLI. `cargo build --features devmode` and `npm run build` clean. `cargo clippy --all-targets --features devmode` reports the same **two** pre-existing warnings and no new one; `cargo clippy --all-targets --workspace` from the root reports the same **three** pre-existing `fleetor-core` warnings and no new one. **No test was deleted, weakened or marked ignored.** The exit code and stderr are asserted against the real binary rather than against a bool: `naming_a_recipient_exits_non_zero_and_says_so_on_stderr` runs `env!("CARGO_BIN_EXE_fleet")` with `FLEETOR_PANE` and `FLEET_SOCKET` removed and pins `status.code() == Some(1)`, the exact sentence, and an empty stdout. `a_message_that_begins_with_a_peers_name_is_not_refused_here` proves the narrow half from the other side — that argv shape gets past every local check and fails on the missing socket instead, which is as far as a test without a hub can push it.
- **Not verified:** **no fleet has been started since this landed** — the same honest gap D-062, D-065, D-066, D-069, D-071, D-072, D-073, D-074, D-075 and D-076 each record. **The nine misdeliveries are the operator's measurement of a run this session did not observe**, and neither the two panes' diagnosis turns nor the three re-sent confirmations were re-derived from the archive here; they are the stated reason for the change and are taken as given. Nothing measures whether a pane that hits this refusal actually re-types `fleet send <pane> "…"` on its next turn rather than dropping the message or arguing with the tool — the sentence is shaped for that and the shape is untested against a live model. **`fleet broadcast` has the identical argv shape and was deliberately not touched**: `fleet broadcast worker-3 "…"` also glues the name onto the body, but broadcast has no recipient to get wrong, so the cost is a stray word rather than a misroute, and no measurement says it happens. `rustfmt` is not installed on this machine, so formatting was not checked. No live spend.
