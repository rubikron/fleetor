---
id: D-071
title: "the target is fixed once a pane exists, and the backend is what says so"
phase: "meta"
status: alive
---

- **What changed, and it is a behaviour change.** `fleet_set_target` and `fleet_pick_target` now **refuse** when the pane registry holds any pane. Both take `State<Arc<PaneRegistry>>` and funnel through one new private `adopt_target`, which checks `ensure_target_settable` before `write_target` and `apply_target`. A command that used to succeed unconditionally now fails in one case. Nothing about the start gate moves: with an empty registry both commands do exactly what they did.
- **The rule is not new; only its address is.** `Fleet.target`'s own doc comment already said the target is "safe to update before panes exist (the start gate); once panes are running the UI hides the target input" — so the invariant was written down, believed, and enforced entirely by `App.tsx:221`'s `!started` latch. That is the interface deciding what the thing that owns the state may do. Half a fleet in one repository and half in another is incoherent, which is the same reasoning that makes the target resolved once at bootstrap rather than re-read (D14).
- **The condition is `PaneRegistry` non-empty — existence, not membership and not liveness.** `roster()` was rejected because it filters to `is_fleet_member()`, so a session holding only the evaluator would answer "no panes" and accept a target change under a pane reading a run. `accepts_input()` was rejected because a pane that has *exited* was still seeded — config dir, worktree, brief, guardrail roots — against the target that was current when it spawned, and `PaneRegistry::spawn` respawns it in place rather than treating it as new. The map is emptied only by `kill`/`kill_all`, which is exactly the moment nothing holds the old target: kill every pane and the target is settable again, by construction rather than by a second rule. A poisoned registry answers "a pane exists" — the caller is a guard and must fail closed.
- **The broader condition that lost: "the fleet is bootstrapped."** `FleetState` being `Some` is what the interface actually keys on (`started` flips when `fleet_bootstrap` resolves, before any pane spawns) and it refuses strictly more often. It was rejected because it is not a reading of "a pane exists" — it is a different rule, and the honest version of it belongs with WP-21's half of D14, where the target snapshot and the evaluator wake become one source. Between bootstrap and the first spawn, `apply_target`'s in-place update is still correct and still the documented behaviour; refusing there would have been a rule this entry did not argue for. **The window is checked and it is not a gap:** `PaneContext` holds the *unrendered* templates and the launch config (`prompts.rs:78`) — nothing target-dependent — and `fleet_bootstrap` reads `f.target` live at each spawn (`fleet.rs:362`), so a target set between bootstrap and the first spawn is honoured in full. That is why the narrower condition costs nothing here.
- **One funnel, not two guards.** The picker also calls `ensure_target_settable` up front, before the folder dialog opens — making an operator browse to a folder and only then refusing it is a worse way to deliver the same sentence — but it still goes through `adopt_target`, so the picker is not a second place the rule has to be right. The refusal precedes `write_target` deliberately: a `config.json` recording a target no pane will ever spawn against is worse than no change at all.
- **The sentence, held as a constant so the test asserts on what the operator reads.** "the target is fixed for a running fleet — every pane was configured against the current one when it spawned. Stop the fleet (close the window) and set the target again at the start gate." **An operator who relied on the old behaviour** — calling `fleet_set_target` mid-run and expecting the next spawn to land in a new repo — never actually got that: panes already up kept the old one, so the result was the split fleet this refuses. The replacement move is the one in the sentence: close the window (which is `teardown_fleet`, killing every pane and shutting the hub), relaunch, set the target at the start gate, start.
- **The interface guard stays, and no UI file was touched.** `!started` still unmounts `StartGate`, which is the only component that calls either wrapper. It is now belt and braces: the interface keeps the control out of reach earlier than the backend refuses, and the backend refuses whatever reaches it.
- **What would reverse it.** A pane kind that genuinely does not care which repository the fleet is in — the Critic reading an *archived* run is the near candidate (WP-23), and the fix would be a predicate on the spec rather than a count of the map. Or a supported target switch that tears the fleet down and brings it back up as one action, at which point the refusal becomes a confirmation prompt in front of that action instead of a dead end.

No prompt template changed, so `brief-cost` is 0 and D-068's 51-token headroom is untouched. **Not verified:** the refusal has never been seen in the running app — no fleet has been started since this landed, the same honest gap D-062, D-065, D-066 and D-069 each record. Nothing exercises the two `#[tauri::command]` wrappers themselves; a `State<'_, T>` is not constructible outside a Tauri runtime, so the test drives `ensure_target_settable`, the function both wrappers pass through, and the wiring between them is held by reading the diff. No live spend.
