id: D-099
title: "a new fleet and a reopen are one launch: tear down, stage the old run, fix seats and target at launch"
phase: meta
status: alive
---

- **What.** One command, `fleet_launch(Fresh | Reopen(id))`, replaces `fleet_bootstrap` and `run_reopen`. Order: verdict → kill panes, drop fleet → stage the old run (rename `state.db`/`run.json` into `_shell/archiving/<id>/`, capture session ids, clone transcripts) → build the fleet → background finish (freeze, export, index). No confirmation. `reopen.json` is removed; the id is passed in. Seats and target are fixed on `Fleet` at launch for both sources (`reopened_seats` becomes `seats`): Fresh takes the gate's, Reopen takes the run's recorded ones (D-095 extended to the target). The gate — seats and target — always describes the *next* fleet and stays editable while one runs. UI: one `launch(source)` switches to the fleet view at once, bumps `generation`, resets statuses, feed and messages, and reloads tasks through a `resetTasks()` hook the task PRD fills in; on failure it returns to Home with the reason. History shows one row per run: Running now → Archiving… → Archived. One live fleet at a time.
- **Slice 1 additions.** `fleet_launch` rejects with `{ reason, torn_down }`, not a string: `torn_down` is false for a refusal at the verdict, which leaves the running fleet untouched. The backend emits `fleet://launching` on every launch once the verdict has passed and the old fleet is down, before the new log opens; the UI's grid remount and its resets of statuses, feed, messages and tasks wait for it, so a refused launch changes nothing but the view. A run's id is claimed at launch (`runs::new_run_id`, recorded in `run.json`), unique against `runs/` and `pane-config/`, so two launches in one second share neither an archive name nor a sessions id.
- **Slice 2 additions.** `fleet_set_target` and `fleet_pick_target` no longer refuse while a pane exists and no longer touch the live fleet: they write `config.json` and forget the harness reading. `Fleet.target` and the task store keyed by it are set once, in build. Home reads the gate's target through a new `fleet_next_config`; `fleet_config` still answers with the running fleet's, which is what the top bar shows. The setup panel opens by default, and `StartGate` lost its target input and its `config` / `onTargetChanged` props. Not verified in the running app.
- **Why.** Clicking New fleet while a reopened fleet was live hit `fleet_bootstrap`'s early return (`fleet.rs:1381`): nothing was torn down and the reopened seats kept running. New fleet and reopen were two paths, and only reopen had a teardown.
- **Amends.** D-058 (reopen via marker, R2), D-071 (target refused while a pane exists → edits apply to the next launch), D-095 (`reopened_seats` → `seats`, plus recorded target). WP-28's one-archive-path rule holds: `rotate` splits into stage + finish, shared by launch, app open and quit.
- **Out of scope.** Restart never respawning, worktree cleanup, the evaluator (operator says it is deleted; this branch still has it, D-073/D-074 alive), per-target gate memory, batching appends (rejected: ~200 events/run, and it would delay delivery).
- **Slices.** 1: `fleet_launch` + UI `launch()`, synchronous archive. 2: target editable while live, setup panel open by default, StartGate dead code removed. 3: parallel kills, background finish, `_shell/archiving/` sweep, History row states.
- **Reverses if.** Two fleets must run at once — then `_shell`, `FleetState`, the socket and pane ids are keyed by session and this single-slot launch is the wrong shape.
