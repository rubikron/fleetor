---
id: D-047
title: "WP-05: the task board is a fold over the event log, and the one arm that never reaches a terminal"
phase: "WP-05"
status: alive
---

- **The default that lost was "a board of work needs somewhere to live."** It does not: `fleet task list` is `task::board(store.events_since(0))`, a fold over the same log the message feed replays. No `tasks` table, no cached copy in the hub, no second source of truth — two hubs over one store compute the same board, pinned by `a_restarted_hub_replays_the_same_board_from_the_log_alone`. The vestigial `tickets` table migration 0003 dropped stays dropped; this package adds no migration at all, because a new `FleetEvent` variant is already a `kind` and a `payload` in the one table there is.
- **`fleet task post|update|list` — one verb, three subcommands, one wire op.** The requirements spend the verb budget once, so `VERBS` gains exactly `task`, the clap tree nests underneath it, and `Op::Task { action: TaskAction }` keeps the pinned "wire tag *is* the CLI verb" test true. Flat flags throughout (`--outcome`, repeatable `--crit-t` / `--crit-s`, `--to`, `--instructions`, `--parent`, `--converges-on`): a weak model emits flat flags far more reliably than JSON, and a malformed nested document costs a whole turn to diagnose from a parser error.
- **The schema is the vision's shape verbatim.** `TaskBlock { outcome, technical[], semantic[], worker, instructions?, parent?, converges_on? }` — what this execution enables, how anyone could check it, which part of the confirmed vision it serves, whose it is, and where it sits among the streams. The block carries no id of its own: the id lives on the `FleetEvent::Task { task, from, at, change }` that posted it, so a post and every later update join on one field rather than two spellings that could disagree. `at` is on the payload rather than only the DB row because the board is replayed in two places and only one of them ever sees a row.
- **`--to`, `--crit-t` and `--crit-s` are `required` in clap** — the same contract-on-the-sender argument that made `fleet cmd --why` required (D-045), and for a sharper reason here. An unassigned block sitting on a board is a *backlog item*, and a backlog item is a thing something eventually picks up: that is the ticket system's first move. Requiring the owner at post time means every block is a decomposition already decided rather than a queue. A block with no checkable criterion is a wish, and the whole point of the shape is that a claim of `done` can be argued with.
- **Status is descriptive and no transition is enforced.** `planned|claimed|done|dropped`, and `done → claimed → planned` is legal, tested twice (unit and over the socket). A worker who marked a block done and then found a failing criterion has to be able to say so; a board that argued would only teach the fleet to stop updating it. `done` is an **unverified claim** — WP-06's receipts and review are what turn one into a fact, and nothing in the CLI or the UI renders it as anything else.
- **Anyone may update any block.** No ownership check: the event's `from` is the whole of the accountability, and a peer who spots that a block marked `done` has a failing criterion must be able to say so on the same record. That is what makes WP-06's review possible without a permission system.
- **The one refusal that is not a gate.** An update naming a block that is not on the board is refused with `no task "…" is on the board — 'fleet task list' shows the ids`, and nothing is written. This is referential validation, the same class as "no pane worker-9 is running" — it constrains nothing about *which* status may follow which, only that a claim has something to be a claim about. Without it a typo'd id vanishes into the log unread. Recorded here rather than absorbed, because it is the only place in this package where anything reads task state before doing something.
- **The tripwire list held; nothing on it was built.** No gate, no supervisor or poller, no auto-routing or load-balancing, no blocking claim, no per-task worktrees, no `Assign`-like op. Cycles in the parent links are tolerated — the replay never walks them, and `fleet task list` renders flat with a note when it finds one. A dangling parent id renders as a root. Validating the links into a legal graph is the workflow engine this is deliberately not.
- **The delivery path's diff is empty, and this time the whole crate that owns it is.** `crates/fleetor-core/src/message.rs`, `crates/fleetor-core/src/command.rs`, `src-tauri/src/deliver.rs`, `src-tauri/src/pty.rs`, `crates/fleetor-server/tests/pane_messaging.rs` and `src-tauri/tests/panes.rs` have **zero** `git diff`. `hub.rs` grew a `task` arm and its dispatch line; no line of `send`/`broadcast`/`reply`/`deliver`/`log_message`/`ask_app`/`last_inbound` changed (checked as a grep over the diff). `src-tauri`'s only change is one test fixture's verb list in `prompts.rs`. `task.rs` copies eight lines of control-character filtering rather than reusing `message::sanitize`, on purpose: same idea, different boundary (a terminal *printing* `fleet task list` vs the pty delivery path), and sharing it would have meant touching the file whose diff had to stay empty.
- **`Hub::task` is not `async` and never touches `self.app`.** Every other arm asks the app to do something to a terminal; this one only reaches the store. The delivery-independence pin makes that a number rather than a reading of the code: ten posts, an update and a list send the app **zero** commands, and a `fleet send` to worker-2 is byte-identical at the pty and in the log whether the board is empty or holds ten blocks including worker-2's own marked `done`.
- **One asymmetry with the message path, deliberate.** A failed `append_event` fails a task op, where it only reaches stderr for a message. For a message the store records something that already happened; for a task the store *is* the deliverable, and reporting success would put a block on a board that does not have it.
- **The Tasks view is the fifth view and writes nothing.** `fleet | messages | tasks | activity | settings`, mounted like every other one (`.is-hidden`, never conditional rendering — §7.5, L7; the 11 real-pty tests and every xterm buffer are untouched). No post button, no status dropdown, no drag-to-reorder: an operator control here would be a second writer with no attribution on a screen where every entry is an attributed claim. WP-07 is where the operator gets a voice, by speaking to the fleet rather than editing its record behind its back. `ui/src/fleet/board.ts` mirrors the Rust fold — duplicated rather than fetched, because the events already arrive on the live bus and a Tauri command re-asking for them would be the second source of truth this package spent its whole design avoiding. Rust is the authority when they disagree.
- **Cost, measured — over budget again, and said out loud.** Rendered orch **1,910 → 2,228** tokens and worker **1,343 → 1,591** (DeepSeek Flash tokenizer, `examples/system-prompt-spike/count.py`): **+318 and +248**, against WP-05's budgeted ~150 *across both*. Just under four times the estimate — the same multiple, and the same reason, D-045 recorded: a verb costs what its *rules* cost, not what its syntax costs. Where it went: seven flag names that have to appear or the schema is unreachable, four status words that have to appear or an invented `in-progress` is a refusal, "write criteria that could fail" with its counter-example, and the diary-not-dispatcher clause with its consequence. Every one is pinned by a test, because shortening it turns it into advice. One tightening pass ran before the number was recorded (−6 orch, −27 worker). WP-09 now audits a **second** visible overrun; the standing tension in `00-index.md` carries both.
- **What would reverse it.** A live shakedown (WP-09) showing DeepSeek Flash cannot write criteria that could fail — in which case the block shape is right and the model is wrong, and the Tier 2 worker-model default is what moves. Evidence that the compact `list` output is still too expensive for a pane's context, which would make `--full` the wrong default half of a split. Or the failure this design is built against actually appearing: any pressure to have something *read* the board, at which point the answer is a Tier 1 question, not a feature.
