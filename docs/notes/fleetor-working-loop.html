Fleetor · mode of operation

How orch and the workers get work done

They work like a small team with a lead. orch agrees the goal with the operator, cuts it into blocks, and hands each block to a worker by message. Workers build in parallel, prove their work with a receipt, and review each other. Almost every step is something a brief asks for. Code enforces only the edges.

Asked: a brief tells the agent to do it, and nothing checks Enforced: code makes it happen or refuses the alternative Drifted: a real run recorded it going wrong

Who is in the room

operator

The human. Talks to orch, can message any pane, and reads the whole message log.

Owns the vision and merges trunk. Their word outranks orch and any block's criteria.

orch

The lead. Settles the vision, cuts it into blocks, assigns, merges, and reports the finish.

Never reviews its own blocks and never merges to trunk.

A fleet that starts fast on the wrong thing wastes five terminals instead of one.

worker ×4

The builders. Each takes one block, proves it with a receipt, and reviews a peer.

Never edits a peer's files. Cannot declare the mission finished.

A worker who finishes their own task and leaves the fleet no wiser has done half the job.

How they talk

Three ways to speak

  • sendTo one pane by name. This is how work is assigned.
  • replyTo whoever last messaged you directly. The usual move.
  • broadcastTo every other pane. Workers stay silent unless it names them.

Three answers the sender gets

  • acceptedThe text reached a live terminal. It does not mean the agent read it.
  • not deliveredThe pane is not running. Nothing else can refuse a message.
  • recordedIt went into the log and no terminal was touched. Task board updates, the handoff and messages to the operator answer this way.

What a pane sees arrive

[fleet · orch] your block is task-1-0, worker-3 reviews it when you are done

Rules of the room

  • A message sent to a busy pane is never held back or timed out. It waits in that terminal until the current turn ends. Messages that arrive together land as one paste, each still labelled with its sender.
  • A peer's message adds to the work in hand and does not replace it, unless orch is plainly assigning something new.
  • The operator's word is final. A pane says back what it is changing because of it.
  • When confused, ask: a peer for the missing piece, orch about the goal or who owns what, the operator when only they can settle it. Then carry on with what you can, because nothing waits.
  • A worker tells orch when it finishes, when it is blocked, and when it is about to touch a file someone else is likely in.
  • orch answers in the fleet, since anything it writes only in its own terminal reaches nobody.
  • A worker compacts its own context between blocks, never mid-task. orch watches the workers' context use and may compact or clear one, then re-briefs it.

What keeps them honest

Most of these produce evidence for a reader. Only the last three can stop an action.

Where real runs drifted from the briefs

Each of these comes from a recorded run. All of them happened at a step that is only asked for.

  • Step 02orch asked how to implement a small request instead of what it was for. The brief was tightened and the re-test held.
  • Step 06Two of four workers sat idle for an entire run and were never assigned a block.
  • Step 10A block was marked done 2.8 seconds before its own check was invoked. The receipt showed uncommitted changes. The worker corrected its own status about two minutes later.
  • Step 12Reviewed work was never integrated, because the integration checkout belonged to a different repository. orch noticed and reported it.
  • Step 13orch reported the run verified by receipts; no receipt existed. In another run it recorded the same unverified evidence as a handoff twice.
  • Delegatingorch abandoned the fleet and did the work itself, uncommitted. The run ended when the operator interrupted it.
  • TalkingA worker's question to the operator was never answered. Workers misaddressed nine replies in under six minutes, which the reply command now refuses.
  • SharingThree panes hit the same guardrail refusal, and three workers separately rediscovered the same setup fault, with no sign that one learned from another.

Where the briefs and the code disagree

  • The worker brief says to point context commands at yourself and lists the task board as read-only. The code lets any pane command any pane and post or update any block.
  • The orch brief gives one fixed path for the integration checkout. Checkouts are now kept per target and per session, and that fixed path is the one behind the failed merge above. Whether it still fails is unverified.
  • A recorded decision says orch runs with automatic approval. The code gives orch no such setting, and a test asserts it is absent.
  • A review verdict goes back to whoever asked for it, which is the author. The briefs do not say how orch learns the verdict beyond a note on the task board. This one is inferred from how replies are routed.
  • Peers' checkouts sit inside the area every pane is allowed to write to, so the write guardrail probably would not stop a worker editing a peer's files. This is inferred and untested.

Plan · proposed, nothing built

Tasks that stay until someone deals with them

Modelled on GitHub issues. A task lives with the target repository instead of with one run, so any agent or person can come back to it later, pick it up, change it, or close it. Every task carries a timeline of who did what, including the comments an agent leaves when it hands unfinished work on.

Today a task already has most of an issue's shape: an outcome, criteria, an owner, a status and a list of notes. Three things stop it behaving like an issue. It is deleted from view when the next run starts, it must name an owner when it is created, and its history holds only status changes and notes.

What changes

What stays exactly as it is

  • Nothing reads the tasks to route, assign, wake or block an agent. A task that stays open is picked up because an agent or a person chooses to pick it up.
  • A claim is a sentence, not a lock. Two agents can claim the same task, and the timeline shows that they did.
  • Every entry is attributed and timestamped, and nothing is ever deleted from a timeline.
  • Messages are untouched. Assignment can still travel as a fleet send, and nothing is added between a send and a terminal.

How it gets built

Four slices, each ending in something you can watch work. The first needs only decision 2 below; the second needs decision 1.

  1. S1

    Comments, release comments and a timeline

    Add comment, release and show. Claiming sets the owner. Receipts are written into the task's timeline. The Tasks view shows the timeline as a chain. The worker brief learns when to release instead of going quiet. Tasks still live inside one run.

    Demoworker-2 releases a half-finished task with what is left, and worker-3 picks it up from the timeline alone.

  2. S2

    Tasks outlive the run

    Tasks move to a store kept per target repository and get short numbers. A run boundary is written into every open task's timeline. The vision becomes a goal task. orch's brief opens each session by going through the open tasks with the operator before planning anything new.

    Demoquit the app with a task open, start a new run, and orch brings the task and its history back up with the operator.

  3. S3

    The operator writes from the Tasks view

    Open a task, comment, edit, close, reopen and reassign, each recorded under the name operator.

    Demoyou open a task from the UI, a worker claims it and comments, and you close it.

  4. S4

    Review and merge in the timeline, and on the worker cards

    Add review and a recorded merge. Each worker card shows that worker's current task and its latest timeline entry, and flags the gaps from the drift list: a task never claimed, done without a receipt, done without a review.

    Demoa full loop where every step shows up on the task, and a skipped review is visible on the card.

Questions the mockups raise

  • Screen 1 groups by goal. Grouping by owner is the other natural view; it could be a toggle, or the worker cards on Screen 4 may already cover it.
  • The "never claimed" flag needs a threshold. I would derive it at render time from timestamps already in the timeline, so nothing runs in the background to compute it.
  • A worker that has marked a task done but sent no receipt is flagged on Screen 4. Marking done before the receipt is the exact drift from the real runs, so this flag may be the most useful one.

Decisions to make before building

Each of these reverses or amends a recorded decision, so none of them is made yet.

1. Where tasks live

D-058 gives each run its own database and archives it when the next run starts, so today's tasks end with their run. Tasks that stay need a home outside that rotation.

Recommended

A. A task store per target repository

A separate append-only log under ~/.fleetor/, folded into tasks exactly as today. Run databases keep the messages. Each entry records its run, so History can still show what a past run did.

History has to read two stores.

B. Carry open tasks into each new run

At rotation, copy the open tasks' entries into the new run database. No new store.

A task's history is split across runs and copied each time. Closed tasks vanish from the live view.

C. Files in the target repository

One file per task, readable and diffable in git.

Breaks Tier 1.1: Fleetor never writes to your repository outside feature branches.

D. Real GitHub Issues

Use GitHub itself through gh.

Every pane needs GitHub credentials inside its fence, the target needs a GitHub remote, and nothing works offline or on test targets.

2. Tasks without an owner

D-047 requires an owner on every task, on the grounds that an ownerless task is a backlog item, and a backlog is "the ticket system's first move". A task released at the end of a run has no next owner yet, so this rule has to give.

Recommended

A. Owner optional

A task can sit unowned. Nothing picks it up automatically, which keeps the line D-047 cared about: no dispatcher.

Amends D-047.

B. Owner required, release must name a successor

Closer to D-047 as written.

Fails at the end of a run, when no successor exists yet.

3. The operator writes to tasks

D-047 keeps the Tasks view read-only so that every entry is an agent's attributed claim. Since D-051 the operator is a name in the record, so an operator entry is attributed too.

Recommended

A. Yes, attributed as operator

Open, comment, edit, close and reassign from the UI.

Amends D-047.

B. No, the operator speaks through orch

D-047 unchanged.

You cannot leave a task for a later run yourself.

Risks

  • Every new verb costs brief length. D-047 measured the task verb at roughly four times its estimate.
  • Open tasks from old runs can go stale. The orch brief has to treat them as questions for the operator, not as work to resume blindly.
  • Release comments only help if agents write them. The drift list shows prompted steps being skipped, so S4's flags are what make a missing one visible.
